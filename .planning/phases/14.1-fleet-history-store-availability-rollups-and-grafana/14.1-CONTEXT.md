# Phase 14.1: Fleet History Store, Availability Rollups and Grafana - Context

**Gathered:** 2026-09-28
**Status:** Ready for planning

<domain>
## Phase Boundary

The fleet gains long-term history. The poller writes metric and state history to a TSDB container whose long-term tier is MinIO (S3 API). The poller also writes one daily availability rollup object per day to MinIO. An analyst-facing Grafana reads the TSDB. A read-only same-origin HTTP path from the dashboard's nginx to the TSDB (and the rollup bucket) is built and proven, but **no dashboard history views are built in this phase** (D-50).

Locked inputs carried from `.planning/phases/14-fleet-intelligence/14-CONTEXT.md` (not re-discussed):
- **D-20:** Checkmk is Raw (CRE); the poller writes metric history. No abstraction for a future edition upgrade.
- **D-21:** Retention 3 years, downsampled; raw resolution roughly 30 days.
- **D-22:** Grafana sits alongside the dashboard, for analysts; optional, never replaces it.
- **D-23:** TSDB container in the compose stack with MinIO as long-term tier; local volume for recent data. Rollups are plain MinIO objects.
- **D-24:** Dashboard access to history is HTTP, read-only; browsers read, only the poller writes, write/admin endpoints unreachable (Phase 8 ACL principle). Amends the "no new backend" constraint; PROJECT.md and CLAUDE.md must be updated in this phase.

</domain>

<decisions>
## Implementation Decisions

### TSDB product
- **D-40:** Product choice stays with research (as D-23 says). Discussion recommendation to research: **Prometheus + Thanos** is the only open-source candidate verified (context7, 2026-09-28) to provide both an S3 long-term tier and free downsampling (compactor `--retention.resolution-raw/5m/1h`). **VictoriaMetrics OSS single-node** has no S3 tier (S3 only via vmbackup) and downsampling is **Enterprise-only**, so it would violate D-21/D-23 unless those are relaxed. Mimir: no native downsampling. InfluxDB 3 Core: needs verification of query-range limits and downsampling.
- **D-41:** The store must work against **both MinIO and AWS S3** by configuration only (endpoint, region, credentials). No MinIO-specific API use. Research must note that MinIO stopped publishing free community images/binaries in late 2025 (`minio/minio:latest` is frozen); portability to AWS S3 is the mitigation.

### What gets recorded
- **D-42:** The poller writes **every parsed `perf_data` metric from every service** it already reads (not only the Phase 12 gauges). Series labels include at least host and service description; label/metric naming is Claude's discretion (must be valid for the chosen TSDB).
- **D-43:** The poller also writes **state time series**: per-host state (UP/DOWN/UNREACHABLE, from `host_state_raw`) with a downtime flag, and per-service state (OK/WARN/CRIT/UNKNOWN). These feed availability (D-47) and Grafana state timelines.
- **D-44:** The poller stays stateless (existing pattern); the write path must not introduce on-disk state in the poller container. How the poller delivers samples (remote-write push vs exposing `/metrics` for scraping) is for research, consistent with the chosen TSDB.

### Availability definition
- **D-45:** Per device per day, report **UP %, DOWN %, UNOBSERVED % (UNREACHABLE)** and **downtime minutes**. Availability = UP / (UP + DOWN), with UNREACHABLE excluded as "not observable" (Phase 14 D-04) and shown alongside so it is never over-trusted.
- **D-46:** Scheduled downtime is **excluded from the denominator** and reported as its own figure.
- **D-47:** Periods with no data (poller or TSDB down) count as **"no data"**, never as up or down, and are reported as their own figure.
- **D-48:** Grouping: per device, and per **folder** (VLAN) as the location stand-in. The rollup schema carries a generic `location`-style group key so Phase 15 can add tower/room groups without a format change.
- **D-49:** Day boundary is **site local time, Asia/Singapore** (the stack's TZ).

### Rollup computation and format
- **D-51:** Rollups are computed **from the TSDB state series**, shortly after local midnight, for the previous day. Not from in-memory poller counters (a restart must not lose a day).
- **D-52:** **Auto-backfill**: on startup and at each midnight, write any missing day objects back as far as raw TSDB data allows (~30 days). **Never overwrite** an existing day object.
- **D-53:** Format: **one JSON object per day**, e.g. `availability/YYYY/MM/YYYY-MM-DD.json`, with a `schema_version` field, per-device and per-folder figures. Exact path/bucket naming is Claude's discretion.

### Dashboard involvement
- **D-50:** **No dashboard history views in 14.1.** No trend charts, availability panels or report page.
- **D-54:** 14.1 **does build the read-only HTTP path** (D-24): a same-origin nginx route in `deploy/dashboard-nginx.conf` to the TSDB's query API (and to the rollup objects), GET/read only. A smoke test must prove that query works and that write/admin/delete endpoints are **not** reachable through it. PROJECT.md and CLAUDE.md constraints are updated to record the amendment.

### Grafana
- **D-55:** Grafana container with a **provisioned TSDB datasource and 2-3 provisioned starter dashboards**: host metrics explorer, fleet state timeline, availability. **Login required** (admin password from `deploy/.env`); no anonymous access.

### Credentials
- **D-56:** **Reuse the existing `minioadmin` root credentials** for the TSDB and rollup writers. No dedicated keys, no root rotation in this phase. Constraint that still applies: the browser-facing read path (D-54) must not expose write capability. The proxy must not forward root credentials in a way that allows PUT/DELETE; the mechanism (for example, read-only bucket policy and nginx method restriction) is for research.

### Claude's Discretion
- Metric/label naming, bucket names and object paths, rollup JSON field names, Grafana dashboard layout, compose service names, and how the midnight job is scheduled inside the poller's loop.

</decisions>

<specifics>
## Specific Ideas

- Scale is small (~50 hosts, 15 s poll): three years at raw resolution is a few GB, so downsampling mostly serves long-range query speed, not storage.
- Carried caveat for 14.2: a projection is only as good as its history. Recording all perf_data from day one (D-42) maximises what 14.2 can trend later.

</specifics>

<code_context>
## Existing Code Insights

### Reusable Assets
- `parse_perf_data()` in `scripts/mqtt_poller.py` already turns every service's `perf_data` into `{metric: {value, warn, crit, ...}}`: the input for D-42.
- The host snapshot already carries `host_state_raw` and downtime flags: the input for D-43.
- MinIO is already deployed on `cmk_net` with `S3_ENDPOINT`/`S3_ACCESS_KEY`/`S3_SECRET_KEY` env names used by the worker service.
- The nginx `/checkmk-api/` location is the template for the new read-only proxy.

### Established Patterns
- The poller is stateless and self-heals from Livestatus; the history write path and rollup job must follow suit (D-44, D-51).
- The poller is installed via `pip install` in a plain `python:3.12-slim` image; any new client library is added there (and in `pyproject.toml` if tests import it).
- Secrets come from `deploy/.env` with empty-default interpolation, so a missing secret degrades rather than blocks the stack (Phase 10 CR-01 fix).
- Compose restart caveat (memory): restarting only the poller once broke Checkmk egress; smoke tests should use a full down/up.

### Integration Points
- Poller poll cycle: emit samples after host/service rows are read.
- Poller loop: midnight (Asia/Singapore) rollup and backfill job.
- `deploy/compose.yaml`: new TSDB container(s) and Grafana; ports must avoid those already in use.
- `deploy/dashboard-nginx.conf`: new read-only locations.

</code_context>
