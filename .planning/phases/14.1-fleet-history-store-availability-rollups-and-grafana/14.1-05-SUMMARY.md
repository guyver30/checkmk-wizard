# Phase 14.1 Plan 05: Daily Availability Rollups Summary

**Poller computes each local day's UP/DOWN/UNOBSERVED/downtime/no-data availability from ClickHouse's `history.host_state` via SQL, writes it once as JSON (boto3, HEAD-before-PUT) and once as Parquet (ClickHouse's own `s3()` export of the identical rows), and backfills missing days on startup and after 00:05 Asia/Singapore.**

## Performance

- **Duration:** ~50 min (includes reconstructing three atomic task commits from a combined working-tree edit — see Deviations)
- **Tasks:** 3/3
- **Files modified:** 4 (scripts/mqtt_poller.py, tests/test_mqtt_poller.py, pyproject.toml, uv.lock)

## Accomplishments

- **Task 1 — pure day math and figures:** `local_day_bounds`, `rollup_days_to_check`, `rollup_object_keys` (Hive-style `date=` prefix), and `compute_daily_availability`/`availability_document`/`availability_document_problems`. All pure, no I/O, never raise on odd input — matching `compute_incidents()`'s style. `uv add boto3 tzdata` recorded in `pyproject.toml`/`uv.lock`. 24 new tests, all exact-value assertions against the behavior table in the plan (e.g. 5760 up-samples at 15s → 1440 up-minutes/100% availability; an empty host list → exactly one fleet row with `availability_pct` `None`).
- **Task 2 — S3 writer and ClickHouse fetch:** `PollerConfig` gained `s3_endpoint`/`s3_access_key`/`s3_secret_key`/`s3_region`/`s3_addressing_style`/`availability_bucket`/`rollup_tz`/`rollup_backfill_days`/`rollup_delay_minutes`, masked correctly in `__repr__`. `build_s3_client`/`object_exists`/`write_if_absent` (HEAD-before-PUT). `fetch_first_data_day` bounds the backfill window; `fetch_host_day_counts` computes per-host sample counts fresh from ClickHouse every call (D-51). `export_parquet` refuses (no request) on a quote/backslash in an S3 credential and never sets `s3_truncate_on_insert`. `rollup_one_day` ties it together: both objects present → `"skipped"`, no ClickHouse call; otherwise compute → insert → export-if-missing → JSON-put-if-missing → `"written"`. `run_rollups` isolates one bad day from the rest of the backfill. 16 new tests, using a hand-rolled `_FakeS3` (no moto).
- **Task 3 — scheduling:** `RollupScheduler` (due immediately on a fresh instance; not due again same local day after success; due at the configured delay past midnight on a new day; backs off 300s on failure). `maybe_run_rollups` is a no-op until both `CLICKHOUSE_URL` and `S3_ENDPOINT` are set, and wraps the whole rollup attempt in one broad `except Exception` so it can never reach the poll loop. Wired into `run_forever()`: `rollup_tz` is resolved once at startup (disabling rollups on `ZoneInfoNotFoundError`/bad tz name, naming Pitfall 3 in the log line), and `maybe_run_rollups` is called every cycle after the Livestatus try/else and before `stop_event.wait`, independent of that cycle's Livestatus result. 10 new tests.
- Full suite: 643 tests passed (593 baseline carried from plan 14.1-02 + 50 new this plan: 24 + 16 + 10), ruff clean on both modified files.

## Decisions Made

- Placed all new functions in one contiguous section directly after `write_history()` and before `available_host_columns()`, in the same task order as the plan (Task 1's pure functions, then Task 2's S3/ClickHouse functions, then Task 3's scheduler) — matches this module's existing habit of clustering one subsystem's functions together.
- `compute_daily_availability`'s folder/fleet rows sum each host's own `base` (`max(expected, observed)` computed per host) rather than deriving one group-level base from `device_count * expected` — this is what makes "more samples than a day holds" degrade gracefully per-host without inflating a group's percentage base artificially.

Separately, all three tasks' implementation and tests were written and verified together in one continuous working-tree edit (as the plan's TDD guidance itself organizes each task as one deliverable, per `14.1-02-SUMMARY.md`'s precedent) before the per-task commit split was performed. To honor "commit each task atomically" without discarding any verified work, the three task-sized deltas were reconstructed losslessly after the fact: each task's exact known text was replayed against a copy of the pre-plan file to build three intermediate file states (`task1.py`, `task2.py`, and the final working-tree state as `task3`), each was diffed against the next to confirm the split was purely additive (zero unexpected line removals) and re-verified to compile, and each was staged via `git hash-object`/`git update-index --cacheinfo` (never `git checkout`/`reset` against the working tree, which stayed at the fully-tested final state throughout) and committed in task order. The working tree's byte-for-byte content was diffed against the pre-split backup after the last commit and found identical.
