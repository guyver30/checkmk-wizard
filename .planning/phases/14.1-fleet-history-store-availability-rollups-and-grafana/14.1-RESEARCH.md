## Summary

Phase 14 already locked the product choice via prior research (context7, 2026-09-28): **Prometheus + Thanos** is the only open-source stack that satisfies both "S3-compatible long-term tier" and "free downsampling" (D-40/D-41) — VictoriaMetrics OSS gates downsampling behind Enterprise, Mimir has no native downsampling built for this shape, and InfluxDB 3 Core's query-range/downsampling story is unverified. This research confirms and extends that choice with the concrete component topology, the poller's write path, and the rollup/read-path mechanics.

The shape that emerges: the poller (already reading Livestatus and parsing `perf_data`) gains a `/metrics` HTTP endpoint using the official `prometheus_client` library — **scrape, not push** — so a new Prometheus container pulls samples every poll interval. This keeps the poller exactly as stateless as D-44 requires (it never touches the TSDB's storage, just serves an in-memory snapshot on request) and avoids remote-write's protobuf+snappy encoding entirely. Prometheus writes to a local volume (recent ~30 days); a Thanos **sidecar** uploads 2-hourly blocks to MinIO; a Thanos **Store Gateway** serves older blocks back out of MinIO; a Thanos **Compactor** does the deduplication, downsampling (5m after 30d² deduplication, 1h after a longer window) and 3-year retention enforcement entirely inside the bucket; a Thanos **Query** (Querier) merges sidecar + store-gateway results and is the single read-only HTTP API surface everything else (nginx, Grafana, the future 14.2 analytics container) talks to. This is five new containers, which is more infrastructure than any prior phase in this project, but it is the minimal correct shape for Thanos's own architecture at the retention/downsampling D-21 already locked — trying to skip a piece (e.g. no Store Gateway) silently loses query access to data older than local Prometheus retention.

For availability rollups (D-45..D-53), the recommendation is to **not** build complex PromQL day-math. Instead, the poller's midnight job fetches each host's raw state/downtime series for the target day via Thanos Query's `/api/v1/query_range` (still inside 30-day raw retention, so no resolution loss), and computes UP/DOWN/UNOBSERVED/downtime percentages as a small pure Python function — consistent with this project's existing style of pure, unit-testable functions (`compute_incidents`, `parse_perf_data`) rather than opaque query expressions. "No data" (D-47) is derived from Prometheus's own `up{job="poller"}` scrape-health series compared against the expected sample count for the day, not inferred from PromQL gaps.

For the read-only HTTP path (D-24/D-54) and rollup writer (D-56), the safest posture given Thanos Query's admin-endpoint surface is not fully documented (LOW confidence — flagged below) is an **allowlist, not a blocklist**: nginx forwards only a fixed set of known-safe, GET-only paths (`/api/v1/query`, `/api/v1/query_range`, `/api/v1/series`, `/api/v1/labels`, `/api/v1/label/*/values`) and 404s everything else by default, so an undocumented admin endpoint is blocked by construction rather than by having correctly enumerated it. The rollup bucket is served the same way (a GET-only nginx proxy to MinIO with the existing root credentials, method-restricted) rather than a public anonymous bucket policy, keeping D-56's "no dedicated keys" decision compatible with "must not expose write capability."

**Primary recommendation:** Prometheus (scraped from the poller's new `/metrics` endpoint) + Thanos sidecar + store gateway + compactor + querier, S3 tier on MinIO via `objstore.config` (works unmodified against AWS S3 per D-41); poller computes rollups in Python from Thanos Query range-vector fetches and writes them to MinIO via `boto3` with HEAD-before-PUT never-overwrite semantics; nginx exposes an explicit GET-only allowlist of Thanos Query paths plus the rollup bucket; Grafana provisioned via file-based datasource/dashboard YAML, `GF_SECURITY_ADMIN_PASSWORD` from `deploy/.env`.

### Pattern 1: Poller exposes metrics for scraping, never pushes
**What:** `prometheus_client.start_http_server(port, addr="0.0.0.0")` (or a manually-managed `HTTPServer` bound to a `CollectorRegistry`) started once in `run_forever`, alongside the existing MQTT client. Every `run_cycle` updates `Gauge`/`Enum` objects in-process; Prometheus scrapes on its own interval.
**When to use:** Any time a stateless process needs to publish metrics without owning storage — exactly the poller's existing self-description ("no on-disk state").
**Example:**
```python
# Source: prometheus/client_python README (github.com/prometheus/client_python)
from prometheus_client import start_http_server, Gauge, Enum

METRIC_GAUGE = Gauge(
    "checkmk_perf_data", "Parsed Nagios perf_data value",
    ["host", "service", "metric"],
)
HOST_STATE = Enum(
    "checkmk_host_state", "Current Checkmk host state",
    ["host"], states=["up", "down", "unreach"],
)

start_http_server(9200)  # once, at startup

# each poll cycle:
for service in services:
    for metric_name, fields in service.perf_data.items():
        METRIC_GAUGE.labels(host=service.host_name, service=service.description, metric=metric_name).set(fields["value"])
for snapshot in snapshots:
    HOST_STATE.labels(host=snapshot.id).state(snapshot.host_state_raw.lower())
```
`Enum` publishes one time series per state, 1 for the current state and 0 for the others — this is exactly what makes `avg_over_time(...[24h])` a direct fraction-of-day computation (D-45's UP %) without extra PromQL logic.

### Pattern 2: Rollup computed in Python from a range-vector fetch, not PromQL day-math
**What:** The midnight job issues one `query_range` HTTP call per host per day (`start`/`end` = Asia/Singapore day boundary converted to UTC, `step` = poll interval) against Thanos Query, then computes UP/DOWN/UNOBSERVED/downtime percentages as a plain Python function over the returned `(timestamp, value)` pairs.
**When to use:** Whenever the "obvious" PromQL expression would need to encode business rules (downtime exclusion, no-data detection) that are easier to state, test and audit as Python — this project already prefers this shape (`compute_incidents`, `classify_host_services`).
**Example:**
```python
# Illustrative — no official source; matches this project's existing pure-function style
def compute_daily_availability(
    state_samples: list[tuple[float, str]],   # (unix_ts, "up"|"down"|"unreach")
    downtime_samples: list[tuple[float, float]],  # (unix_ts, 0|1)
    scrape_interval_seconds: float,
    expected_samples: int,
) -> dict:
    """Pure function — mirrors compute_incidents()'s no-hidden-state style."""
    if not state_samples:
        return {"no_data_pct": 100.0, "up_pct": 0.0, "down_pct": 0.0, "unobserved_pct": 0.0, "downtime_minutes": 0.0}
    downtime_ts = {ts for ts, flag in downtime_samples if flag}
    counts = {"up": 0, "down": 0, "unreach": 0, "downtime": 0}
    for ts, state in state_samples:
        if ts in downtime_ts:
            counts["downtime"] += 1
            continue
        counts[state] += 1
    observed = sum(counts.values())
    no_data = max(expected_samples - len(state_samples), 0)
    denom = counts["up"] + counts["down"] or 1  # D-45: availability excludes UNREACHABLE
    return {
        "up_pct": round(counts["up"] / denom * 100, 2),
        "down_pct": round(counts["down"] / denom * 100, 2),
        "unobserved_pct": round(counts["unreach"] / max(observed, 1) * 100, 2),
        "downtime_minutes": round(counts["downtime"] * scrape_interval_seconds / 60, 1),
        "no_data_pct": round(no_data / expected_samples * 100, 2) if expected_samples else 0.0,
    }
```

### Pattern 3: Never-overwrite object write via HEAD-before-PUT
**What:** Before writing `availability/YYYY/MM/YYYY-MM-DD.json`, `head_object` the key; only `put_object` if it 404s. Accept the narrow TOCTOU race as negligible (single writer, once-daily-per-day job).
**When to use:** D-52's "never overwrite" requirement, on a backend (MinIO) whose support for atomic `If-None-Match: *` conditional writes is version-dependent (see Pitfalls).
**Example:**
```python
# Illustrative, boto3 documented pattern (docs.aws.amazon.com/boto3)
import boto3
from botocore.config import Config
from botocore.exceptions import ClientError

s3 = boto3.client(
    "s3",
    endpoint_url=os.environ["S3_ENDPOINT"],       # works unmodified against AWS S3 too (D-41)
    aws_access_key_id=os.environ["S3_ACCESS_KEY"],
    aws_secret_access_key=os.environ["S3_SECRET_KEY"],
    config=Config(signature_version="s3v4", s3={"addressing_style": "path"}),
    region_name="us-east-1",
)

def write_day_if_absent(bucket: str, key: str, payload: bytes) -> bool:
    try:
        s3.head_object(Bucket=bucket, Key=key)
        return False  # already exists — never overwrite (D-52)
    except ClientError as exc:
        if exc.response["Error"]["Code"] != "404":
            raise
    s3.put_object(Bucket=bucket, Key=key, Body=payload, ContentType="application/json")
    return True
```

### Pattern 4: Allowlist-only read proxy (not a blocklist)
**What:** nginx `location` blocks that match exact known-safe paths and reject any method but GET; everything unmatched falls through to nginx's default 404.
**When to use:** Any time the upstream's full endpoint surface (here: Thanos Query's admin/debug endpoints) isn't fully documented — allowlisting removes the need to enumerate every dangerous path.
**Example:**
```nginx
# Extends deploy/dashboard-nginx.conf's existing /checkmk-api/ same-origin pattern
location = /tsdb-api/v1/query {
    limit_except GET { deny all; }
    proxy_pass http://thanos-query:10902/api/v1/query;
}
location = /tsdb-api/v1/query_range {
    limit_except GET { deny all; }
    proxy_pass http://thanos-query:10902/api/v1/query_range;
}
location = /tsdb-api/v1/series {
    limit_except GET { deny all; }
    proxy_pass http://thanos-query:10902/api/v1/series;
}
location ~ ^/tsdb-api/v1/label/[^/]+/values$ {
    limit_except GET { deny all; }
    proxy_pass http://thanos-query:10902$request_uri;
}
# No catch-all /tsdb-api/ location: an unmatched path (including any undocumented
# admin/debug endpoint) 404s by nginx's own default, not by an explicit deny rule.

location /availability/ {
    limit_except GET { deny all; }
    proxy_pass http://minio:9000/fleet-availability/;
}
```

### Anti-Patterns to Avoid
- **Blocklisting Thanos Query's admin surface:** Thanos Query's exact endpoint list beyond the documented `/api/v1/*` query paths is not fully confirmed in public docs (LOW confidence, see Pitfalls) — a blocklist can only block what's known, an allowlist blocks everything except what's proven safe.
- **Publishing rollups from in-memory poller counters:** D-51 explicitly rejects this — a poller restart mid-day must not lose or corrupt that day's figures; always recompute from the TSDB's durable state series.
- **Treating MinIO's `If-None-Match: *` support as guaranteed:** it varies by MinIO version/build (see Pitfalls) — HEAD-before-PUT is the portable mechanism; treat conditional-write support as a bonus hardening layer, not the primary guarantee.
- **Relying on container `TZ=Asia/Singapore` for day-boundary math:** compute boundaries explicitly with `zoneinfo.ZoneInfo("Asia/Singapore")` in Python so the logic is correct regardless of how the container's OS timezone is configured, and is unit-testable without a live container.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Prometheus exposition-format text encoding | A hand-written `# TYPE`/`# HELP` text generator | `prometheus_client` | Exact escaping/formatting rules (label value quoting, NaN/Inf encoding) are easy to get subtly wrong; the official client is the reference implementation |
| S3 conditional/atomic writes across MinIO + AWS | A custom distributed lock or ETag-diffing scheme | HEAD-before-PUT (accept the narrow single-writer race) or `If-None-Match: *` where supported | D-52's actual risk (a concurrent second writer) doesn't exist — the midnight job is a singleton per poller process; a home-grown lock would add complexity with no real risk it removes |
| Long-term downsampled TSDB storage | A custom rollup-and-delete script against Prometheus's own TSDB | Thanos Compactor's `--retention.resolution-*` flags | Compaction, deduplication and downsampling correctness (especially across HA replicas, though this deployment has none) is exactly what Thanos already solved |
| Grafana dashboard/datasource setup via clicking in the UI | Manual UI configuration, undocumented and lost on redeploy | File-based provisioning (`datasources/*.yaml`, `dashboards/*.yaml` + JSON) | D-55 requires this to survive a redeploy the same way the rest of this stack is config-as-code (`deploy/*.conf`, `deploy/*.yaml`) |

**Key insight:** every "Don't Hand-Roll" item here has an existing, actively maintained open-source implementation that is also the documented, intended way to solve it — the temptation in this phase is scope creep toward custom scripts (a home-grown TSDB, a home-grown lock), which would also be the parts hardest to keep correct under this project's "everything self-heals, nothing is fragile" convention.

## Common Pitfalls

### Pitfall 1: `python:3.12-slim` has no IANA timezone database
**What goes wrong:** `zoneinfo.ZoneInfo("Asia/Singapore")` raises `ZoneInfoNotFoundError` at runtime — the midnight job silently can't compute day boundaries.
**Why it happens:** Debian slim images intentionally omit `/usr/share/zoneinfo`; `zoneinfo` falls back to the PyPI `tzdata` package only if it's installed. [VERIFIED via WebSearch, cross-referenced against `docs.python.org/3/library/zoneinfo.html`'s documented fallback behavior]
**How to avoid:** Add `tzdata` to the poller's `pip install` list in `deploy/compose.yaml` (already verified clean by slopcheck).
**Warning signs:** Works fine in local dev (host OS usually has tzdata), fails only inside the container — a classic "works on my machine" trap.

### Pitfall 2: MinIO's `If-None-Match: *` conditional-write support is version-dependent
**What goes wrong:** Code that relies on `PutObject` with `If-None-Match: *` returning `412 Precondition Failed` to enforce "never overwrite" may instead get a `200` (silent overwrite) on an older or differently-configured MinIO build.
**Why it happens:** AWS S3 added the wildcard `If-None-Match: *` conditional-write semantic in 2024; MinIO's support for the specific wildcard form (vs. an exact-ETag match) has lagged and evolved across releases — public trackers show both "not supported" and "now supported" reports at different points. [LOW confidence — WebSearch only, sources disagree by MinIO version; not verified against this project's pinned MinIO build]
**How to avoid:** Use HEAD-before-PUT as the primary mechanism (works identically on every S3-compatible backend, no conditional-header support required); treat `If-None-Match` as an optional defense-in-depth layer if the deployed MinIO build is confirmed to support it.
**Warning signs:** A rollup day silently gets overwritten after a backfill re-run — write a regression test that calls `write_day_if_absent` twice and asserts the second call returns `False` and the object bytes are unchanged.

### Pitfall 3: Thanos Query's full HTTP endpoint surface isn't exhaustively documented publicly
**What goes wrong:** A blocklist-style nginx config ("deny everything except known write paths") could miss an undocumented admin/debug endpoint, defeating D-54's "write/admin endpoints unreachable" requirement.
**Why it happens:** Public Thanos docs and GitHub search did not turn up a definitive, current list of every HTTP path Thanos Query registers (health/ready endpoints are documented; a Prometheus-style `/-/quit` shutdown endpoint's presence on Thanos Query specifically could not be confirmed either way in this research pass). [LOW confidence — WebSearch inconclusive]
**How to avoid:** Use the allowlist pattern (Pattern 4 above) so this gap doesn't matter — only explicitly listed GET paths are ever forwarded.
**Warning signs:** The D-54 smoke test should explicitly attempt a `POST`/`DELETE`/`PUT` against the proxy's base path and every allowlisted path, and attempt a `GET` against a handful of guessed admin-style paths (`/-/quit`, `/-/reload`, `/debug/pprof/`) — all must return the proxy's own 404/403, not a Thanos response.

### Pitfall 4: Publishing every `perf_data` metric with unbounded label cardinality
**What goes wrong:** If a metric label ever includes a high-cardinality value (e.g. a raw timestamp, a per-request ID) instead of the intended `host`+`service`+`metric` triple, Prometheus/Thanos memory and the compactor's runtime blow up.
**Why it happens:** D-42 says "every parsed perf_data metric from every service" — at ~50 hosts × ~20 services × a handful of perf_data keys each, cardinality is in the low thousands, which is fine, but a careless implementation (e.g. labeling by `plugin_output` text) would not be.
**How to avoid:** Label only by `host`, `service` (description), and `metric` (perf_data key name) — never by a free-text or high-cardinality field. Validate this at code-review time against the CONTEXT specifics ("Scale is small (~50 hosts, 15s poll)").
**Warning signs:** Prometheus's own `prometheus_tsdb_head_series` metric growing unboundedly instead of plateauing after the fleet's services stabilize.

### Pitfall 5: Running the rollup job only at midnight misses restarts and outages
**What goes wrong:** If the poller container was down at local midnight, that day's rollup is simply never written, silently leaving a permanent gap.
**Why it happens:** D-52 explicitly anticipates this ("on startup and at each midnight... auto-backfill... never overwrite") — this is why the requirement exists, not a hypothetical edge case.
**How to avoid:** Implement the backfill scan as the same code path run at both startup and midnight: list which of the last ~30 days have no rollup object yet (one `head_object` or `list_objects_v2` call), compute and write each missing one.
**Warning signs:** A gap in the availability history around any period the poller container was observed to be restarting (compose logs, `podman ps` history).
