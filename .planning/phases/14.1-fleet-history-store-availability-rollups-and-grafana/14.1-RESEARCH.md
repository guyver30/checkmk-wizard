- **D-41:** The store must work against **both MinIO and AWS S3** by configuration only (endpoint, region, credentials). No MinIO-specific API use. MinIO stopped publishing free community images/binaries in late 2025 — portability to AWS S3 is the mitigation. Same holds for ClickHouse's S3 disk config and the poller's S3 writer. **This research escalates that finding — see Pitfall 1.**
- **D-42:** Poller writes **every parsed `perf_data` metric from every service**. Series labels include at least host and service description; naming is Claude's discretion (must be valid for ClickHouse).
- **D-43:** Poller also writes **state time series**: per-host state (UP/DOWN/UNREACHABLE) with a downtime flag, and per-service state (OK/WARN/CRIT/UNKNOWN).
- **D-44:** Poller stays stateless; write path introduces no on-disk state in the poller container. - **D-45:** Per device per day: UP %, DOWN %, UNOBSERVED % (UNREACHABLE), downtime minutes. Availability = UP / (UP + DOWN); UNREACHABLE excluded as "not observable" and shown alongside.

- **D-47:** Periods with no data count as "no data", never up or down, reported as their own figure.
- **D-48:** Grouping: per device and per folder (VLAN, as location stand-in). Rollup schema carries a generic `location`-style group key for Phase 15.
- **D-49:** Day boundary is site local time, **Asia/Singapore**.
- **D-51:** Rollups computed **from the ClickHouse state tables** (SQL), shortly after local midnight, for the previous day — not from in-memory poller counters.
- **D-52:** **Auto-backfill** on startup and each midnight, as far as raw retention allows (~30 days). **Never overwrite** an existing day object.
- **D-53:** Format: one JSON object per day (`availability/YYYY/MM/YYYY-MM-DD.json`), `schema_version` field, per-device and per-folder figures. Exact path/bucket naming is Claude's discretion.
- **D-57 (added 2026-09-28):** Each day's rollup is **also written as Parquet**, same figures, next to the JSON (e.g. Hive-style `availability_parquet/date=YYYY-MM-DD/…parquet`). JSON serves the future dashboard views; Parquet is the Databricks/Athena bridge. Never-overwrite (D-52) applies to both; a day counts as written only when both exist. Whether ClickHouse writes the Parquet or the poller does is for research (see Pattern 3 below).
- **D-50:** **No dashboard history views in 14.1.** No trend charts, availability panels, report page.
- **D-54:** 14.1 builds the read-only HTTP path: same-origin nginx route to ClickHouse's HTTP interface and to the rollup objects (JSON and Parquet), GET/read only. Login required (admin password from `deploy/.env`); no anonymous access.

ClickHouse's own users (writer and read-only) are new and separate from MinIO credentials, passwords from `deploy/.env` with the empty-default pattern. No dedicated keys, no root rotation. The read path must not expose write capability regardless; the mechanism is for research.

## Summary

CONTEXT.md's D-40 already locked the product: **ClickHouse**, single-node OSS, one container, S3 disk on MinIO today and AWS S3 by config change later. This research confirms every load-bearing ClickHouse claim in CONTEXT.md against the official docs via context7 (`clickhouse/clickhouse-docs`, verified live 2026-09-28) and fills in the concrete shape the planner needs: table design, TTL expressions, the poller's write path, the rollup computation and Parquet export, the read-only proxy, and Grafana provisioning.

The shape that emerges is dramatically simpler than the superseded Prometheus + Thanos design: **one new container** (`clickhouse`) instead of five (Prometheus, sidecar, store-gateway, compactor, querier). ClickHouse's `MergeTree` family natively supports everything D-21/D-23/D-40b need in a single engine: a `storage_policy` with a `default` (local) volume and an `s3` volume, `TTL <expr> TO VOLUME 's3'` to age data out to the S3 tier, and `TTL <expr> GROUP BY <prefix-of-order-by> SET <aggregates>` to downsample expired rows in place — no separate compactor process, no separate query-federation layer. The poller keeps its existing synchronous, `urllib`-only style (confirmed live in this session: `scripts/mqtt_poller.py` uses **no async/httpx anywhere** — it is a threaded, synchronous script driven by `run_forever()`/`time.sleep`, contradicting an assumption in this task's brief) and gains one more single-choke-point function that does a plain HTTP `POST` to ClickHouse's HTTP interface with a `FORMAT JSONEachRow` body — the same shape `_livestatus_request`/`fetch_host_config` already use, no new HTTP client dependency needed at all (not `clickhouse-connect`, not `httpx`).

For availability rollups (D-45..D-53, D-57), the state tables live in ClickHouse specifically so the midnight job can ask ClickHouse itself to do the per-day aggregation in SQL (`GROUP BY toDate(ts, 'Asia/Singapore')`), then the poller does the same small, pure, unit-testable Python transform this project already uses elsewhere (`compute_incidents`, `parse_perf_data`) to turn ClickHouse's result rows into the JSON schema, and writes both the JSON (via `boto3`, HEAD-before-PUT never-overwrite — the same portable, backend-agnostic mechanism that survives an unconfirmed MinIO conditional-write feature) and the Parquet (via ClickHouse's own `INSERT INTO FUNCTION s3(..., 'Parquet')`, run from the same query connection, so no new Python Parquet-writing dependency like `pyarrow` is needed on the poller side).

For the read-only HTTP path (D-24/D-54), ClickHouse's HTTP GET already forces `readonly=1` **at the server itself** (confirmed via context7 against ClickHouse's own C++ access-control source: `ContextAccess.cpp`'s `not_readonly_flags` check explicitly special-cases "For queries over HTTP, method GET implies readonly"). Combined with a settings profile pinning `readonly = 1` on a dedicated `dashboard_reader` user with `GRANT SELECT` only on the history database, this gives **two independent layers** enforcing read-only, exactly as D-54 asks: nginx's `limit_except GET { deny all; }` is belt, ClickHouse's own server-side readonly enforcement is braces. The rollup bucket (JSON + Parquet) gets the same GET-only nginx proxy pattern already used for `/checkmk-api/`.

One finding materially escalates a risk CONTEXT.md already flagged (D-41's "MinIO stopped publishing free community images... late 2025"): as of **2026-09-11** (17 days before this research date), `minio/minio` and `minio/mc` were not merely frozen but **fully removed from Docker Hub** — the currently-running `deploy/compose.yaml`'s `minio` service (`image: minio/minio:latest`) will fail to *pull* on any fresh clone or `podman compose pull` from today onward, even though the already-running container keeps working. Since this phase adds two *new* hard dependencies on that same MinIO service (ClickHouse's S3 disk, the rollup/Parquet writers), this is flagged prominently as Pitfall 1 with a concrete, low-effort mitigation (repoint to a pinned `quay.io/minio/minio` tag).

**Primary recommendation:** One `clickhouse` container (official `clickhouse/clickhouse-server` image), schema and users provisioned via `/docker-entrypoint-initdb.d/*.sql` (writer user + `dashboard_reader` read-only user with a `readonly=1` settings profile), S3 disk configured against MinIO today (`endpoint` with the documented trailing `//`) and portable to AWS S3 by config only; poller pushes each cycle's metric/state rows via a single new `_clickhouse_insert()` choke-point function using plain `urllib.request` (no new poller dependency); midnight rollup job queries ClickHouse's state tables via HTTP GET, computes the day's figures in a pure Python function, writes JSON via `boto3` HEAD-before-PUT and triggers a ClickHouse-side `INSERT INTO FUNCTION s3(..., 'Parquet')` for the Parquet twin; nginx exposes a GET-only allowlist to ClickHouse's `/` endpoint (as the read-only user, via a fixed backend query pattern) and to the rollup bucket; Grafana provisioned via file-based datasource/dashboard YAML with `GF_INSTALL_PLUGINS=grafana-clickhouse-datasource` and `GF_SECURITY_ADMIN_PASSWORD` from `deploy/.env`.

**Not added, and why:** `clickhouse-connect` (official Python client, PyPI `1.9.0` [VERIFIED: PyPI registry]) was considered and rejected — the poller's INSERT path is a single `POST` with a `FORMAT JSONEachRow` body plus reading back a query result as JSON, both trivially doable with the stdlib `urllib.request` this file already uses exclusively for its REST calls (`fetch_host_config`). Adding `clickhouse-connect` would introduce a second HTTP-client convention into a file that has deliberately used only `urllib`/`socket` for five phases (CLAUDE.md Simplicity First: no dependency for something a few lines of stdlib already does, matching this project's existing choke-point pattern). `pyarrow` was considered for a poller-side Parquet writer and rejected for the same reason D-57 itself flags as "for research": ClickHouse can write the Parquet directly from the rows it already holds via `INSERT INTO FUNCTION s3(...)`, so no Python Parquet library is needed at all.

### Alternatives Considered
| Instead of | Could Use | Tradeoff |
|------------|-----------|----------|
| ClickHouse | Prometheus + Thanos | D-40a already rejects this (no native Parquet/Databricks path, 5 containers vs. 1) — not re-litigated |
| `urllib.request` POST INSERT | `clickhouse-connect` (official Python client) | Adds compression, connection pooling, typed result parsing — genuinely useful at higher throughput, but at ~50 hosts/15s this project's existing "one choke-point function per subsystem" convention already solves the actual problem (normalized error handling) with zero new dependencies |
| ClickHouse-side Parquet export | Poller-side `pyarrow` writer | Would duplicate data ClickHouse already has in memory/on disk from the SQL fetch; `INSERT INTO FUNCTION s3(..., 'Parquet')` is one more SQL statement against the same connection, not a new library or a second data round-trip |
| `TTL … GROUP BY … SET` in-place downsampling | Materialized view into a separate `AggregatingMergeTree` rollup table | CONTEXT.md D-40 names both as options; `TTL GROUP BY` needs no second table and no query-time `*Merge()` rewriting, but its `GROUP BY` columns must be a prefix of the table's `ORDER BY`/`PRIMARY KEY` [VERIFIED via context7] — this constrains the table's key design (see Architecture Patterns); a materialized view is more flexible but is a second table with its own storage/TTL to manage. Recommend `TTL GROUP BY` for the metric/state tables here since the natural key (`metric_name, host, toStartOfInterval(ts)` or similar) already needs to be a query-time filter prefix regardless |
| Allowlist nginx proxy to ClickHouse's `/` endpoint | Blocklist (deny known-bad paths) | ClickHouse's HTTP interface is one endpoint (`/` plus `/ping`, `/replicas_status`) rather than Thanos Query's larger surface, which somewhat reduces this risk vs. the superseded design — but the *query itself* passed in the URL/body could still request a system table or a `SETTINGS readonly=0` override if the read-only user's grants were misconfigured; allowlist-by-method (GET-only) plus server-side `readonly=1` (two independent layers, not one) is still the safer posture and is what D-54 asks for |

### Pattern 1: Poller pushes one INSERT batch per cycle, never buffers
**What:** After the existing MQTT publish step, build a newline-delimited JSON batch (`FORMAT JSONEachRow`) of this cycle's metric rows and state rows, and `POST` it to ClickHouse's HTTP interface in one request. On any failure, log and drop the batch — no retry queue, no on-disk buffer (D-44).
**When to use:** Every poll cycle, immediately after the values that feed it are computed (`parse_perf_data`, `host_state_raw`) — matches D-44's "stateless, gap reads as no data" contract exactly.
**Example:**
```python
# Source: HTTP insert shape verified via context7 (clickhouse/clickhouse-docs,
# docs/integrations/interfaces/http.md); function shape follows this project's
# own fetch_host_config() choke-point convention (scripts/mqtt_poller.py:1214-1309)
class ClickHouseError(RuntimeError):
    """Raised when a ClickHouse HTTP request fails; caught at the call site and
    logged — never allowed to interrupt the mandatory Livestatus poll cycle."""


def _clickhouse_insert(base_url: str, table: str, rows: list[dict], timeout: float) -> None:
    if not rows:
        return
    body = "\n".join(json.dumps(row) for row in rows).encode()
    query = f"INSERT INTO {table} FORMAT JSONEachRow"
    url = f"{base_url}/?query={urllib.parse.quote(query)}"
    try:
        request = urllib.request.Request(url, data=body, method="POST")
        with urllib.request.urlopen(request, timeout=timeout) as response:
            response.read()
    except (urllib.error.HTTPError, urllib.error.URLError, OSError, TimeoutError) as exc:
        raise ClickHouseError(f"ClickHouse INSERT into {table} failed: {exc}") from exc
```
Call site (inside `run_forever`'s existing per-cycle block, after MQTT publish):
```python
try:
    _clickhouse_insert(clickhouse_url, "metrics", metric_rows, timeout=5.0)
    _clickhouse_insert(clickhouse_url, "host_state", host_state_rows, timeout=5.0)
    _clickhouse_insert(clickhouse_url, "service_state", service_state_rows, timeout=5.0)
except ClickHouseError as exc:
    _logger.warning("ClickHouse write failed this cycle; gap reads as no-data (D-47): %s", exc)
```

### Pattern 2: Table design — `TTL … TO VOLUME` and `TTL … GROUP BY … SET` on the same table
**What:** A single `MergeTree` table per series family (metrics, host_state, service_state), whose `ORDER BY`/`PRIMARY KEY` starts with the columns the downsampling `GROUP BY` needs (a documented constraint: "The `GROUP BY` columns in the `TTL` clause must be a prefix of the `PRIMARY KEY`" [VERIFIED via context7]), carrying two TTL clauses: one that rolls up expired raw rows via `GROUP BY … SET`, another that moves aged parts to the `s3` volume via `TO VOLUME`.
**When to use:** This is the mechanism that replaces the superseded design's entire Thanos Compactor + Store Gateway — D-40b's "5-minute for ~1 year, 1-hour to 3 years" shape is expressed as TTL expressions on the table itself, not a separate process.
**Example:**
```sql
-- Source: pattern verified via context7 against clickhouse/clickhouse-docs
-- (docs/guides/developer/ttl.md "Implementing a rollup" + "Modify table TTL
-- to move data across volumes"); column/table names are this phase's own design.
CREATE TABLE metrics
(
    ts        DateTime,
    host      LowCardinality(String),
    service   LowCardinality(String),
    metric    LowCardinality(String),
    value     Float64,
    value_min AggregateFunction(min, Float64) DEFAULT minState(value),
    value_max AggregateFunction(max, Float64) DEFAULT maxState(value),
    value_avg AggregateFunction(avg, Float64) DEFAULT avgState(value)
)
ENGINE = MergeTree
PRIMARY KEY (metric, host, service, toStartOfFiveMinutes(ts), ts)
TTL
    ts + INTERVAL 30 DAY GROUP BY metric, host, service, toStartOfFiveMinutes(ts)
        SET value_min = minMerge(value_min), value_max = maxMerge(value_max),
            value_avg = avgMerge(value_avg), ts = toStartOfFiveMinutes(ts),
    ts + INTERVAL 1 YEAR TO VOLUME 's3'
SETTINGS storage_policy = 's3_tiered';
```
`value` itself becomes meaningless post-rollup (only the aggregate columns are trustworthy after 30 days) — the planner should decide in the plan whether raw `value` is dropped/zeroed by the `SET` clause or left stale-but-ignored; either is valid, document the choice. A second, coarser `TTL … GROUP BY toStartOfHour(ts) … SET …` clause at the 1-year mark achieves the "1-hour to 3 years" tier from D-40b, chained after the 5-minute one.

### Pattern 3: Rollup — Python day-math against ClickHouse SQL, Parquet via ClickHouse itself
**What:** The midnight job issues one `SELECT ... WHERE ts >= <day-start> AND ts < <day-end>` HTTP GET per day against ClickHouse's `host_state`/`service_state` tables (still inside 30-day raw retention for the ~30-day backfill window D-52 requires), computes UP/DOWN/UNOBSERVED/downtime percentages as a small pure Python function (same pattern as `compute_incidents`), writes the JSON via `boto3` HEAD-before-PUT, and — for D-57 — issues one more ClickHouse statement to write the same day's figures as Parquet directly from a `VALUES`/temp-table insert into `s3(..., 'Parquet')`, or (simpler) writes the JSON's own computed row set back into ClickHouse as a temp table first, then exports that.
**When to use:** Whenever the "obvious" SQL expression would need to encode business rules (downtime exclusion, no-data detection) that are easier to state, test and audit as Python — matches this project's established preference.
**Example:**
```python
# Illustrative — matches this project's existing pure-function style
# (compute_incidents, classify_host_services); SQL shape verified via context7
# GROUP BY/day-boundary conventions (docs/sql-reference/functions/date-time-functions.md
# toDate(ts, 'Asia/Singapore') pattern is documented ClickHouse timezone-aware date truncation).
def compute_daily_availability(
    state_rows: list[tuple[float, str]],        # (unix_ts, "up"|"down"|"unreach")
    downtime_rows: list[tuple[float, bool]],     # (unix_ts, downtime_flag)
    scrape_interval_seconds: float,
    expected_samples: int,
) -> dict:
    """Pure function — no I/O. Mirrors compute_incidents()'s no-hidden-state style."""
    if not state_rows:
        return {"no_data_pct": 100.0, "up_pct": 0.0, "down_pct": 0.0,
                 "unobserved_pct": 0.0, "downtime_minutes": 0.0}
    downtime_ts = {ts for ts, flag in downtime_rows if flag}
    counts = {"up": 0, "down": 0, "unreach": 0, "downtime": 0}
    for ts, state in state_rows:
        if ts in downtime_ts:
            counts["downtime"] += 1
            continue
        counts[state] += 1
    observed = sum(counts.values())
    no_data = max(expected_samples - len(state_rows), 0)
    denom = counts["up"] + counts["down"] or 1  # D-45: availability excludes UNREACHABLE
    return {
        "up_pct": round(counts["up"] / denom * 100, 2),
        "down_pct": round(counts["down"] / denom * 100, 2),
        "unobserved_pct": round(counts["unreach"] / max(observed, 1) * 100, 2),
        "downtime_minutes": round(counts["downtime"] * scrape_interval_seconds / 60, 1),
        "no_data_pct": round(no_data / expected_samples * 100, 2) if expected_samples else 0.0,
    }
```
Parquet export for the same day, run against ClickHouse directly (no Python-side Parquet writer):
```sql
-- Source: context7-verified pattern (clickhouse/clickhouse-docs,
-- knowledgebase/s3_export_data_year_month_folders.mdx — INSERT INTO FUNCTION s3(...))
INSERT INTO FUNCTION s3(
    'http://minio:9000/fleet-availability/availability_parquet/date=2026-09-27/day.parquet',
    'minioadmin', 'minioadmin', 'Parquet',
    'host String, folder String, up_pct Float64, down_pct Float64,
     unobserved_pct Float64, downtime_minutes Float64, schema_version UInt16'
)
SELECT host, folder, up_pct, down_pct, unobserved_pct, downtime_minutes, 1 AS schema_version
FROM daily_availability_tmp   -- populated by the poller's own INSERT before this statement
WHERE date = '2026-09-27';
```
The poller writes its computed Python dict rows into a small temp/staging table first (one more `_clickhouse_insert()` call, same choke-point function as Pattern 1), then runs this export statement — so the JSON and the Parquet are guaranteed to carry identical figures, satisfying D-57's "same figures" requirement by construction rather than by two independent code paths that could drift.

### Pattern 4: Never-overwrite object write via HEAD-before-PUT (unchanged from prior research)
**What:** Before writing `availability/YYYY/MM/YYYY-MM-DD.json`, `head_object` the key; only `put_object` if it 404s. Accept the narrow TOCTOU race as negligible (single writer, once-daily-per-day job).
**When to use:** D-52's "never overwrite" requirement, on a backend (MinIO) whose support for atomic `If-None-Match: *` conditional writes is version-dependent (see Pitfall 2). Apply this same check before the Parquet `INSERT INTO FUNCTION s3(...)` statement too (a cheap `s3.head_object` against the Parquet key before running the SQL) so D-57's "never-overwrite applies to both objects" is enforced identically for both formats.
**Example:** (unchanged from prior research — `boto3`, `endpoint_url` + path-style addressing, works unmodified against AWS S3 per D-41)
```python
import boto3
from botocore.config import Config
from botocore.exceptions import ClientError

s3 = boto3.client(
    "s3",
    endpoint_url=os.environ["S3_ENDPOINT"],
    aws_access_key_id=os.environ["S3_ACCESS_KEY"],
    aws_secret_access_key=os.environ["S3_SECRET_KEY"],
    config=Config(signature_version="s3v4", s3={"addressing_style": "path"}),
    region_name="us-east-1",
)

def write_if_absent(bucket: str, key: str, payload: bytes, content_type: str) -> bool:
    try:
        s3.head_object(Bucket=bucket, Key=key)
        return False  # already exists — never overwrite (D-52/D-57)
    except ClientError as exc:
        if exc.response["Error"]["Code"] != "404":
            raise
    s3.put_object(Bucket=bucket, Key=key, Body=payload, ContentType=content_type)
    return True
```

### Pattern 5: Allowlist-only read proxy to ClickHouse's HTTP interface
**What:** nginx forwards only GET requests, and only to a fixed backend path, so the query text itself is the only thing that varies — never the method, never an admin endpoint. Because ClickHouse's HTTP interface is a single endpoint (`/`, plus `/ping` and `/replicas_status` health checks — a much smaller surface than the superseded Thanos Query design had), the allowlist is simpler than the prior research's version, but the same "GET forces readonly" server-side guarantee (Pattern in Summary) is the real safety net, not the proxy alone.
**Example:**
```nginx
# Extends deploy/dashboard-nginx.conf's existing /checkmk-api/ same-origin pattern.
# ClickHouse's own dashboard_reader user (readonly=1 settings profile, SELECT-only
# grants) is embedded in the upstream URL here — the browser never sees credentials.
location /ch-api/ {
    limit_except GET { deny all; }
    # HTTP GET is server-enforced readonly by ClickHouse itself (verified via
    # context7 against ContextAccess.cpp) — this nginx layer is defense-in-depth,
    # not the sole guarantee.
    proxy_pass http://dashboard_reader:${CH_READER_PASSWORD}@clickhouse:8123/;
}

location /availability/ {
    limit_except GET { deny all; }
    proxy_pass http://minio:9000/fleet-availability/;
}
# No catch-all beyond these two locations: an unmatched path 404s by nginx's own
# default, not by an explicit deny rule.
```
nginx cannot itself interpolate an env var into `proxy_pass` at parse time the way compose does — the planner should resolve this via an `envsubst`-based entrypoint wrapper (a well-known nginx-image pattern) or bake the reader password into a mounted config generated at container build/start, consistent with how this project already keeps secrets out of tracked files (`deploy/.env` empty-default pattern). Flagged as a planning detail, not a blocker.

### Anti-Patterns to Avoid
- **Treating the ClickHouse writer user as also the browser-facing user:** the writer needs `INSERT`; the browser-facing path must use a separate `dashboard_reader` user with a `readonly=1` profile and `GRANT SELECT` only (D-54/D-56) — never share credentials across the write and read paths, even though both currently reuse the same MinIO root creds for the *S3 disk*, which is a different, already-accepted risk (D-56).
- **Publishing rollups from in-memory poller counters:** D-51 explicitly rejects this — a poller restart mid-day must not lose or corrupt that day's figures; always recompute from ClickHouse's durable state tables.
- **Making the Parquet export a second independent computation:** write the day's computed rows into ClickHouse once, then export via SQL — never recompute the Parquet figures from a second Python pass, which could silently drift from the JSON (D-57's "same figures" requirement).
- **Treating MinIO's `If-None-Match: *` support as guaranteed:** unchanged from the prior research — HEAD-before-PUT is the portable primary mechanism (see Pitfall 2).
- **Relying on container `TZ=Asia/Singapore` for day-boundary math:** compute boundaries explicitly with `zoneinfo.ZoneInfo("Asia/Singapore")` in Python (for the day-window bounds passed into the SQL `WHERE` clause) so the logic is correct regardless of container OS timezone configuration and is unit-testable without a live container. ClickHouse's own `toDate(ts, 'Asia/Singapore')` can independently double-check the boundary server-side, but the poller's Python boundary is the source of truth for what window it asks for.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Long-term downsampled TSDB storage | A custom rollup-and-delete cron job, or a separate compactor process | ClickHouse's own `TTL … GROUP BY … SET` + `TTL … TO VOLUME` clauses on the table | This is exactly the engine-native feature D-40 was chosen for; a hand-rolled job would duplicate logic ClickHouse already runs as part of its background merges |
| S3 conditional/atomic writes across MinIO + AWS | A custom distributed lock or ETag-diffing scheme | HEAD-before-PUT (accept the narrow single-writer race) | D-52's actual risk (a concurrent second writer) doesn't exist — the midnight job is a singleton per poller process |
| Prometheus/Nagios-format `perf_data` parsing | (n/a — already built in Phase 12) | `parse_perf_data()`, unchanged | Not new to this phase; the write path just feeds its output into `_clickhouse_insert()` instead of (in addition to) MQTT |
| Parquet file writing | A poller-side `pyarrow` writer | ClickHouse's `INSERT INTO FUNCTION s3(..., 'Parquet')` | ClickHouse already holds the row data in memory from the SQL query that produced it; exporting from there avoids a second data path and a new Python dependency |
| Grafana dashboard/datasource setup via clicking in the UI | Manual UI configuration, undocumented and lost on redeploy | File-based provisioning (`datasources/*.yaml`, `dashboards/*.yaml` + JSON) [VERIFIED via context7, grafana.com/docs/grafana/latest/administration/provisioning/] | D-55 requires this to survive a redeploy the same way the rest of this stack is config-as-code |

**Key insight:** ClickHouse's single-container, TTL-native design means this phase's "don't hand-roll" list is shorter than the superseded Prometheus + Thanos version — there is no separate compactor/store-gateway/querier whose correctness needs protecting from a custom reimplementation, because those roles don't exist as separate processes here.

## Common Pitfalls

### Pitfall 1: `minio/minio` was fully removed from Docker Hub on 2026-09-11 — not merely frozen
**What goes wrong:** `deploy/compose.yaml`'s existing `minio` service (`image: minio/minio:latest`) will fail with an image-pull error (`404`/`repository does not exist`) on any fresh clone, CI run, or `podman compose pull`/`up` from a host that hasn't already cached the image locally. This phase makes MinIO's availability *more* load-bearing than before (ClickHouse's S3 disk now depends on it too, in addition to the existing `worker` use and the rollup writer), so a broken MinIO pull now blocks more of the stack than it did before this phase.
**Why it happens:** D-41 already flagged "MinIO stopped publishing free community images/binaries in late 2025" as a frozen-tag risk. This research escalates that: per live WebSearch (2026-09-28), MinIO's Community Edition went source-only in October 2025, and on **2026-09-11** Docker Hub actually deleted `minio/minio` and `minio/mc` outright — this already happened, it is not a future risk. [MEDIUM confidence — WebSearch, cross-referenced across multiple independent GitHub issue reports (`milvus-io/milvus#53430`, `lobehub/lobehub#9845`, `zilliztech/woodpecker#376`) all dated within days of each other, consistent with a real, dated platform-level removal rather than a single unreliable source]
**How to avoid:** Repoint the `minio` service's `image:` to a pinned tag on `quay.io/minio/minio` (the last confirmed community push there was `RELEASE.2025-09-07T16-13-09Z`, per WebSearch — verify the exact current tag at plan/execute time, since quay.io's own availability for this repo is itself described as a "stopgap" by multiple sources, not a permanent fix) rather than leaving `minio/minio:latest`, which will 404 on pull. This is adjacent to, but not strictly inside, the phase's own HIST-0x requirements — flag it to the operator as a required companion fix (likely its own small `compose.yaml` edit + a documentation note) rather than silently working around it inside a ClickHouse-specific task, since it affects the *existing* `minio` service used by `worker` today, independent of anything this phase adds.
**Warning signs:** `podman compose pull` or `podman compose up minio` failing with a pull/manifest error on a machine that has never pulled `minio/minio` before; this will NOT reproduce on the current deployment host if its local image cache already has `minio/minio:latest` pulled from before the removal date.

### Pitfall 2: MinIO's `If-None-Match: *` conditional-write support is version-dependent
**What goes wrong:** Code that relies on `PutObject` with `If-None-Match: *` returning `412 Precondition Failed` to enforce "never overwrite" may instead get a `200` (silent overwrite) on an older or differently-configured MinIO build.
**Why it happens:** AWS S3 added the wildcard `If-None-Match: *` conditional-write semantic in 2024; MinIO's support for the specific wildcard form has lagged and evolved across releases, and (per Pitfall 1) MinIO's community edition is now frozen at whatever its last published state was — no future patch will change this. [LOW confidence — WebSearch only, sources disagree by MinIO version; not verified against this project's pinned MinIO build]
**How to avoid:** Use HEAD-before-PUT as the primary mechanism (works identically on every S3-compatible backend, no conditional-header support required) — unchanged recommendation from the prior research pass.
**Warning signs:** A rollup day silently gets overwritten after a backfill re-run — write a regression test that calls `write_if_absent` twice (for both the JSON and, separately, verify the Parquet export path also checks first) and asserts the second call returns `False` and the object bytes are unchanged.

### Pitfall 3: `python:3.12-slim` has no IANA timezone database
**What goes wrong:** `zoneinfo.ZoneInfo("Asia/Singapore")` raises `ZoneInfoNotFoundError` at runtime — the midnight job silently can't compute day boundaries.
**Why it happens:** Debian slim images intentionally omit `/usr/share/zoneinfo`; `zoneinfo` falls back to the PyPI `tzdata` package only if it's installed. [VERIFIED via WebSearch, cross-referenced against `docs.python.org/3/library/zoneinfo.html`'s documented fallback behavior] — unchanged from the prior research pass.
**How to avoid:** Add `tzdata` to the poller's `pip install` list in `deploy/compose.yaml` (already verified clean by slopcheck).
**Warning signs:** Works fine in local dev (host OS usually has tzdata), fails only inside the container.

### Pitfall 4: `TTL … GROUP BY` requires its columns to be a prefix of the table's key
**What goes wrong:** A `TTL <expr> GROUP BY <cols> SET ...` clause fails to create (or silently never fires) if `<cols>` isn't a left-prefix of the table's `PRIMARY KEY`/`ORDER BY`.
**Why it happens:** This is a documented, hard requirement of the feature [VERIFIED via context7, `clickhouse/clickhouse-docs`, docs/guides/developer/ttl.md: "The `GROUP BY` columns in the `TTL` clause must be a prefix of the `PRIMARY KEY`"], not a soft recommendation.
**How to avoid:** Design the `ORDER BY`/`PRIMARY KEY` for the metrics/state tables around the columns the downsampling rollup needs to group by (`metric, host, service, toStartOfFiveMinutes(ts)` in Pattern 2's example) *before* deciding what queries need to filter on — this is a schema-first decision, and changing it later requires a table rebuild (`CREATE ... AS ... ORDER BY ...` + re-insert), not an in-place `ALTER`.
**Warning signs:** `CREATE TABLE` succeeds but the TTL rule never visibly reduces row count / never appears in `system.parts`' `TTL_INFO` after the interval has clearly elapsed — verify with a short-interval test TTL (e.g. `INTERVAL 1 MINUTE`) against a scratch table during planning, mirroring this project's existing "verify against a live column probe" convention (`--check-columns`).

### Pitfall 5: Unbounded label/column cardinality from a careless metric write
**What goes wrong:** If the `metrics` table's key columns ever include a high-cardinality value (a raw timestamp component beyond the intended grain, a per-request ID, `plugin_output` text) instead of the intended `host`+`service`+`metric` triple, ClickHouse's `system.parts` count and merge/TTL-rollup runtime blow up disproportionately to the fleet's actual size.
**Why it happens:** D-42 says "every parsed perf_data metric from every service" — at ~50 hosts × ~20 services × a handful of perf_data keys each, cardinality is in the low thousands, which is fine, but a careless implementation (e.g. keying by `plugin_output` text) would not be. Unchanged risk shape from the prior research pass, now expressed as ClickHouse `LowCardinality(String)` column design instead of Prometheus label cardinality.
**How to avoid:** Key only by `host`, `service` (description), and `metric` (perf_data key name) as `LowCardinality(String)` columns — never a free-text or high-cardinality field. Validate this at code-review time against the CONTEXT specifics ("Scale is small (~50 hosts, 15s poll)").
**Warning signs:** `system.parts` row/part count growing unboundedly instead of plateauing after the fleet's services stabilize; ClickHouse's merge scheduler falling behind (visible in `system.merges`).

### Pitfall 6: Running the rollup job only at midnight misses restarts and outages
**What goes wrong:** If the poller container was down at local midnight, that day's rollup (JSON and Parquet) is simply never written, silently leaving a permanent gap.
**Why it happens:** D-52 explicitly anticipates this ("on startup and at each midnight... auto-backfill... never overwrite") — this is why the requirement exists, not a hypothetical edge case. Unchanged from the prior research pass.
**How to avoid:** Implement the backfill scan as the same code path run at both startup and midnight: list which of the last ~30 days have no rollup object yet (one `head_object`/`list_objects_v2` call per bucket prefix, both JSON and Parquet), compute and write each missing pair.
**Warning signs:** A gap in the availability history around any period the poller container was observed to be restarting.

### ClickHouse HTTP interface — reading a query result as JSON (poller/rollup job)
```python
# Source: context7-verified against clickhouse/clickhouse-docs
# (docs/integrations/interfaces/http.md GET / query pattern)
def _clickhouse_query(base_url: str, sql: str, timeout: float) -> list[dict]:
    url = f"{base_url}/?query={urllib.parse.quote(sql)}&default_format=JSONEachRow"
    try:
        with urllib.request.urlopen(url, timeout=timeout) as response:
            body = response.read().decode()
    except (urllib.error.HTTPError, urllib.error.URLError, OSError, TimeoutError) as exc:
        raise ClickHouseError(f"ClickHouse query failed: {exc}") from exc
    return [json.loads(line) for line in body.splitlines() if line]
```

## Open Questions

1. **Exact ClickHouse port exposure and whether it needs a compose-level published port**
   - What we know: ClickHouse's HTTP interface (8123) only needs to be reachable from the poller, the rollup job, Grafana, and the dashboard nginx container — all already on `cmk_net`. No LAN publish is needed, matching the container-boundary constraint (consistent with how `checkmk`'s REST port 5000 is handled today: internal-only, not published to the host).
   - What's unclear: whether the planner wants ClickHouse's native TCP port (9000) exposed at all, or only HTTP (8123) — the poller/rollup job/nginx examples above use HTTP exclusively, so 9000 may not need to be opened even internally.
   - Recommendation: HTTP-only (8123) internal to `cmk_net`, no host publish; record the final port table in the phase's PLAN.md, avoiding the existing used-port list (8080/8000/6556/1883/9000/9001/9002/8090 — note ClickHouse's *default* native port 9000 would collide with MinIO's already-published host port 9000, another reason to stay HTTP-only or remap).

2. **Whether `TTL … GROUP BY … SET` or a materialized view is the better downsampling mechanism for this phase's three series tables**
   - What we know: D-40 names both as valid ClickHouse mechanisms; `TTL GROUP BY` requires the grouping columns to be a `PRIMARY KEY` prefix (Pitfall 4) but needs no second table.
   - What's unclear: at ~50 hosts' actual data volume (CONTEXT's own "a few GB over three years" estimate), either approach is well within ClickHouse's comfort zone — this is a design-taste choice, not a correctness-driven one.
   - Recommendation: use `TTL GROUP BY … SET` (Pattern 2) as the default for the planner, since it avoids a second table per series and matches D-40's own framing ("materialized views are the alternative", implying GROUP BY TTL is the primary path); flag as reversible if the plan-checker or a later phase finds it too rigid for query-time flexibility.

3. **How the nginx `proxy_pass` interpolates the ClickHouse reader password without landing it in a tracked file**
   - What we know: this project's established pattern is `deploy/.env` (gitignored) + compose `${VAR:-}` interpolation for secrets, but nginx config files don't get compose-style env interpolation natively.
   - What's unclear: whether the planner should use an `envsubst`-based nginx entrypoint wrapper (common, well-documented pattern for the official nginx image) or bake the credential into a mounted, gitignored `deploy/dashboard-nginx-secrets.conf` generated by a startup script.
   - Recommendation: `envsubst` wrapper is the more standard, less bespoke choice — flagged as a planning decision, not a blocker.

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Browser reaches a ClickHouse endpoint that bypasses the read-only user's grants | Elevation of Privilege | Server-side `readonly=1` settings profile on `dashboard_reader` (cannot be overridden by a client-supplied `SETTINGS readonly=0` — ClickHouse's access-control check happens after settings merge, per the `ContextAccess.cpp` logic verified via context7) plus nginx's GET-only method restriction — two independent layers |
| Browser or a compromised dashboard asset writes to the rollup bucket via the read-only proxy | Tampering | `limit_except GET { deny all; }` on every proxied location; no PUT/DELETE method ever reaches MinIO or ClickHouse through nginx |
| A malformed or oversized `perf_data` value creates a high-cardinality metric key, causing resource exhaustion in ClickHouse's part/merge scheduler | Denial of Service | Key only by `host`/`service`/`metric` as `LowCardinality(String)` (Pitfall 5); never key by a raw value or free-text field |
| Grafana anonymous access accidentally left enabled by a future config change | Information Disclosure | Explicit `GF_AUTH_ANONYMOUS_ENABLED=false` in compose (belt-and-braces even though it's Grafana's own default), verified by the HIST-10 smoke test |
| `minio/minio:latest` silently failing to pull on a redeploy, leaving the whole history stack (ClickHouse's S3 disk, rollup writes) without its S3 backend | Denial of Service (operational) | Pin `minio` to a specific `quay.io/minio/minio` tag (Pitfall 1) rather than a Docker-Hub-only rolling tag |
