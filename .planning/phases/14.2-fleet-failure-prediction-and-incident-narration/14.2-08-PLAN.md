  <behavior>
    Tiers and ids:
    - tier_from_criticality: critical->immediate, high->urgent, medium->standard, low->standard, None->standard (D-08)
    - tier_from_days: 2.9->immediate, 3.0->urgent, 20.0->urgent, 20.1->standard, 90.0->standard, 90.1->None (D-09)
    - need_id is deterministic, matches ^[fts]-[0-9a-f]{12}$, differs per source, and stays topic-safe for service "Filesystem /var" (D-14)
    Trend (D-07 source 2, D-09, D-10, D-16):
    - trending fit, days_to_crit 10, metric in trend_need_metrics -> urgent need, source "trend", narration non-empty
    - trending fit, metric not in trend_need_metrics (e.g. CPU util) -> None (D-16)
    - status stable or no_clear_trend -> None
    - days_to_crit 1, confidence low, metric in wear_metrics -> tier urgent (capped); same with confidence medium -> immediate
    - days_to_crit None (no crit level) -> None
    Sustained (D-07 source 3):
    - 20 of 24 hourly values >= crit -> immediate need, source "sustained", sustained_fraction 0.83, window_hours 24
    - 10 of 24 >= crit with latest < crit -> None; a single spike -> None
    - metric in trend_need_metrics and latest >= crit -> immediate need even if fraction is low ("a disk already critical")
    - crit None, or crit < warn (lower-is-worse) -> None
    Failure (D-07 source 1, D-08, D-27):
    - status host_state_raw "DOWN", host not covered -> failure need, service "", tier from topology criticality
    - same host listed in an open incident's root/confirmed_down/not_observable -> no need (D-27)
    - services row state "CRIT" with description "Systemd Service nginx", "Service Spooler" or "TCP Port 443" -> failure need for that service; "Systemd Service Summary" and other services (e.g. "CPU load") -> none
    - topology node service_criticality {"Systemd Service nginx": "critical"} with host criticality low -> that service need is immediate
    - the two service regexes equal the poller's `_CHOSEN_SERVICE_RE` and `_TCP_PORT_SERVICE_RE` patterns (test loads scripts/mqtt_poller.py via importlib and compares `.pattern`)
    NeedTracker:
    - a new candidate is published with since = now; on later cycles since is preserved
    - a need absent for 1 cycle is still published; absent for resolve_after_clean_cycles (2) consecutive cycles -> tombstoned id returned once; a recurrence afterwards gets a fresh since and triage None (D-23 "recurrence starts untriaged")
    - computed tier worsening applies immediately; improving applies only after it has held for resolve_after_clean_cycles cycles
    - one candidate per (host, service, metric): if trend and sustained both fire, only the sustained one is published and the trend id is tombstoned (no double listing)
    - restore() seeds state from retained payloads (since and triage kept)
    Triage carry-over (D-22, D-23):
    - prev triage downgrade set at computed tier urgent; new computed tier urgent -> triage kept, effective tier = triage tier
    - new computed tier immediate (worse than urgent) -> triage dropped, effective tier = computed, returns audit dict {action: "auto_reset", tier_before, tier_after, computed_tier}
    - cancel triage is kept while the need stays open and the need is still published (dashboard hides it)
