### Locked Decisions

#### History inputs and container responsibilities
- **D-01:** Add a ClickHouse filesystem read cache on the `s3` disk (config only, in
  `deploy/clickhouse-config/config.d/`). Forecasts read more than 31 days of history, so
  without it they would hit cold MinIO parts on every query. (Resolves roadmap open decision A.)
- **D-02:** The analytics container is the durable recorder of event and incident history. It
  subscribes to MQTT and writes `history.events` and `history.incidents`. The poller is not
  changed (D-44 posture kept: push-only, no on-disk state). This is a requirement because the
  broker, S3, ClickHouse and dashboard will move to the cloud. (Resolves roadmap open decision B.)
- **D-03:** Interim ingestion until the separate transport phase:
  - The container reads today's `sites/<site_id>/lan/events/recent` (bounded, at most 1000
    entries) and `sites/<site_id>/lan/incidents/+/status`.
  - It deduplicates events against what it has already written.
  - An incident tombstone means close: the container writes the close row with duration.
- **D-04:** The daily availability rollup (14.1, JSON + Parquet to MinIO) moves from the poller
  to the analytics container in this phase.
- **D-05:** D-30 restated: the operator's own cloud tenancy counts as inside the network.
  Nothing goes to third-party model providers or SaaS the operator does not control.
- **D-06:** All endpoints (broker, ClickHouse, MinIO) are env-configured and location-agnostic.
  The target split is Checkmk, poller and worker on-prem, with broker, S3, ClickHouse,
  dashboard, Grafana and analytics in the cloud, over metered 4G links with many sites.

#### Need sources and tiers
- **D-07:** There are three need sources:
  1. **Failure:** a ping host is DOWN, a TCP port or a monitored systemd/Windows service fails.
     Derived from the live `status`, `services` and `topology` topics.
  2. **Trend to threshold:** disk fill, SSD/NVMe wear, reallocated sectors, memory creep.
     Simple linear regression (D-31, no ML), fitted from ClickHouse.
  3. **Sustained or already-breached:** for example a disk already critical, or CPU near 100%
     most of the time. This is a new rule type over a time window, not a regression.
- **D-08:** The tier derives from the existing criticality by a fixed mapping:
  - critical → immediate
  - high → urgent
  - medium/low → standard

  This applies to failure needs. There is no new setting; the existing `CriticalityEditor`
  stays the editor. It is cheap and reversible. The parked todo on the criticality model stays
  open.
- **D-09:** Trend tiers are banded by **days until the critical level**:
  - immediate: already critical or under 3 days
  - urgent: 3 to 20 days
  - standard: over 20 days
  - nothing shown as a need beyond 90 days

  All bands are configurable. This updates the D-34 defaults (3/15). The warning-crossing date
  is shown but does not set the tier. A sustained breach is immediate.
- **D-10:** The confidence tag depends on history length and fit quality:
  - low: under 14 days of history
  - medium: 14 to 60 days
  - high: over 60 days with a good straight-line fit

  A noisy, flat or receding series gets no date and is labelled "stable" or "no clear trend".
  A low-confidence SMART/wear date is never immediate on its own (D-31 dispatch risk).
- **D-11:** A trend fit starts after the last sharp drop in the series, such as a disk cleanup,
  so one cleanup does not bend the trend.
- **D-12:** Warn and crit levels come from the latest sample's `warn`/`crit` columns in
  `history.metrics`, which are Checkmk's own levels. Analytics config supplies fallback levels
  for metrics that Checkmk gives no levels for (for example reallocated sectors).

#### Publication contract
- **D-13:** The analytics container evaluates every 15 minutes.
- **D-14:** It publishes one retained QoS 1 topic per active need,
  `sites/<site_id>/lan/needs/{need_id}/status`, built with the same `site_topic()` convention.
  The dashboard sees the topic as `lan/needs/...` after `mqttClient.ts` strips the prefix.
  - The topic is tombstoned (empty retained payload) when the need resolves.
  - Payload: source, host, service/metric, tier, computed tier, days to warn and days to crit,
    warn and crit dates, confidence, history_days, narration text, and the triage fields from
    D-22.
  - `need_id` is stable per (source, host, service, metric), so the same problem keeps the same
    id while it is open.
- **D-15:** It publishes a retained forecast fit for **every chartable trend metric**, not only
  for metrics with an active need, so the chart can be opened at any time (D-18). Suggested
  topic: `sites/<site_id>/lan/forecasts/{host}`, one message per host carrying all of that
  host's metric fits. The researcher or planner may choose a per-metric topic instead.
  - Each fit carries: service, metric, unit, slope, intercept, fit window start and end, warn
    and crit levels, warn and crit crossing dates (or null), confidence, history_days, and a
    status of trending, stable or no clear trend.
  - The dashboard draws from these numbers and **never refits**, so the chart and the need
    cannot disagree.
- **D-16:** Trend **needs** are raised only for the D-31 monotonic set: filesystem used %,
  SSD/NVMe wear, reallocated sectors and memory creep. The set is a configurable list.
  - Other chartable metrics, such as CPU, get a fit and a chart, but they do not raise a trend
    need.
  - A sustained breach on any metric still raises an immediate need (D-07 source 3).
  - For noisy metrics like CPU, the D-10 gate will usually return "no clear trend", so the chart
    shows no forecast date.
- **D-17:** The broker ACL (`deploy/mosquitto.acl.template`) gets an analytics login with these
  rights:
  - read: the site's `lan/#` and `needs/triage/cmd`
  - write: `lan/needs/#`, `lan/forecasts/#` and `lan/incidents/+/narration`

  It also gets a triage login with write access to `needs/triage/cmd` only (D-21).

#### Forecast chart (added by the user in this discussion)
- **D-18:** A line chart is available **at any time for every trend metric** of a host: disk
  (each filesystem), CPU, RAM, and other gauges that benefit from a line chart. It is not limited
  to active needs.
  - It opens from host details, where the host's chartable metrics are listed.
  - It also opens from a trend-need row in the Needs pane and from the Needs section in host
    details.
- **D-19:** The chart draws:
  - measured history as a solid line
  - horizontal warn and crit level lines
  - a vertical "today" line
  - a dashed trend line extended forward from the fit window
  - a marker and date label where the trend crosses warning and where it crosses critical
  - the confidence badge and history span in the chart header

  A low-confidence trend is drawn fainter with a caption (for example "9 days of history, low
  confidence").
- **D-19a (user, 2026-10-04):** The trend line is drawn **only when the regression shows a clear
  trend**: a meaningful slope with a good straight-line fit, using the same fit-quality gate as
  D-10.
  - When values are random or noisy with no clear trend, or flat, **no trend line is drawn at
    all**, not even a faint one. The chart shows history, the levels and the today line, with a
    "no clear trend" or "stable" label.
  - Confidence (low/medium/high) only changes how a *clear* trend is drawn. It never makes a
    line appear for noise.
  - A clear trend that moves away from the levels is drawn without crossing markers.
- **D-20:** History for the chart is read by the dashboard from ClickHouse through the existing
  same-origin, GET-only `/ch-api/` path as `dashboard_reader` (14.1 D-24). It uses hourly
  averages; the range covers the fit window and recent history.
  - This is the first dashboard feature that uses `/ch-api/`. It is limited to this chart, so
    D-50's "no history views" holds otherwise.
  - The forecast part comes from the D-15 topic.

#### Triage (D-35)
- **D-21:** Write path (same pattern as Phase 16 admin mode):
  - The dashboard publishes a triage command on `sites/<site_id>/needs/triage/cmd` using a
    separate broker login that can only write to that topic.
  - The analytics container consumes it and records an audit row per action in a ClickHouse
    `history.need_triage` table.
  - It then republishes the need with the triage applied.

  Checkmk host labels are not used. No custom backend is added.
- **D-22:** Triage actions are downgrade, upgrade to immediate, and cancel. The need payload
  carries the original computed tier, the override, when it was set, and an optional note or
  name.
- **D-23:** An override lasts until the need resolves (is tombstoned). A recurrence starts
  untriaged. If the computed tier becomes **worse** than it was at triage time, the override is
  dropped and the need reappears. A cancelled need is hidden from the pane but kept in the
  table.
- **D-24:** Triage controls appear only in the dashboard's edit mode, the existing gate on this
  closed network. Real per-user identity is out of scope.

#### Dashboard placement of needs
- **D-25:** A new **Needs pane** sits beside the incident pane. Each row shows:
  - tier badge, host, what (metric or service) and date
  - a prominent confidence badge with the history span

  Clicking a row selects the host. Triage controls appear in edit mode.
- **D-26:** A small tier marker on tree rows and map nodes, separate from the state colour.
  Host details gets a Needs section.
- **D-27:** No double counting: a failure need for a host already covered by an open incident is
  not listed separately. The incident card shows the derived tier instead.

#### Narration
- **D-28:** Narration is template-based only in 14.2; a local model stays deferred (D-30).
  - Every sentence is filled from incident or event fields.
  - Tests assert that no sentence appears when its field is absent, so narration never states
    a fact absent from the data.
  - English only.
- **D-29:** Open incidents: the analytics container publishes a retained
  `sites/<site_id>/lan/incidents/{incident_id}/narration` with a headline plus 2 to 4 sentences.
  The poller's `.../status` topic stays the poller's. The narration topic is tombstoned when the
  incident closes. Example:
  - "sw1 (low criticality) has been DOWN since 12:05 (3 min)."
  - "2 devices behind it cannot be observed: cam1, linux1."
  - "No dependent devices are affected."
- **D-30 (phase-local):** Closed incidents get a final summary (adds duration and recovery
  time), stored in `history.incidents`, so "what happened last Tuesday" can be answered in
  Grafana. There is no dashboard history view for it.
- **D-31 (phase-local):** The incident card shows the narration and falls back to today's card
  when the narration is missing. Needs carry their own one-line narration text.

## Summary

The phase is mostly a new Python service plus dashboard slices, built on rails that already exist. The poller already publishes everything the failure and narration paths need (`lan/devices/{id}/status`, `.../services`, `lan/devices/topology`, `lan/events/recent`, `lan/incidents/{id}/status`), and `history.metrics` already carries per-sample `value`, `warn`, `crit` plus rollup-safe `value_sum`/`value_count`. The regression itself is small: Python's stdlib `statistics.linear_regression` and `statistics.correlation` (verified locally, 3.11) are enough, so no numpy or ML dependency is needed. The deliberately hard parts are the decisions around it: a fit-quality gate that makes noise return "no clear trend" (D-19a), a sharp-drop rule (D-11), need identity/hysteresis so needs do not flap, and keeping the chart and the need numerically identical by publishing the fit parameters and never refitting in the browser.

Four findings change the plan versus the CONTEXT's assumptions. (1) The dashboard has **no chart library** and the design system has none; the lean choice is a hand-written SVG component with `d3-scale` for time/linear scales and nice ticks, styled with the existing Tailwind token classes so light/dark work for free. (2) `history.metrics` has **no unit column** (the poller strips the UOM when parsing perf data), so the D-15 `unit` field must come from a static metric-to-unit map in analytics config. (3) The **SMART/wear metric names are not verified**: Checkmk's own docs for `smart_ata_stats`/`smart_nvme_stats` list no metric names, and the SMART checks are counter-increase checks, so the trend metric list must be seeded from a live metric catalog query on dmc-server before the allow-list is finalized (handed to the user as a live step). (4) **Topology edit mode hides the incident pane and host details** (`IndexRoute.tsx` passes `undefined` for both), so the D-24 rule "triage only in edit mode" needs the Needs pane to stay visible in edit mode; this is a layout decision the planner must make explicitly.

The deployment cut-over is the main operational risk: new ClickHouse user/tables, new broker logins, new compose service, a ClickHouse cache config, and the rollup moving out of the poller. 14.1's own precedent applies (initdb scripts only run on an empty volume, so existing hosts need a one-off migration run through `podman exec clickhouse clickhouse-client`, which is not a container restart). The ClickHouse config change and the new broker passwords need a full `podman compose down && up -d`, which is the safe path anyway.

**Primary recommendation:** Build a small `analytics/` Python package (pure modules for fit, rules, narration; thin I/O modules for MQTT, ClickHouse HTTP, S3) mounted into a `python:3.12-slim` compose service; publish per-host `lan/forecasts/{host}`, per-need `lan/needs/{need_id}/status` and per-incident `.../narration` as retained QoS 1 with tombstones; write the forecast chart as an SVG component fed by those payloads plus one parameterised `/ch-api/` query.

## Architecture Patterns

### System Architecture Diagram

```
                       on-prem (today: same compose)
 Checkmk --Livestatus--> poller --MQTT retained--> broker (mosquitto)
                           |                          |  ^
                           | HTTP INSERT (unchanged)  |  | write lan/needs, lan/forecasts,
                           v                          |  | lan/incidents/+/narration
                      ClickHouse (history.*) <--------+--+---- analytics container
                       |   ^   tiered -> MinIO (s3)   |  |          |  ^  |
                       |   |   + NEW fs read cache    |  |          |  |  | S3 (rollup JSON+Parquet)
   GET /ch-api/ (RO)   |   +--- SELECT hourly/6h buckets ----------+  |  v
   dashboard_reader    |        INSERT events/incidents/need_triage    MinIO fleet-availability
                       |
                       v                         read lan/devices/+/status|services|topology,
                dashboard (nginx, static SPA) <--------- lan/events/recent, lan/incidents/+/status,
                  |   ^ subscribe lan/needs/+/status, lan/forecasts/+,    lan/needs/+/status (restore)
                  |   |   lan/incidents/+/narration (wsreader)
                  |   +--- chart history: GET /ch-api/?query=...&param_*
                  |
                  +-- edit mode: PUBLISH sites/<id>/needs/triage/cmd (wstriage, write-only)
                                   |
                                   v
                       analytics consumes -> audit row (history.need_triage)
                                          -> republish need with triage applied

Analytics loop:
  on message: update in-memory device/services/topology/incident state; diff events -> INSERT;
              incident open/update/close -> narration topic + history.incidents row
  every 15 min (D-13): query ClickHouse buckets -> fit per series -> publish forecasts/{host}
              -> evaluate failure + trend + sustained rules -> publish/tombstone needs
  daily after local midnight: availability rollup (moved from poller)
```

### Pattern 1: Fit publishes parameters, never a series
**What:** Publish `fit_end_ts`, `value_at_end` and `slope_per_day` (not an epoch-scaled intercept). The browser evaluates `y(t) = value_at_end + slope_per_day * (t - fit_end_ts)/86400` and crossing date = `fit_end + (level - value_at_end)/slope_per_day` days. Same numbers feed the need, so chart and need agree.
**When to use:** every fit. **Why:** an intercept at the epoch loses float precision (about 1.7e9 seconds) and invites a refit in the browser.
```python
# Source: stdlib statistics (verified locally on 3.11); thresholds are assumed defaults, see Assumptions Log
from statistics import linear_regression, correlation

def fit_series(points: list[tuple[float, float]], cfg) -> Fit:
    # points: (t_days, value) hourly/6h averages AFTER the last sharp drop (D-11)
    xs = [p[0] for p in points]; ys = [p[1] for p in points]
    if len(points) < cfg.min_points or max(xs) - min(xs) < cfg.min_span_days:
        return Fit(status="no_clear_trend")               # too little data: no date, no line
    if max(ys) == min(ys):
        return Fit(status="stable")
    slope, intercept = linear_regression(xs, ys)
    r2 = correlation(xs, ys) ** 2
    if r2 < cfg.r2_min:
        return Fit(status="no_clear_trend")               # noisy/random: D-19a, no line at all
    if slope * 30 < cfg.min_change_per_30d:               # flat or receding
        return Fit(status="stable")
    ...                                                   # trending: compute crossings, confidence
```
`correlation` raises `StatisticsError` on a constant series; guard with the `max == min` check above (verified by behaviour of the stdlib function: constant input has zero variance).

### Pattern 2: One retained topic per need, tombstone on resolve, hysteresis before tombstone
Mirrors `publish_incident`/`publish_incident_tombstone` (`scripts/mqtt_poller.py:3713-3735`): `client.publish(topic, payload=None, retain=True, qos=1)` plus `wait_for_publish(timeout=5)` for tombstones. Add a `RESOLVE_AFTER_CLEAN_CYCLES` (default 2) so a value hovering on a threshold does not tombstone/re-publish every 15 minutes (Pitfall 3).

### Pattern 3: Command topic with dedup by id (admin-mode pattern)
Dashboard publishes QoS 1, not retained; analytics keeps a bounded seen-id set (poller uses `ADMIN_SEEN_IDS_MAX = 64`), validates `need_id` against its live need table, applies, writes the audit row, republishes the need. No ack topic: the visible effect is the republished need (see Open Question 4).

### Pattern 4: Subscribe to specific filters, not `lan/#`
The ACL grants `read lan/#` (D-17) but the service should subscribe to exactly the six input filters (+ `lan/needs/+/status` during restore only). Subscribing to `lan/#` would loop the analytics' own forecast/needs/narration writes back into its handler.

### Pattern 5: Restore state from retained topics, reconcile once on start
- Needs and their triage fields are restored by reading the retained `lan/needs/+/status` for a short settle window (default 5 s) after subscribe, then unsubscribing from that filter. The retained topic is the live state; `history.need_triage` is the audit.
- Open incidents: after the retained replay of `lan/incidents/+/status` settles, any `history.incidents` row (FINAL) with `status='open'` whose incident is not in the retained set is closed now (`close_source='reconcile'`). A broker never delivers tombstones on (re)connect, so this reconcile is the only way to catch a close missed while analytics was down. Use `clean_session=True` and one reconcile code path rather than persistent sessions (simpler, easier to troubleshoot).

### Anti-Patterns to Avoid
- **Refit in the browser:** violates D-15 and lets chart and need disagree.
- **Publishing a time series on MQTT:** the lean contract is fit parameters; history comes from `/ch-api/` (the recent quick task removed the history topics for the same reason).
- **Evaluating failure needs only from `lan/devices/{id}/status.state`:** that field collapses WARN/CRIT of any shown service into the host state; use the `services` topic rows for per-service failures.
- **Hardcoding SMART metric names:** unverified (see Pitfall 5); drive them from config seeded by a live catalog.
- **A flag file or local DB for analytics state:** no on-disk state, same posture as the poller (D-44). State = retained topics + ClickHouse.
- **Importing `scripts/mqtt_poller.py` from analytics:** it is a deliberately standalone script (D-01 in its header). Move the rollup code; copy the 15-line topic helpers.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Linear fit, correlation | Own least squares | `statistics.linear_regression`, `statistics.correlation` | Edge-case handling; stdlib |
| "Nice" axis ticks and time scales | Own tick algorithm | `d3-scale` `scaleTime`/`scaleLinear` `.ticks()` | The only genuinely fiddly part of the chart |
| Query parameter quoting for the chart | String-concatenated SQL | ClickHouse typed parameters `{h:String}` + `param_h=` in the URL | Injection-safe; documented HTTP feature [CITED: clickhouse-docs docs/integrations/interfaces/http.md via ctx7] |
| Hourly averages after TTL rollup | `avg(value)` | `sum(value_sum)/sum(value_count)` | After the 30-day rule `value` is a bucket mean and rows are mixed; `value_sum`/`value_count` stay correct at every resolution [VERIFIED: `01-schema.sql` comments] |
| Retained-state restore | A state file/DB | Read own retained topics at start | Already persisted by the broker (`persistence true`) |
| MQTT reconnect/backoff | Custom loop | paho `loop_start()` + `reconnect_delay_set` | Same as poller idioms |
| ClickHouse DDL idempotence | Ad hoc `if not exists` shell | `CREATE TABLE IF NOT EXISTS` migration file run through `clickhouse-client` | Matches 14.1 initdb style |
| Rollup logic | Rewrite | Move the existing, tested `compute_daily_availability`, `rollup_one_day`, `RollupScheduler` code verbatim with its tests | Never-overwrite semantics already proven live (D-44/D-52) |

**Key insight:** the novelty is in the rules and the contract, not in infrastructure. Every I/O shape (HTTP insert/query, retained publish/tombstone, command topic, Tailwind-token styling, zustand slice with reset-on-connect) already has a working example in this repo; reuse those and spend effort on tests of the pure modules.

## ClickHouse filesystem cache (D-01)

- **Cache location in the existing file.** `deploy/clickhouse-config/config.d/s3-storage.xml` is the only config file mounted (compose mounts that single file). Put the cache in the same file and no compose volume change is needed. Cache directory under `/var/lib/clickhouse/` is inside the already mounted `clickhouse_data` volume, so it survives a down/up.
- **Two documented shapes.**
  1. A `type=cache` wrapper disk: `<s3_cache><type>cache</type><disk>s3</disk><path>…</path><max_size>10Gi</max_size></s3_cache>`, "example of configuration for versions later or equal to 22.8" [CITED: clickhouse.com/docs/operations/storing-data, via WebFetch summary; same shape in ctx7 clickhouse-docs s3-minio guide]. **Risk for this repo:** the policy volume `s3` points at disk `s3`. To read through a wrapper disk the volume would have to list the wrapper disk instead, and parts already stored under disk `s3` are tied to the disk name; ClickHouse scans the disks in the storage policy, so renaming/replacing a volume disk can orphan existing parts. Do not do this on a volume that already has parts in S3 without a test.
  2. A named cache attached to the existing disk: top-level `<filesystem_caches><s3_cache><path>…</path><max_size>…</max_size></s3_cache></filesystem_caches>` and `<cache_name>s3_cache</cache_name>` inside the `s3` disk, with `enable_filesystem_cache` as the per-query switch (default true) [CITED: oneuptime.com/blog/post/2026-03-31-clickhouse-filesystem-cache, a secondary source; `system.filesystem_cache_settings` is documented at clickhouse.com/docs/reference/system-tables/filesystem_cache_settings]. This keeps the disk name `s3` and the policy untouched, which is why it is the recommendation. **Confidence MEDIUM:** the key spelling was confirmed from a blog, not from the official page, and was not run against 26.9.4.3.
- **Recommendation:** shape 2, `max_size` modest and configurable (for example `2Gi`), written in `s3-storage.xml`. Prove it live: after the full down/up, `SELECT cache_name, path, max_size, current_size FROM system.filesystem_cache_settings` must list the cache, and a first and second run of a >31-day query should show cache hits (`ProfileEvents['CachedReadBufferReadFromCacheHits']` in `system.query_log`). Fallback if the server rejects `cache_name`: shape 1 plus a one-off check that `system.parts` shows no parts on disk `s3` yet (the stack was first started 2026-09-30 and the 31-day move has barely begun) before changing the volume.
- **Config applies only after server start.** `config.d` changes need a ClickHouse restart; hand the user the full `podman compose down && up -d`, never a single `podman restart clickhouse`.
- **Data on S3 is small right now.** Parts older than 31 days are the ones that move to MinIO. The first forecast reads at 90-day depth will touch cold parts only once the stack is older than a month; the cache matters from then on. Build it now anyway (D-01).

## Fit algorithm (Claude's discretion; values are recommended defaults, all env-overridable, all [ASSUMED] and to be tuned on real data)

**Input query (one per evaluation, all chartable series):** 6-hour buckets over the last 90 days, restricted by host/service/metric allow-lists:
```sql
-- Source: schema from deploy/clickhouse-config/initdb/01-schema.sql; aggregation per its TTL comments
SELECT host, service, metric,
       toUnixTimestamp(toStartOfInterval(ts, INTERVAL 6 HOUR)) AS t,
       sum(value_sum) / sum(value_count) AS v
FROM history.metrics
WHERE ts >= now() - INTERVAL 90 DAY
  AND (metric IN ('fs_used_percent','util','mem_used_percent' /* + catalog */))
GROUP BY host, service, metric, t
ORDER BY host, service, metric, t
FORMAT JSONEachRow
```
and a second small query for current levels: `argMax(warn, ts)`, `argMax(crit, ts)` per series over the last 2 days (D-12). Note: ClickHouse renders `UInt64` as JSON strings; `toUnixTimestamp` returns `UInt32`, `Float64` stays numeric, but `count()` columns need `int()` (see poller's `_clickhouse_query` docstring).

Why 6 hours, not hourly, for fits: 100 hosts x ~6 chartable series x 90 days hourly is about 1.3 million rows per 15-minute evaluation; 6-hour buckets are 4x smaller and lose nothing a straight-line fit needs. Make it `FIT_BUCKET_HOURS` (default 6). The chart reads hourly for one series (about 2,000 rows), which is cheap. **Measure the row count at first live run** (Open Question 6).

**Steps per series:**
1. Drop leading data to the **last sharp drop** (D-11): a sharp drop is a bucket-to-bucket fall larger than `max(DROP_MIN_ABS, 0.25 * (series max - series min))` with `DROP_MIN_ABS` 5.0 for percent metrics (proposed: 1.0 for count metrics such as reallocated sectors). Fit starts at the bucket after the drop.
2. Minimum data: at least 8 buckets (2 days of 6 h) and at least 2 days of span, else status `no_clear_trend` with `history_days` still reported; a need needs more than "no data".
3. OLS on (days since fit start, value). Quality gate: `r2 >= 0.70` AND `slope * 30 >= MIN_RISE_30D` (default 1.0 unit; so about 1 percentage point per month). Receding (`slope <= 0`) or below the rise floor is `stable`; r2 below the floor is `no_clear_trend`.
4. Crossing days from the **last actual bucket value** (not the fitted value) to avoid a fit that lags today: `days_to_crit = max(0, (crit - last_value) / slope)` if `last_value < crit`, else 0 (already critical). Same for warn. Report `warn_date`/`crit_date` as ISO date strings or null. If a level is absent for the series, use the config fallback (D-12) or report null.
5. **Confidence (D-10):** `history_days` = span of available data for this series (not the fit window). low under 14, medium 14-60, high over 60 **and** `r2 >= R2_HIGH` (default 0.9); a trending fit with over 60 days and `0.7 <= r2 < 0.9` is medium.
6. **Tier by days to critical (D-09):** immediate if already critical or `days_to_crit < 3`; urgent `3 <= d <= 20`; standard `> 20`; no need if `days_to_crit > 90` (the horizon). Warning date never sets the tier. A trending metric already at or past warn but not crit still needs a date; it is a need as long as `days_to_crit <= 90`.
7. **Low-confidence cap (D-10):** for SMART/wear/reallocated metrics, if confidence is low, the computed tier is capped at `urgent` (never `immediate` on its own). Already-critical (latest value at or over crit, per Checkmk's own level) is not a prediction, so it stays immediate (it is a D-07 source 3 breach, not a forecast date); the planner should state this reading explicitly in the plan.

**Sustained / already-breached rule (D-07 source 3, new rule type):**
- Window `SUSTAINED_WINDOW_HOURS` (default 24); hourly or 1 h buckets from the same history source (a small second query for the last 24 hours at hourly resolution).
- Raise an immediate need if at least `SUSTAINED_FRACTION` (default 0.8) of the window's buckets are at or over `crit`, for any chartable metric. A single spike never qualifies.
- For the D-16 monotonic set, additionally raise immediate when the **latest** bucket is already at or over `crit` ("a disk already critical"), because that is not a fluctuation.
- Same `need_id` family but source `sustained`; if both the trend and the sustained rule fire for the same series, publish one need, source `sustained`, tier immediate (do not double list; the planner may make this explicit in the plan).

**Failure rule (D-07 source 1)** from in-memory MQTT state:
- Host DOWN (`host_state_raw == 'DOWN'`) and the host is not part of any open incident's `root`/`confirmed_down`/`not_observable` (D-27). In practice almost every DOWN host is in an incident; this rule only catches the leftover edge case that `compute_incidents` documents (a host that reaches no top root).
- Service failure: a row in `lan/devices/{id}/services` with `state == 'CRIT'` whose description matches the monitored-service patterns the poller already uses (`Systemd Service …`, `Service …`, `TCP Port N …`, excluding the `… Summary` rows) [VERIFIED: `_CHOSEN_SERVICE_RE`, `_TCP_PORT_SERVICE_RE`, `scripts/mqtt_poller.py:767-768`]. Skipped when the host is covered by an open incident (D-27).
- Tier (D-08): `criticality` from the topology node for the host; if the node's `service_criticality` map names this service, use that value instead (a per-service label already exists, `SERVICE_CRITICALITY_LABEL`, so honoring it is a natural reading of "existing criticality"; flag for confirmation, Open Question 8). critical -> immediate, high -> urgent, medium/low -> standard.

**Need identity:** `need_id = source[:1] + "-" + sha1(f"{source}|{host}|{service}|{metric}").hexdigest()[:12]`. Service names contain spaces and slashes ("Filesystem /var"), and MQTT topic levels must not contain `/`, `+`, `#`; a hash is always topic-safe and stable. Host/service/metric stay in the payload for display. Hosts whose id fails the poller's `is_publishable_device_id` rule are skipped for `lan/forecasts/{host}` (they never get a retained status topic anyway); the planner should copy that function into `analytics/topics.py` with a test.

**Triage state machine (D-21 to D-23):**
- `downgrade` = one step down (immediate -> urgent -> standard; standard stays); `upgrade` = to immediate; `cancel` = hidden.
- Payload fields: `computed_tier`, `tier` (effective), `triage: {action, set_at, computed_tier_at_set, note, by}` or `null`.
- Drop the override when `rank(computed_tier_now) > rank(computed_tier_at_set)` where immediate is worst; the need reappears untriaged and the drop is written to `history.need_triage` as an `auto_reset` row.
- Cancelled needs stay published (retained) with `triage.action == "cancel"` so a restart restores them; the dashboard filters them out. They are tombstoned only on resolution, like any need (D-23: "until the need resolves").
- Recurrence after resolve: a new tombstone then a new open = untriaged, naturally.

## Narration (D-28 to D-31)

Pure functions in `analytics/narrate.py` taking the incident dict (poller payload) and the device-name/criticality lookup. Rules:
- Each sentence is a template guarded by the presence of its field(s): headline always from `root`, `root_state`; criticality parenthetical only if `worst_criticality` present (the example "(low criticality)" uses the root's own tier from the payload's `worst_criticality`; confirm this reading, Open Question 8); "since HH:MM (N min)" only if `since` parses; `not_observable` sentence only if non-empty ("2 devices behind it cannot be observed: cam1, linux1."); `confirmed_down` sentence only if non-empty; "No dependent devices are affected." only when `dependents` is present and empty, otherwise a dependents sentence listing them.
- Keep D-04's wording discipline (`IncidentCard.tsx` header): never claim that an UNREACH/inferred device "is down"; use "cannot be observed". Test: for each field removed from a full incident, the corresponding phrase is absent (D-28), plus a snapshot of the example in D-29.
- Time: render local time with the site timezone (`ROLLUP_TZ` already `Asia/Singapore`), or UTC with a label; choose one and say so in the text. Duration in minutes, then hours/days.
- Closed incident summary (D-30): adds "Closed at HH:MM after N min" using the tombstone observation time (or `reconcile` flag) and recovery time. Stored in `history.incidents.summary`.
- Need one-liners (D-31) follow the same rule: fill only from payload fields, e.g. "linux1 /var is 82% used; at the current rate it reaches the critical level (90%) on 2026-11-20 (medium confidence, 31 days of history)." No date sentence when `crit_date` is null.
- The incident card falls back to today's card when no narration message exists (D-31); needs and incidents derive the tier shown on the card from the same Python mapping, published as `tier` in the narration payload, so the dashboard never re-implements D-08.

## Dashboard integration

**Store and subscriptions.** `RELATIVE_SUBSCRIBE_TOPICS` in `dashboard-react/src/lib/topics.ts` gains `lan/needs/+/status`, `lan/forecasts/+` and `lan/incidents/+/narration`. `useAppStore.handleMessage` routes them by segment position like incidents (`parts[1] === 'needs' && parts[3] === 'status'`, `parts[1] === 'forecasts'`, `parts[1] === 'incidents' && parts[3] === 'narration'`). ## Common Pitfalls

### Pitfall 1: A fit that always finds a trend
**What goes wrong:** OLS always returns a slope, so noisy CPU series get dates and a dashed line.
**Why:** no quality gate. **Avoid:** the r2 and rise-floor gate in "Fit algorithm"; D-19a requires no line at all for noise. **Warning signs:** CPU series with a date; a flat disk with a far-future date. **Tests:** random noise, flat, receding, step-after-cleanup, steady ramp, short history.

### Pitfall 2: A cleanup drop bends the trend (D-11) or is missed
**What goes wrong:** one disk cleanup makes the slope near zero or negative. **How to avoid:** cut the fit after the last sharp drop; a relative-plus-absolute threshold so a 2-point wobble on a 90% disk is not a "drop". **Edge:** a drop leaves very few points; then fall back to `no_clear_trend`, not a date from three buckets. A reboot also resets memory creep; same rule.

### Pitfall 3: Needs flap and tombstone-republish storms
**What goes wrong:** value hovers around a tier boundary or `crit_date` straddles 3/20/90 days, so the need's tier or existence changes every 15 minutes, spamming retained publishes and the audit table. **Avoid:** `RESOLVE_AFTER_CLEAN_CYCLES` (default 2) before tombstone; republish only when the payload minus `generated_at` changes (compare with a stable signature as `incident_signature` does); tier changes need a day-margin hysteresis (planner picks, e.g. 0.5 day). Because triage overrides depend on the computed tier, flapping tiers would also reset overrides (D-23).

### Pitfall 4: Tombstones missed while analytics is down
**What goes wrong:** an incident closes while the container is stopped; no tombstone is ever delivered on reconnect, so `history.incidents` keeps an open row forever and narration topics linger. **Avoid:** the one-time reconcile after the retained replay (Pattern 5): close any stored-open incident that is not retained anymore (`close_source='reconcile'`) and tombstone any retained narration whose incident is not open. Same for needs and forecasts for hosts that no longer exist.

### Pitfall 5: SMART/wear metric names are unverified
**What goes wrong:** the allow-list matches nothing, so SSD wear and reallocated-sector needs never appear and nobody notices. **Why:** Checkmk's docs for `smart_ata_stats` and `smart_nvme_stats` list monitored counters but no perf-data names (WebFetch of checkmk.com/integrations pages 2026-10-04); candidate names such as `harddrive_reallocated_sectors` and `nvme_percentage_used` came from a search summary only [ASSUMED]. The ATA check is also a counter-increase check against the discovery baseline, so "reallocated sectors" may not carry warn/crit levels at all (hence D-12's fallback levels). **Avoid:** config-driven matching seeded by a live catalog; log (INFO) at startup how many series each allow-list entry matched and warn on zero matches; an environment-variable override for the lists.

### Pitfall 6: Events deduplication and bounded feed
**What goes wrong:** `lan/events/recent` is a whole bounded array rewritten on every change; duplicates on every message, or a gap if more than 1000 events occur while analytics is offline. **Avoid:** in-memory seen-key set (`(timestamp, device_id, event, from, to)`) seeded from the last two days of `history.events` at start; `ReplacingMergeTree` as belt and braces; accept that a gap during a long outage is lost (documented; the transport phase fixes it). Many state changes share one timestamp (a cascade at 12:05:00), so do not use a timestamp-only watermark.

### Pitfall 7: Edit mode hides the Needs pane
See Dashboard integration: `IndexRoute.tsx` passes `incidents={editMode ? undefined : ...}`. If the Needs pane is added next to the incident pane without handling edit mode, triage controls (edit-mode only, D-24) are never visible.

### Pitfall 8: Existing volumes do not get the new schema, user or config
**What goes wrong:** the stack starts, analytics logs permission/missing-table errors, nothing is recorded. **Avoid:** the migration file, hand-run `clickhouse-client` step in the live checklist, and analytics that detects the missing table (HTTP error text "doesn't exist") and keeps retrying with a precise log line. This is the same trap as the 14.1 `max_execution_time` ALTER and `GRANT CREATE TEMPORARY TABLE` fixes recorded in `02-users.sh`.

### Pitfall 9: The poller keeps the rollup config and S3 pins
Removing the rollup from the poller leaves `AVAILABILITY_*`, `ROLLUP_*`, `S3_*` env lines, the `boto3` and `tzdata` pins and test fixtures behind unless explicitly removed. Do it in the same plan as the move, after analytics is live.

### Pitfall 10: Stale retained data looks fresh
Forecast and need topics are retained. If analytics is stopped, the dashboard keeps drawing the last forecast. Publish `generated_at`, render "as of", dim after two missed cycles.

### Pitfall 11: The Livestatus TLS trap does not apply, do not introduce it
The analytics container reads MQTT and ClickHouse only. If any design later wants Livestatus (it should not), remember a fresh 2.4 site has Livestatus TCP TLS on and a plain client gets connection reset (memory: livestatus-tcp-tls-breaks-poller).

### Pitfall 12: `from`/`to` columns and 64-bit JSON strings
`from`/`to` are SQL keywords: store as `from_state`/`to_state`. ClickHouse returns `UInt64`/`Int64` as JSON strings by default; `toUnixTimestamp()` is `UInt32` (number) but `count()` is not (`int()` at the call site, as the poller's `_clickhouse_query` docstring warns).

### Pitfall 13: `/ch-api/` path details
`location = /ch-api/` is an exact match, the bare `/ch-api` and any sub path return 404, `?user=`/`?password=` args are refused, and credentials are injected by nginx. A chart request that omits the trailing slash or uses a `user` parameter name fails with a confusing 404/403.

### Pitfall 14: Re-entrancy of the 15-minute loop
Evaluation can take seconds to tens of seconds on a large history; use a monotonic scheduler (`next_run = max(last_start + interval, now)`), skip rather than overlap, and keep paho's network loop on `loop_start()` so message handling is not blocked. Shared state between the paho thread and the loop needs a lock or a queue (the poller's admin worker already uses `queue`).

### Need identity and tier mapping
```python
import hashlib
_TIER_FROM_CRITICALITY = {"critical": "immediate", "high": "urgent", "medium": "standard", "low": "standard"}  # D-08

def need_id(source: str, host: str, service: str, metric: str) -> str:
    digest = hashlib.sha1(f"{source}|{host}|{service}|{metric}".encode()).hexdigest()[:12]
    return f"{source[0]}-{digest}"          # topic-safe, stable while the need is open (D-14)

def tier_from_days(days_to_crit: float, cfg) -> str | None:
    if days_to_crit < cfg.immediate_days:   # 3
        return "immediate"
    if days_to_crit <= cfg.urgent_days:     # 20
        return "urgent"
    if days_to_crit <= cfg.horizon_days:    # 90
        return "standard"
    return None                             # beyond horizon: not a need
```

### Known Threat Patterns

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Triage credential readable by any LAN user (open `/triage-config.json`) | Spoofing/Elevation | Accepted for the closed network (D-24); login can only write one topic; command effect bounded to a tier change with audit row; record in docs |
| Forged or replayed triage command | Tampering/Repudiation | Command id dedup, strict validation, audit table, no secrets in the payload |
| Oversized or malformed MQTT payloads into analytics | DoS/Tampering | Size caps and try/except around every `json.loads`; ignore unknown shapes (same posture as `parse_events_payload`) |
| Host or service name with `/`, `+`, `#` forming a topic | Tampering | Hash-based `need_id`; `is_publishable_device_id` for `forecasts/{host}` |
| SQL injection via host/service name | Tampering | Typed ClickHouse parameters in the browser query; analytics builds SQL from allow-listed metric names only, host names only in `IN` lists built through an escaping helper or fetched by metric then filtered in Python |
| Browser reading other ClickHouse data through `/ch-api/` | Info disclosure | Already limited to `SELECT ON history.*` read-only user; new tables are inside that scope by design (events/incidents/triage are not secrets on this network) |
| Narration stating unsupported facts | Integrity | Template only, field-presence tests (D-28) |
| Cross-site leakage on a shared broker | Info disclosure | ACL rendered per site; extend the exact-grants test |
