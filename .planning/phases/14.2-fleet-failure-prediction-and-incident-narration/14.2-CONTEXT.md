# Phase 14.2: Fleet Failure Prediction and Incident Narration - Context

**Gathered:** 2026-10-04 (discussion started 2026-10-03, resumed from checkpoint)
**Status:** Ready for planning

<domain>
## Phase Boundary

A separate analytics container computes service needs, trend forecasts and incident narration
from 14.1's ClickHouse history and the poller's live MQTT topics. It publishes them as retained
MQTT topics under `sites/<site_id>/`. The dashboard shows:

- a Needs pane
- tier markers
- a forecast line chart for any trend metric
- narrated incident cards

Experts can triage needs. The analytics container also takes over writing durable event and
incident history and the daily availability rollup.

Out of scope: the cloud transport optimisation phase, a local language model, dashboard history
views beyond the forecast chart, and kiosk mode (removed in `4937450`, DASH-17 descoped).

</domain>

<decisions>
## Implementation Decisions

### History inputs and container responsibilities
- **D-01:** Add a ClickHouse filesystem read cache on the `s3` disk (config only, in
  `deploy/clickhouse-config/config.d/`). Forecasts read more than 31 days of history, so
  without it they would hit cold MinIO parts on every query. (Resolves roadmap open decision A.)
- **D-02:** The analytics container is the durable recorder of event and incident history. It
  subscribes to MQTT and writes `history.events` and `history.incidents`. The poller is not
  changed (D-44 posture kept: push-only, no on-disk state). This is a requirement because the
  broker, S3, ClickHouse and dashboard will move to the cloud. (Resolves roadmap open decision B.)
- **D-03:** Interim ingestion until the separate transport phase:
  - The container reads today's `sites/<site_id>/lan/events/recent` (bounded, at most 1000
    entries) and `sites/<site_id>/lan/incidents/+/status`.
  - It deduplicates events against what it has already written.
  - An incident tombstone means close: the container writes the close row with duration.
- **D-04:** The daily availability rollup (14.1, JSON + Parquet to MinIO) moves from the poller
  to the analytics container in this phase.
- **D-05:** D-30 restated: the operator's own cloud tenancy counts as inside the network.
  Nothing goes to third-party model providers or SaaS the operator does not control.
- **D-06:** All endpoints (broker, ClickHouse, MinIO) are env-configured and location-agnostic.
  The target split is Checkmk, poller and worker on-prem, with broker, S3, ClickHouse,
  dashboard, Grafana and analytics in the cloud, over metered 4G links with many sites.

### Need sources and tiers
- **D-07:** There are three need sources:
  1. **Failure:** a ping host is DOWN, a TCP port or a monitored systemd/Windows service fails.
     Derived from the live `status`, `services` and `topology` topics.
  2. **Trend to threshold:** disk fill, SSD/NVMe wear, reallocated sectors, memory creep.
     Simple linear regression (D-31, no ML), fitted from ClickHouse.
  3. **Sustained or already-breached:** for example a disk already critical, or CPU near 100%
     most of the time. This is a new rule type over a time window, not a regression.
- **D-08:** The tier derives from the existing criticality by a fixed mapping:
  - critical → immediate
  - high → urgent
  - medium/low → standard

  This applies to failure needs. There is no new setting; the existing `CriticalityEditor`
  stays the editor. It is cheap and reversible. The parked todo on the criticality model stays
  open.
- **D-09:** Trend tiers are banded by **days until the critical level**:
  - immediate: already critical or under 3 days
  - urgent: 3 to 20 days
  - standard: over 20 days
  - nothing shown as a need beyond 90 days

  All bands are configurable. This updates the D-34 defaults (3/15). The warning-crossing date
  is shown but does not set the tier. A sustained breach is immediate.
- **D-10:** The confidence tag depends on history length and fit quality:
  - low: under 14 days of history
  - medium: 14 to 60 days
  - high: over 60 days with a good straight-line fit

  A noisy, flat or receding series gets no date and is labelled "stable" or "no clear trend".
  A low-confidence SMART/wear date is never immediate on its own (D-31 dispatch risk).
- **D-11:** A trend fit starts after the last sharp drop in the series, such as a disk cleanup,
  so one cleanup does not bend the trend.
- **D-12:** Warn and crit levels come from the latest sample's `warn`/`crit` columns in
  `history.metrics`, which are Checkmk's own levels. Analytics config supplies fallback levels
  for metrics that Checkmk gives no levels for (for example reallocated sectors).

### Publication contract
- **D-13:** The analytics container evaluates every 15 minutes.
- **D-14:** It publishes one retained QoS 1 topic per active need,
  `sites/<site_id>/lan/needs/{need_id}/status`, built with the same `site_topic()` convention.
  The dashboard sees the topic as `lan/needs/...` after `mqttClient.ts` strips the prefix.
  - The topic is tombstoned (empty retained payload) when the need resolves.
  - Payload: source, host, service/metric, tier, computed tier, days to warn and days to crit,
    warn and crit dates, confidence, history_days, narration text, and the triage fields from
    D-22.
  - `need_id` is stable per (source, host, service, metric), so the same problem keeps the same
    id while it is open.
- **D-15:** It publishes a retained forecast fit for **every chartable trend metric**, not only
  for metrics with an active need, so the chart can be opened at any time (D-18). Suggested
  topic: `sites/<site_id>/lan/forecasts/{host}`, one message per host carrying all of that
  host's metric fits. The researcher or planner may choose a per-metric topic instead.
  - Each fit carries: service, metric, unit, slope, intercept, fit window start and end, warn
    and crit levels, warn and crit crossing dates (or null), confidence, history_days, and a
    status of trending, stable or no clear trend.
  - The dashboard draws from these numbers and **never refits**, so the chart and the need
    cannot disagree.
- **D-16:** Trend **needs** are raised only for the D-31 monotonic set: filesystem used %,
  SSD/NVMe wear, reallocated sectors and memory creep. The set is a configurable list.
  - Other chartable metrics, such as CPU, get a fit and a chart, but they do not raise a trend
    need.
  - A sustained breach on any metric still raises an immediate need (D-07 source 3).
  - For noisy metrics like CPU, the D-10 gate will usually return "no clear trend", so the chart
    shows no forecast date.
- **D-17:** The broker ACL (`deploy/mosquitto.acl.template`) gets an analytics login with these
  rights:
  - read: the site's `lan/#` and `needs/triage/cmd`
  - write: `lan/needs/#`, `lan/forecasts/#` and `lan/incidents/+/narration`

  It also gets a triage login with write access to `needs/triage/cmd` only (D-21).

### Forecast chart (added by the user in this discussion)
- **D-18:** A line chart is available **at any time for every trend metric** of a host: disk
  (each filesystem), CPU, RAM, and other gauges that benefit from a line chart. It is not limited
  to active needs.
  - It opens from host details, where the host's chartable metrics are listed.
  - It also opens from a trend-need row in the Needs pane and from the Needs section in host
    details.
- **D-19:** The chart draws:
  - measured history as a solid line
  - horizontal warn and crit level lines
  - a vertical "today" line
  - a dashed trend line extended forward from the fit window
  - a marker and date label where the trend crosses warning and where it crosses critical
  - the confidence badge and history span in the chart header

  A low-confidence trend is drawn fainter with a caption (for example "9 days of history, low
  confidence").
- **D-19a (user, 2026-10-04):** The trend line is drawn **only when the regression shows a clear
  trend**: a meaningful slope with a good straight-line fit, using the same fit-quality gate as
  D-10.
  - When values are random or noisy with no clear trend, or flat, **no trend line is drawn at
    all**, not even a faint one. The chart shows history, the levels and the today line, with a
    "no clear trend" or "stable" label.
  - Confidence (low/medium/high) only changes how a *clear* trend is drawn. It never makes a
    line appear for noise.
  - A clear trend that moves away from the levels is drawn without crossing markers.
- **D-20:** History for the chart is read by the dashboard from ClickHouse through the existing
  same-origin, GET-only `/ch-api/` path as `dashboard_reader` (14.1 D-24). It uses hourly
  averages; the range covers the fit window and recent history.
  - This is the first dashboard feature that uses `/ch-api/`. It is limited to this chart, so
    D-50's "no history views" holds otherwise.
  - The forecast part comes from the D-15 topic.

### Triage (D-35)
- **D-21:** Write path (same pattern as Phase 16 admin mode):
  - The dashboard publishes a triage command on `sites/<site_id>/needs/triage/cmd` using a
    separate broker login that can only write to that topic.
  - The analytics container consumes it and records an audit row per action in a ClickHouse
    `history.need_triage` table.
  - It then republishes the need with the triage applied.

  Checkmk host labels are not used. No custom backend is added.
- **D-22:** Triage actions are downgrade, upgrade to immediate, and cancel. The need payload
  carries the original computed tier, the override, when it was set, and an optional note or
  name.
- **D-23:** An override lasts until the need resolves (is tombstoned). A recurrence starts
  untriaged. If the computed tier becomes **worse** than it was at triage time, the override is
  dropped and the need reappears. A cancelled need is hidden from the pane but kept in the
  table.
- **D-24:** Triage controls appear only in the dashboard's edit mode, the existing gate on this
  closed network. Real per-user identity is out of scope.

### Dashboard placement of needs
- **D-25:** A new **Needs pane** sits beside the incident pane. Each row shows:
  - tier badge, host, what (metric or service) and date
  - a prominent confidence badge with the history span

  Clicking a row selects the host. Triage controls appear in edit mode.
- **D-26:** A small tier marker on tree rows and map nodes, separate from the state colour.
  Host details gets a Needs section.
- **D-27:** No double counting: a failure need for a host already covered by an open incident is
  not listed separately. The incident card shows the derived tier instead.

### Narration
- **D-28:** Narration is template-based only in 14.2; a local model stays deferred (D-30).
  - Every sentence is filled from incident or event fields.
  - Tests assert that no sentence appears when its field is absent, so narration never states
    a fact absent from the data.
  - English only.
- **D-29:** Open incidents: the analytics container publishes a retained
  `sites/<site_id>/lan/incidents/{incident_id}/narration` with a headline plus 2 to 4 sentences.
  The poller's `.../status` topic stays the poller's. The narration topic is tombstoned when the
  incident closes. Example:
  - "sw1 (low criticality) has been DOWN since 12:05 (3 min)."
  - "2 devices behind it cannot be observed: cam1, linux1."
  - "No dependent devices are affected."
- **D-30 (phase-local):** Closed incidents get a final summary (adds duration and recovery
  time), stored in `history.incidents`, so "what happened last Tuesday" can be answered in
  Grafana. There is no dashboard history view for it.
- **D-31 (phase-local):** The incident card shows the narration and falls back to today's card
  when the narration is missing. Needs carry their own one-line narration text.

### Claude's Discretion
- Chart library choice. It must use `kone-design-system` tokens and work in light and dark; the
  design system has no chart component.
- Exact fit-window length, the definition of a "sharp drop", and the fit-quality threshold.
- `history.events` / `history.incidents` / `history.need_triage` schemas and TTLs, which follow
  14.1 conventions.
- Analytics container language and layout. The default is Python with uv, reusing the poller's
  conventions.
- Which gauges beyond CPU, RAM and filesystems are listed as chartable in host details.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `site_topic()` / `relative_topic()` in `scripts/mqtt_poller.py`: the per-site topic convention for every new topic.
- Phase 16 admin command path (`admin/cmd`, `admin/ack`, retained `admin/faked`): the template for triage commands.
- `history.metrics` already stores every perf-data metric of every service with `warn`/`crit` per sample, so thresholds and chart history need no poller change.
- `kone-design-system` (`design-system/src/components`): Badge, Tooltip, Table and others; no chart component.

### Established Patterns
- Retained QoS 1 topics with a tombstone on close. The dashboard clears its slice and rebuilds it on reconnect (see `MQTT-CONTRACT-WALKTHROUGH.md`). The needs, forecasts and narration slices must follow the same rule.
- Best-effort, never-fatal side writes (14.1 ClickHouse writer). The analytics container should degrade the same way when ClickHouse or MinIO is unavailable.
- Restarting a single container on dmc-server breaks Checkmk egress, so the deploy instructions must use a full `podman compose down && up -d`. dmc-server is the only deployment, and the user runs live steps there.

### Integration Points
- Dashboard `mqttClient.ts` subscriptions: add `lan/needs/+/status`, `lan/forecasts/...` and `lan/incidents/+/narration`.
- Dashboard host details: the metric list and chart entry point. Needs pane beside `IncidentList`.
- `deploy/compose.yaml`: new analytics service with env-configured endpoints. The rollup job moves out of the poller.

</code_context>
