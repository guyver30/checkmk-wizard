## Warnings

### WR-01: Triage apply is split across two lock windows with ClickHouse I/O between them
**File:** `analytics/service.py:456-478`
`_on_triage` computes the override under the lock, releases it, does a blocking ClickHouse insert (up to 5 s) and only then calls `tracker.apply_override`. In the gap `run_cycle` can tombstone the need (the audit row claims a change that never happened) or fire an auto-reset (the stale override is re-applied, then dropped on the next tick with a second audit row). The publish can also race `run_cycle`'s publish of the same need; it self-heals on the next fast tick (~15 s). `_need_sigs` is written from both threads without the lock.
**Fix:** do lookup, compute, `apply_override` and the `_need_sigs` update in one `with self.lock:` block; keep the audit insert outside it (skip the audit if `tracker.get()` is None or its `computed_tier` changed), or keep the two-phase shape and re-validate under the second lock.

### WR-02: A downgraded need can end up shown above its computed tier
**File:** `analytics/rules.py:331`, `:361`
`carry_triage` only drops a triage when the computed tier gets worse than at triage time. A downgrade from immediate to urgent therefore stays "urgent" if the computed tier later improves to "standard", so the need shows as more urgent than the data says while labelled "Downgraded". Same for `apply_override`.
**Fix:** for `action == "downgrade"`, clamp the effective tier to the less urgent of the stored triage tier and the new computed tier (`max(..., key=_TIER_RANK)`).

### WR-03: No broker message-size limit and an unbounded inbound queue behind open write logins
**File:** `deploy/mosquitto.conf`; `analytics/service.py:290-294, 269`
Mosquitto's default `message_size_limit` is effectively unlimited, and `wstriage`/`wsadmin` are served openly. `on_message` queues the full message on an unbounded `queue.Queue()` before `parse_triage_command` applies its 4096-byte check. Every valid command costs a ClickHouse insert that can block the single worker for up to 5 s when ClickHouse is down, so status, incident and event messages queued behind it go stale.
**Fix:** set `message_size_limit` (e.g. 2 MB; `MAX_EVENTS_PAYLOAD_BYTES` is 1 MB), drop oversized triage payloads in `on_message` before enqueueing, bound the queue, optionally move the audit insert off the shared worker.

### WR-04: Deeply nested JSON raises RecursionError, which the parsers do not catch
**File:** `analytics/triage.py:64-67`; `analytics/service.py:187-191`; `analytics/recorder.py:62-65`; `scripts/mqtt_poller.py:1122`
These parsers catch `(UnicodeDecodeError, ValueError)`. About 4000 `[` bytes fit under `MAX_COMMAND_BYTES` and make `json.loads` raise `RecursionError` (a `RuntimeError`). `_work` catches it, so the service survives, but each message logs a full traceback (log flood); `handle_message` called inline would crash.
**Fix:** also catch `RecursionError` in `parse_triage_command`, `_load_json`, `EventRecorder.new_rows` and `parse_admin_command`.

### WR-05: The smoke test restarts the broker by default
**File:** `scripts/smoke_test_broker.py` (~640; `--restart-cmd` default `podman compose restart mosquitto`)
Unless `--skip-restart` is passed a plain run restarts a single container, which project memory records as turning all real hosts DOWN (2026-10-02). The final line also prints "all checks passed" when the wsadmin, analytics and wstriage groups were skipped for lack of passwords.
**Fix:** make the restart opt-in (`--with-restart`) or default `--skip-restart` to true; print `N checks passed, M skipped`.

### WR-06: The analytics container installs dependencies from the network on every start and runs as root
**File:** `deploy/compose.yaml:467-469`; `deploy/clickhouse-config/initdb/02-users.sh:105-106`
It runs `pip install paho-mqtt==2.1.0 boto3==1.43.105 tzdata==2026.4 && exec python -m analytics` on every start: it will not start offline, a PyPI outage turns a crash into a restart loop, transitive dependencies are unpinned and unhashed, and it runs as root (source mount read-only). `analytics_writer` holds `GRANT S3 ON *.*` and `CREATE TEMPORARY TABLE ON *.*`, which lets that login read or write any reachable S3/HTTP URL through the `s3()` table function; the grants are needed for the Parquet rollup and the S3 keys are the default `minioadmin` pair.
**Fix:** build a small image with pinned, hashed dependencies and a non-root `USER`; give the rollup its own ClickHouse user that holds the S3 grant.

### WR-07: The drawing has no shape cap on add, so saved shapes beyond 500 are silently lost
**File:** `dashboard-react/src/store/mapDrawingStore.ts:92-94, 73-85`; `dashboard-react/src/lib/mapDrawing.ts:170, 180-182`
`addShape` enforces no limit but `sanitizeDrawing` keeps only `MAX_SHAPES` (500). After saving, `saved` is the truncated copy while `draft` keeps all shapes and `dirty` is false, so the UI shows "saved" and shapes past the 500th vanish on reload.
**Fix:** reject `addShape` at `MAX_SHAPES`, or have `saveDrawing` throw `MapDrawingError("Too many shapes")`.

### WR-08: Blocking ClickHouse and rollup work on the main loop thread stalls the 15 s failure tick
**File:** `analytics/service.py:613-649, 653-691`; `analytics/rollup.py:704-735`
`run_cycle(slow=True)` runs three sequential ClickHouse queries (5 s timeout each, up to ~15 s) and `maybe_run_rollups` (28-day backfill, several HEAD and ClickHouse calls per day) runs on the same thread, so the 15 s failure tick is delayed. The fast-tick goal of quick 261005-dox holds only while ClickHouse and MinIO are healthy and quick. The 90-day fit query may also exceed the shared 5 s timeout, in which case forecasts and trend needs are skipped with a one-line warning.
**Fix:** run the slow cycle and rollups on a separate thread, or at least give the fit queries their own timeout; keep the failure tick independent behind the existing lock.
