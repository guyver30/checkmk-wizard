<objective>
Build the browser-side Checkmk REST writer (D-03/D-04/D-05/D-06/D-07). It is a TypeScript port of `api.py`'s proven choke-point, GET-ETag-PUT and activation-polling patterns. The plan also adds the scoped-credential config constants and the same-origin route the browser needs to reach Checkmk at all.

Purpose: plans 13-06 (map edit wiring) and 13-07 (Apply) call only these functions, never fetch() directly.

Same-origin decision (planner, recorded here and flagged to the user): a browser page served from the dashboard's origin cannot call Checkmk's REST API on a different origin (port 8080) unless Checkmk answers CORS preflights, and research found no Checkmk CORS support. 13-01's P5 probe records the live answer. The writer therefore targets the configurable prefix `CHECKMK_REST_ORIGIN = "/checkmk-api"`. The dashboard's own Vite dev/preview server proxies that prefix to Checkmk. After the deferred D-42 cutover, the same job is one nginx `location` block in the existing dashboard container (documented in 13-08). No new service, backend process or server-side credential exists: the browser still authenticates directly to Checkmk with its own Bearer credential, which is D-04's substance. If 13-01's `VERDICT V-CORS` is ALLOWED, an operator may point CHECKMK_REST_ORIGIN straight at `CHECKMK_BASE_URL` instead; that is the one-constant literal D-04 path.

Output: `checkmkWrite.ts` plus tests, `config.ts` constants, and the `vite.config.ts` proxy.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser (LAN) → dashboard origin /checkmk-api → Checkmk REST | A write-capable Bearer credential crosses from browser JS into Checkmk config |
| operator input (host name) → Checkmk host_config | Free text becomes a Checkmk host name and a URL path segment |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-13-09 | Elevation of Privilege | TOPOLOGY_EDITOR_SECRET in the bundle | mitigate | Scoped topology_editor role (13-04), never admin; config.ts comment documents the WRITE scope explicitly; residual accepted under D-04's trusted-LAN posture |
| T-13-14 | Information Disclosure | CheckmkWriteError messages | mitigate | The error message/fields carry method, url, status and body only; the Authorization header is never copied into an error (tested: the message excludes the secret) |
| T-13-15 | Tampering / Injection | host names in URL paths and POST bodies | mitigate | isValidHostName (`^[-0-9a-zA-Z_.]+$`) gates createUnmanagedSwitch; every path segment is encodeURIComponent-encoded; label values come only from formatMapPosition (integers) or the fixed "yes" |
| T-13-16 | Tampering | lost update / attribute stripping | mitigate | GET-ETag-merge-PUT with If-Match (REPLACE verdict); a serialized write chain prevents stale-ETag races |
| T-13-17 | Elevation of Privilege | activating others' pending changes | mitigate | force_foreign_changes: false is hard-coded (acceptance grep) |
| T-13-18 | Spoofing / CSRF | /checkmk-api proxy route | accept | Auth is a Bearer header set by script (not a cookie), so cross-site form posts carry no credential; the proxy adds no auth of its own and exposes nothing beyond Checkmk's already LAN-published port 8080 |
| T-13-19 | Denial of Service | activation polling | mitigate | Hard bound of 60 polls × 500 ms, then a visible error; there is no background retry |
</threat_model>
