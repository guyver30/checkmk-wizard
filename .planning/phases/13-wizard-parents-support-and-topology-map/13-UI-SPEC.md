# Phase 13 — UI Design Contract

> Visual and interaction contract for the vis-network topology map, its "Edit topology" mode,
> and the manipulation/apply UI that replaces `dashboard-react/src/components/MapPlaceholder.tsx`
> in `IndexRoute.tsx`'s `centreTop` slot. Generated by bm-ui-researcher from `13-CONTEXT.md` (11
> locked decisions, D-01–D-11), `13-RESEARCH.md`, and the live `dashboard-react/` codebase
> (kone-design-system's light palette, established since Phase 11.1).
>
> **This spec covers only what Phase 13 adds.** State palette, staleness treatment, physics
> behavior, typography roles, spacing scale, and the base color system are inherited **unchanged**
> from Phase 11/11.1 (`stateMapping.ts`, `design-system/src/tokens.css`) — this document cites
> their exact values so the map's canvas rendering (which cannot read CSS) stays byte-for-byte
> consistent with the DOM rendering (which can), rather than re-deriving a second palette.
>
> **Auto-mode note:** produced without user questions per the orchestrator's Auto Mode. Every
> discretionary call this spec makes (node-state-to-hex mapping for canvas recolor, manipulation
> toolbar restyle, toolbar/button placement, delete-edge confirmation mechanism) is logged in
> "Auto-Mode Design Decisions" at the end, with its rationale, for the checker/planner to audit.

## Spacing Scale

Inherited from the established `dashboard-react` scale (Tailwind defaults + the one existing
12px exception already in use by `GroupingControls`/`TreeNode`). No new spacing token is
introduced by this phase.

| Token | Value | Usage in this phase's new UI |
|-------|-------|-------------------------------|
| xs | 4px | Icon-to-label gaps inside toolbar buttons |
| sm | 8px | Gap between Edit-topology `Switch`, pending-count `Banner`, and the `Apply` `Button` in the toolbar row (`gap-2`) |
| md | 12px | Toolbar row's own padding (`p-3`) — same inherited exception as `GroupingControls`'s `p-3`, not a new one |
| lg | 16px | Gap between the toolbar row and the map canvas below it, and the map wrapper's internal padding, matching the existing `centreTop` `p-3`→content pattern in `IndexRoute.tsx` (rounded up to `gap-4` only where the existing layout already used it — do not invent a new value here) |
| xl | 24px | Not used by this phase's new UI |

**Explicitly out of scope for this scale:** the vis-network canvas's internal node-grid spacing
(`SPACING = 150` logical graph units in the D-01 initial-placement algorithm, see Topology Map
Rendering below) is a **graph-layout distance**, not a CSS spacing token, and must not be confused
with or forced onto the 4px-multiple scale above.

## Color

Light theme throughout (unchanged, kone-design-system default / Phase 11.1's palette pivot). Every
hex below is read directly from `design-system/src/tokens.css` and `design-system/src/components/
Badge.tsx`'s `colorMap` — **not re-derived** — so the canvas (which needs a literal hex string for
the D-08 SVG recolor) stays byte-identical to the DOM (which reads the same values through CSS
custom properties).

```css
/* Already-defined tokens this phase reads, does not redefine: */
--color-bg-canvas-default: #ffffff;      /* neutral-0 */
--color-bg-surface-subtle-default: #f2f2f4; /* neutral-100 */
--color-brand-default: #1450f5;          /* blue-500, "KONE Blue" */
--color-alert-default: #e5252a;          /* red-500 */
```

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#ffffff` (`--color-bg-canvas-default`, neutral-0) | The map's own canvas background (vis-network `background` option) — matches the page's dominant surface exactly, so colored node icons read against the same white the rest of the app uses, not a separate dark or tinted canvas |
| Secondary (30%) | `#f2f2f4` (`--color-bg-surface-subtle-default`, neutral-100) | The map's outer wrapper background (`bg-bg-subtle`, inherited unchanged from `MapPlaceholder.tsx`) and the toolbar row's background |
| Accent (10%) | `#1450f5` (`--color-brand-default`, "KONE Blue") | **Reserved for, and only for:** (a) the "Edit topology" `Switch` in its ON state (already `Switch`'s own `checked:bg-brand`, no override needed); (b) the `Apply changes` `Button` (`variant="primary"`, already blue by the existing `Button` component); (c) the manipulation toolbar's currently-active tool button (e.g. "Add Edge" while armed); (d) the in-progress edge-drawing preview line while the operator drags from one node toward another; (e) the selected/being-dragged node's halo ring (vis-network `node.color.highlight.border`); (f) focus outline on every interactive element in this phase's new UI (inherited global rule, unchanged) |
| Destructive | `#e5252a` (`--color-alert-default`, red-500) | **Reserved for, and only for:** the manipulation toolbar's "Delete edge" action/icon, and the `window.confirm()` guard's implicit destructive framing (see Destructive Confirmation below) |

Accent is never reused for node **state** meaning — the state palette below is fully separate, per
the unbroken Phase 11 D-11 rule that a blue accent can never be misread as a health/status color.

### State palette for map nodes (inherited unchanged from Phase 11 D-11/D-12/D-15 — canvas hex values, traced from `stateMapping.ts`/`Badge.tsx`, not re-derived)

The map's `circularImage` recolor (D-08) needs a literal hex per state to string-replace into each
SVG's `fill="#141414"`. This table is the single source of truth for that hex — it is not a new
palette, it is the exact color each state already renders as via `Badge`'s `colorMap`, transcribed
so canvas code and DOM code can never drift apart.

| Device state | Hex (canvas fill) | Source (`Badge.tsx` `colorMap`) | DOM equivalent |
|---|---|---|---|
| OK | `#22c55e` | `success.text` → `--color-fg-success` → `--green-500` | `StateBadge` `color="success"` |
| WARN | `#f97316` | `warning.text` → `--color-fg-warning` → `--orange-500` | `StateBadge` `color="warning"` |
| CRIT | `#e5252a` | `danger.text` → `--color-fg-danger` → `--red-500` | `StateBadge` `color="danger"` variant `soft` |
| UNREACH | `#e5252a` | same `danger` as CRIT | `StateBadge` `color="danger"` variant `outline` |
| DOWN | `#e5252a` | same `danger` as CRIT/UNREACH | `StateBadge` `color="danger"` variant `solid` |
| UNKNOWN | `#111114` | `black.text` → `--color-fg-onwhite-primary` → `--neutral-900` | `StateBadge` `color="black"` |
| PEND | `#55555f` | `neutral.text` → `--color-fg-secondary` → `--neutral-600` | `StateBadge` `color="neutral"` |
| STALE | `#55555f` | same `neutral` as PEND | `StateBadge` `color="neutral"` variant `outline` |

**Accepted, explicitly-documented tradeoff — CRIT/UNREACH/DOWN collapse to one hex on the map.**
`Badge` distinguishes these three states only by *variant* (soft/outline/solid — border weight and
fill density), a distinction that does not translate to a single flat-fill SVG recolor. Rather than
inventing three different reds that would silently diverge from `Badge`'s real DOM colors (the exact
mistake Phase 11's dark-theme revision explicitly called out and reverted for CRIT/DOWN), this phase
keeps the map's fill color identical for all three and instead differentiates them at the **node
border**, which vis-network natively supports as canvas styling (not CSS):

```ts
// Applied per-node at DataSet.update() time, alongside the recolored image:
{
  DOWN:    { borderWidth: 4, shapeProperties: { borderDashes: false } },
  UNREACH: { borderWidth: 3, shapeProperties: { borderDashes: [4, 2] } },
  CRIT:    { borderWidth: 2, shapeProperties: { borderDashes: false } },
  STALE:   { borderWidth: 2, shapeProperties: { borderDashes: [2, 2] } }, // dashed = Phase 11's
                                                                            // hatch-texture intent,
                                                                            // ported to canvas
}
```
Border color for all of the above is the same state hex as the fill (never the accent blue — see
Color's reserved-for list). **This map is a topology overview, not a replacement for the sidebar
tree or the per-device drill-down** — an operator who needs the exact CRIT-vs-UNREACH-vs-DOWN
distinction clicks through to `/details?id={id}` (D-10), where `StateBadgeForState` already renders
it precisely via `Badge`'s variant system. This is consistent with D-11 (this phase's own map stays
"flat," deliberately not duplicating what the tree/table already do well).

**Unmanaged-switch nodes (D-05/D-06):** since a no-agent/no-IP host reports `state: "OK"` by
Checkmk's own default ("host check of these hosts will always report UP," per `13-RESEARCH.md`'s
docs citation), an unmanaged switch renders with the **same green `#22c55e` OK fill** as any healthy
managed host — this is not a bug, it correctly reflects "nothing is checked, so nothing can fail."
No separate visual state is invented for this phase; the `NetworkDevice`/`internet.svg` icon shape
is the only signal that a node is a network-topology device at all (managed or not — the icon does
not currently distinguish the two, and this phase does not add a new tag/label to do so; flagged as
a real, open gap for whoever revisits this, not silently resolved).

## Topology Map Rendering

**Container & mount point:** replaces `MapPlaceholder.tsx` at the exact geometry
`IndexRoute.tsx`'s `centreTop` slot already reserves (D-27's sized-by-container rule, unchanged).
The wrapper `<div>` keeps `MapPlaceholder`'s own classes (`rounded-md border border-neutral-150
bg-bg-subtle`) — the vis-network `<div ref={containerRef}>` mounts *inside* that wrapper, with the
canvas background set to `#ffffff` (Color: Dominant) via the `Network` constructor's `background`
option, not the wrapper's `bg-bg-subtle`, so icons read against a clean white field.

**Toolbar row (new):** a single row sits between the existing `StatsStrip` and the map canvas,
inside `centreTop`'s flex column (same `gap-2 p-3` pattern `IndexRoute.tsx` already uses for its
`StatsStrip` + placeholder stack):

```
[Switch: Edit topology]   [Banner: "N changes not yet applied"]   [Button: Apply changes]
```
The `Banner` and `Apply changes` `Button` render **only** while edit mode is on — in read-only mode
the row shows only the `Switch`, collapsed to its own height (no empty `Banner`/`Button` placeholder
space reserved), so a kiosk/read-only viewer sees the smallest possible chrome.

**Node shape/icon/recolor (D-08/D-09, locked):** `shape: 'circularImage'`, `image` set to
`data:image/svg+xml;utf8,${encodeURIComponent(recolored)}` where `recolored` is the vendored SVG's
raw text with `fill="#141414"` replaced by the state hex from the State palette table above. Node
size: 32px diameter (matches the sidebar tree's `.icon` visual weight scaled up for map legibility;
not a new token, a canvas-only pixel value). Node label: `displayName()` (D-18's alias-or-id rule,
reused verbatim from `display.ts` — never re-derived), rendered below the icon at Label size
(12px)/Inter, color `#111114` (`--color-fg-primary` equivalent).

**Edge styling:** `arrows: 'to'`, arrow pointing **from parent to child** (matches Checkmk's own
convention: a host's `parents` are what it depends on for reachability). Default edge color
`#96969f` (`--neutral-400`); the in-progress `addEdge` preview line (drawn while dragging, before
release) is `#1450f5` (Accent) at 2px, per Color's reserved-for list.

**Initial grid placement (D-01, Claude's Discretion per `13-CONTEXT.md`):** parentless hosts use
the row-major grid from `13-RESEARCH.md`'s Code Examples (`COLS = ceil(sqrt(n))`, `SPACING = 150`
logical units) as their starting `x`/`y` before the one-time stabilization pass (Phase 11 D-09,
unchanged) settles them. This is graph-layout math, not a CSS spacing decision — see Spacing Scale's
explicit carve-out.

**Merge-in-place (DASH-07, unchanged):** every MQTT `lan/devices/topology` update and every
device-status color change goes through `nodesDataSet.update()`, never `network.setData()` — see
`13-RESEARCH.md` Pattern 2/Anti-Patterns for the exact contract; this UI-SPEC does not repeat that
implementation detail beyond confirming it does not change any visual value declared above (a
`DataSet.update()` call and a full re-render must produce byte-identical node/edge styling).

## Edit Mode & Manipulation Toolbar

**Toggle behavior (D-02, locked):** the `Switch` is the single source of truth for whether
manipulation is possible. When off, `network.setOptions({ manipulation: { enabled: false } })` and
node dragging is disabled (`interaction: { dragNodes: false }`) — a stray touch/drag on a shared
display cannot move a node or draw an edge. When on, both re-enable.

**Toolbar restyle (D-03's built-in toolbar, kone-design-system visual language):** vis-network's
default manipulation UI ships its own unstyled `.vis-manipulation`/`.vis-button` DOM overlay. This
phase overrides that default CSS to match the existing `Button` component's `neutral` variant
exactly, rather than leaving vis-network's raw appearance:

```css
.vis-manipulation {
  background: #f2f2f4;           /* --color-bg-surface-subtle-default, matches toolbar row */
  border-radius: 999px;          /* --radius-pill, matches Button's rounded-pill */
  font-family: 'Inter', 'Helvetica Neue', Arial, sans-serif;
  font-size: 13px;               /* Body role */
  padding: 4px;
}
.vis-button {
  border-radius: 999px;
  border: 1px solid #b8b8c2;     /* --neutral-300, matches Button neutral's border */
  color: #111114;                /* --color-fg-primary */
}
.vis-button.vis-active,
.vis-button:hover {
  background: #1450f5;           /* Accent — active/selected tool only */
  color: #ffffff;
  border-color: #1450f5;
}
.vis-button.vis-delete { color: #e5252a; border-color: #e5252a; } /* Destructive */
```
This is a CSS override of vis-network's shipped class names, not a rebuild of the toolbar — no
custom drag-to-connect code is written (per `13-RESEARCH.md`'s Don't-Hand-Roll table).

**Click-mode gating (interaction contract, new — not explicit in `13-CONTEXT.md`, resolved here):**
node click means two different things depending on mode, and the two must never both fire:
- **Read-only mode (Switch off):** clicking a node navigates to `/details?id={id}` (D-10). Cursor:
  `pointer` on node hover.
- **Edit mode (Switch on):** clicking a node is captured by vis-network's manipulation toolbar
  (selecting the first/second node of a new edge, or the node to reposition). It must **not**
  navigate. The `click`/`selectNode` handler checks the edit-mode boolean before calling
  `navigate()` — this gating is a required implementation detail of this contract, since vis-network
  fires the same event in both modes.

**Idle-timeout auto-exit (discretionary, recommended, not locked):** `13-RESEARCH.md`'s Security
Domain flags "a tab left in edit mode" as the residual risk after D-02's toggle. This UI-SPEC
recommends (not requires) auto-reverting the `Switch` to off after 5 minutes of no map interaction,
surfaced via the same `Banner`/`Snackbar` pattern already available ("Edit topology turned off after
5 minutes of inactivity") — flag for planning to lock in or explicitly decline, not silently skip.

## Apply / Activation Flow

Every `addEdge`/`editEdge`/`deleteEdge` callback PUTs the change to Checkmk immediately (per D-03/
D-04) but does **not** activate it — per `13-RESEARCH.md`'s Pitfall 3, a Checkmk host-attribute PUT
is a pending WATO change until activated. The pending-changes `Banner`'s count is the number of
edits made since the last successful Apply, tracked client-side (not re-derived from Checkmk's own
pending-changes count, to avoid an extra REST round-trip on every keystroke of interaction).

**Apply button states:**

| State | `Button` prop | Label |
|---|---|---|
| No pending changes | `disabled` | "Apply changes" |
| Pending changes, idle | enabled, `variant="primary"` | "Apply changes" |
| Activation in-flight | `loading` (existing `Button` `loading` prop — spinner already built in) | "Applying…" |
| Activation failed | enabled, `variant="primary"` (retry) | "Apply changes" (Snackbar carries the error copy, button label does not change to avoid two error surfaces) |

On success: `Snackbar` "Topology updated" (2–3s auto-dismiss, matching the component's existing
transient-feedback role), pending count resets to 0, `Banner` disappears. On failure: `Snackbar`
"Saved, but not live yet" persists until dismissed or the next successful Apply (per Copywriting
Contract) — never silently retried in the background, matching this codebase's established
"best-effort must be visible" posture (contrast with `wizard.py`'s own retry/poll pattern, which
IS silent because it runs in a CLI the operator is already watching; a browser tab may not be
watched the same way).

## Empty / First-Load State

When `useAppStore`'s `topology` slot has devices but zero drawn `parents` edges anywhere (the
pre-D-01-migration state on a fresh site), the map renders every host in the D-01 grid layout —
**not** a blank canvas and **not** the Copywriting Contract's empty-state heading/body, which is
reserved for the *zero devices at all* case (mirrors DASH-01's existing "Waiting for device data…"
precedent — do not duplicate that string here for a different condition). Instead, a small
dismissible `Banner` (only shown when edit mode is off AND zero edges exist) nudges the operator:

> **"No connections drawn yet — turn on Edit topology to start."**

This is the *only* new copy for this state; the grid of nodes itself is the primary visual, not a
placeholder graphic, so every host stays clickable/navigable exactly as it would with edges present
(D-01's "every node reachable/draggable" requirement, applied to click-through as well as drag).

## Accessibility

- **Color is never the only signal (inherited rule, applied to canvas):** every node's state is
  additionally carried by border weight/dash pattern (see State palette table) — not full parity
  with the DOM's icon-based signal, but the closest canvas-native equivalent, and an explicitly
  documented, accepted gap (see Color's "Accepted, explicitly-documented tradeoff").
- **Canvas focus/keyboard:** vis-network's canvas is not natively keyboard-navigable per-node.
  This phase does not attempt to retrofit full keyboard graph navigation (out of scope, matches
  `13-CONTEXT.md`'s silence on it) — the sidebar tree remains the keyboard-accessible path to every
  device's `/details` view, unaffected by this phase.
- **Edit-mode toggle, Apply button, toolbar buttons** all inherit `Switch`/`Button`'s existing
  `focus-visible:shadow-focus` treatment — no override needed, already accessible by construction.
- **Toolbar restyle keeps vis-network's own `title`/ARIA attributes** on its manipulation buttons
  (vis-network sets these itself for its built-in add/edit/delete controls) — the CSS override
  above changes only color/shape/font, never removes or replaces existing accessible markup.

## Destructive Confirmation — why `window.confirm()`, not a modal

`kone-design-system`'s full export list (`design-system/dist/index.d.ts`) contains no `Modal`/
`Dialog` primitive. Per CLAUDE.md's simplicity-first rule and `13-RESEARCH.md`'s Don't-Hand-Roll
table (avoid inventing UI machinery a well-tested primitive already covers), this phase does **not**
build a custom modal component for one confirmation. The native `window.confirm()` — already an
accepted pattern for irreversible-ish actions in browser apps without a modal library — gates
`deleteEdge` only (the one destructive action D-03 exposes); `addEdge`/`editEdge` write immediately
with no confirmation, since they are additive/correctable (delete the wrong edge, redraw) rather
than lossy.
