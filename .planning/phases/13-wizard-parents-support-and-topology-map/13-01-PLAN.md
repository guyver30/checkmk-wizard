Create a stdlib-only script (urllib.request, urllib.error, json, os, sys, re) with the same structure and conventions as `scripts/probe_host_attribute_merge.py`: env-var-only configuration using the five names listed in the interfaces block, the Authorization header never printed (render it as `Bearer <username> ***` if at all), and a module docstring that explains the questions it answers and cites RESEARCH.md A1-A4. Throwaway host names are the module constants `PROBE_PARENT = "gsd-probe-topo-parent"` and `PROBE_CHILD = "gsd-probe-topo-child"`. Every step prints a `P<n>` header, the HTTP status and the relevant response fields. It never calls activate-changes (same rationale as the merge probe: a create-then-delete pair leaves self-cancelling pending changes). It deletes both hosts in a `finally` block, child first, and tolerates 404 on delete.

Steps:
- P1 (RESEARCH A4, OpenAPI capability scan): GET `{base}/openapi-doc.yaml` as text. Scan it without a YAML library: find each path key line and the HTTP-method keys indented under it, up to the next path key at the same indent. Print VERDICT lines for four questions. (a) Does `/domain-types/user_role/collections/all` have `post`? Print `user_role create: AVAILABLE|ABSENT`. (b) Does `/objects/user_role/{role_id}` have `put`? Print `user_role edit: AVAILABLE|ABSENT`. (c) Does any path containing `host_attribute` or `custom_attribute` have `post`? Print `custom host attribute definition: AVAILABLE|ABSENT`, listing the matching paths. (d) Does `/objects/host_tag_group/{name}` have `put`? Print `host_tag_group update: AVAILABLE|ABSENT`. Match path parameters with any `{...}` placeholder name (the spec may say `{role_id}`, `{name}` or `{ident}`), and print the literal matched path keys so the verdict is auditable.
- P2 (RESEARCH A1, built-in tag groups): GET `/domain-types/host_tag_group/collections/all` and print, for the group ids `agent`, `snmp_ds`, `address_family` and `device_type`, each group's id and its list of tag ids. If a built-in group is not in the collection, also try GET `/objects/host_tag_group/{id}` and print that result.
- P3 (RESEARCH A1/A2, D-06 switch shape + labels): POST `/domain-types/host_config/collections/all` with query `bake_agent=false`, folder `/`, host_name PROBE_PARENT and attributes `tag_address_family: "no-ip"`, `tag_agent: "no-agent"`, `tag_snmp_ds: "no-snmp"`, `tag_device_type: "NetworkDevice"`, `labels: {"map_position": "120,-40", "unmanaged_switch": "yes"}`. Print the status and, on success, the echoed `extensions.attributes`. On a 400, print the error body and retry without `tag_device_type`, then again without `tag_address_family`, printing which attribute caused the rejection. Print `VERDICT V-SWITCH: <the exact attribute dict that was accepted>`.
- P4 (parents + label merge round-trip): create PROBE_CHILD with the same no-ip/no-agent/no-snmp tags and no labels. GET it (capture ETag). Build the full `extensions.attributes` dict minus `meta_data`, set `parents: [PROBE_PARENT]` and `labels: {"map_position": "0,0"}`, and PUT it with `If-Match`. GET it again and print `parents` and `labels`. Print `VERDICT V-PARENTS: parents round-trip OK|FAILED (<shape observed>)` and `VERDICT V-LABELS: label values with comma and minus accepted: YES|NO`. Then GET the collection `/domain-types/host_config/collections/all` and print, for the two probe hosts, whether `extensions.attributes.labels` is present in the collection entry. Print `VERDICT V-LABELS-IN-COLLECTION: YES|NO`, which plan 13-04's poller change depends on.
- P5 (CORS): send an OPTIONS request to `{base}/objects/host_config/{PROBE_CHILD}` with headers `Origin: http://dashboard.invalid:8090`, `Access-Control-Request-Method: PUT` and `Access-Control-Request-Headers: authorization,content-type,if-match`. Use `urllib.request.Request(method="OPTIONS")` and catch HTTPError so non-2xx still prints. Print the status and every response header whose name starts with `Access-Control-`. Print `VERDICT V-CORS: ALLOWED` only if `Access-Control-Allow-Origin` is present and `Access-Control-Allow-Headers` covers authorization. Otherwise print `NOT ALLOWED`.
- P6 (RESEARCH A3, permissions): GET `/objects/user_role/user` and `/objects/user_role/admin`. Print the top-level keys of each role's `extensions` and the admin role's enabled permission ids that start with `wato.`, sorted. Then print present/absent against the candidate list `wato.use`, `wato.edit`, `wato.all_folders`, `wato.edit_hosts`, `wato.manage_hosts`, `wato.activate`, `wato.activateforeign`, `wato.see_all_folders`. The candidate list only makes the output easy to scan. The executor must not treat it as confirmed.
- Finally: GET `/domain-types/activation_run/collections/pending_changes` and print how many pending changes exist and whether an ETag header came back. Do not activate.

Exit 0 when every step ran (VERDICT lines may still say ABSENT or NOT ALLOWED; those are findings, not failures). Exit 1 only on missing CMK_REST_SECRET or an unreachable REST base.
