<objective>
Build the two modules that own all external I/O: the MQTT-over-WebSockets connection with its
hand-rolled jittered backoff, and the state store every render module reads from.

Purpose: DASH-05's "jittered exponential backoff" cannot be satisfied by an mqtt.js option —
`reconnectPeriod` is a fixed interval with no growth and no jitter (RESEARCH.md's central
finding, Pitfall 1). And Pattern 1 fixes the merge discipline: every topic's payload is already
a complete bounded snapshot, so the client replaces a slot and never appends.

Output: one connection choke point and one store, both free of DOM code.
</objective>

Create `dashboard/js/mqtt-connection.js` as a classic script exposing a global `connection`
object with `connect()`, `onStatus(handler)` and `disconnect()`.

Connection URL is built at runtime as `ws://` + `location.hostname` + `:` + `WS_PORT` — D-02
requires the host be derived from the page's own origin so the dashboard works unchanged from any
LAN device, and nginx and mosquitto are published from the same host. Pass `username`/`password`
from config, and `reconnectPeriod: 0` to DISABLE mqtt.js's own retry — this is the whole point:
its built-in retry is a fixed interval with neither growth nor jitter, so leaving it on would
both miss DASH-05's literal requirement and let every open tab retry in lockstep after a broker
restart. Keep `clean: true` (the default): retained-message delivery on SUBACK is independent of
the clean-session flag, and a persistent session per browser tab would only leave dead
session-table entries on the broker.

Hand-rolled backoff, exactly the formula RESEARCH.md Pattern 3 gives:
`delay = min(MAX_DELAY_MS, BASE_DELAY_MS * 2 ** attempt) * (0.5 + Math.random() * 0.5)` with
`BASE_DELAY_MS = 1000` and `MAX_DELAY_MS = 30000` as named constants. Increment `attempt` per
scheduled retry; reset it to 0 and clear the pending timer on `connect`. Drive retries from the
`close` event via `setTimeout(() => client.reconnect(), delay)`.

Attach all five listeners in this one module and nowhere else: `connect` (reset attempt,
subscribe, report `"connected"`), `close` (schedule the retry, report `"reconnecting"` with the
computed delay so the indicator can count down), `offline` (report `"disconnected"`), `error`
(log and never rethrow — an unhandled `error` event can abort the rest of page initialization and
leave a blank page whose only visible symptom is silence, which is the classic first-deploy
misdiagnosis), and `message` (hand `(topic, payload)` straight to `store.handleMessage` and do no
parsing here).

On `connect`, subscribe to exactly these five filters: `lan/devices/+/status`,
`lan/devices/+/history`, `lan/devices/topology`, `lan/events/recent`, `lan/poller/status`.
Subscribing is what triggers the broker's retained-message replay, so no cache-warming request
of any kind is needed or permitted.

Report `"connecting"` immediately at `connect()` time so the indicator's initial state is honest
rather than implied. Expose the current phase and pending delay through `onStatus` handlers only;
this module must not touch the DOM.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| broker → browser | Retained payloads of unverified shape enter the store |
| browser → broker | The WS connection authenticates as the read-only `wsreader` user |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-11-12 | Denial of Service | reconnect loop | mitigate | Delay is capped at `MAX_DELAY_MS` (30s) and jittered by a 0.5-1.0 factor, so neither an unbounded wait nor a synchronized reconnect storm across open tabs is possible after a broker restart |
| T-11-13 | Tampering | malformed/forged retained payload | mitigate | `JSON.parse` in try/catch plus a shape check before storing; a forged payload can at worst be dropped or stored as data — it is never executed, and no render module uses innerHTML on it (enforced in plans 11-06/07/08) |
| T-11-14 | Denial of Service | unhandled `error` event | mitigate | The `error` listener is attached unconditionally, so a wrong credential or unresolvable host surfaces as a visible disconnected indicator rather than an exception that aborts page init |
| T-11-15 | Elevation of Privilege | topic subscription | mitigate | Only the five fixed filters above are subscribed; no user-supplied string is interpolated into a subscribe call in this module (the `?id=` param is used for store lookup only, in plan 11-08) |
| T-11-SC | Tampering | npm/pip/cargo installs | mitigate | No installs — mqtt.js was vendored and audited in plan 11-02 |
</threat_model>
