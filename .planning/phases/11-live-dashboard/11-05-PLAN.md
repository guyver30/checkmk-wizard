<objective>
Build the dashboard's two infrastructure modules: the MQTT-over-WebSockets connection with a
hand-rolled jittered exponential backoff (DASH-05), and the state store that routes every
incoming topic into exactly one slot.

Purpose: RESEARCH.md's central finding is that mqtt.js's `reconnectPeriod` is a fixed interval
with no growth and no jitter, so DASH-05 cannot be satisfied by passing an option — it needs a
backoff wrapper around the connect lifecycle. And Pattern 1's wholesale-replace merge is what
keeps a long-lived kiosk tab from leaking memory, because the poller already ships complete
bounded arrays.

Output: two modules with no DOM knowledge whatsoever. Render modules subscribe to them via
callbacks; they never reach into the DOM and never import a render module.
</objective>

Connection setup:

  host as runtime-derived so the dashboard works unchanged from any LAN device: nginx and
  mosquitto are published from the same host. Do not read the host from `config.js`.

- Pass `reconnectPeriod: 0`. This is the load-bearing option: it disables mqtt.js's own
  fixed-interval retry entirely. Add a comment citing the reason — mqtt.js's `reconnectPeriod`
  is a fixed interval with neither exponential growth nor jitter (confirmed against the
  mqtt.js README and the still-open upstream issue mqttjs/MQTT.js#561), so DASH-05's jittered
  exponential backoff has to live here. A future reader must not "simplify" this back to a
  config option.
- Pass `connectTimeout: 30000` explicitly for clarity even though it is the library default.
- Leave `clean` at its default `true`. Add a comment stating why: retained-message delivery on
  subscribe is a broker guarantee entirely independent of the clean-session flag, and every
  page load is a fresh random client identity, so a persistent session would only leave an
  unused session-table entry per browser tab (RESEARCH.md Pitfall 2).

Backoff:
- Implement `delay = Math.min(RECONNECT_MAX_DELAY_MS, RECONNECT_BASE_DELAY_MS * 2 ** attempt)`
  multiplied by a jitter factor of `0.5 + Math.random() * 0.5`, then increment `attempt`.
  Reset `attempt` to 0 and clear any pending timer on a successful `connect`.
- Drive reconnection from the `close` event via `setTimeout(() => client.reconnect(), delay)`.
- Never let two timers run concurrently: clear the pending timer before scheduling a new one,
  and clear it in `stop()`.
- The jitter is what prevents a synchronized reconnect storm when several kiosk tabs all
  observe the same broker restart; say so in a comment so the multiplier is not removed as
  noise.

Events, all attached here and nowhere else — this module is the single choke point for the
connection, exactly as `_livestatus_request()` and `_publish_json()` are in the poller:
- `connect`: reset attempt, clear timer, report `"connected"`, then subscribe to all five
  topic patterns from the interfaces block in one `client.subscribe([...])` call. Subscribing
  inside `connect` rather than once after construction is required: a reconnect must re-issue
  the subscriptions, and it is the SUBACK that triggers the broker's retained-message replay.
- `message`: forward `(topic, payloadBuffer)` straight to the `onMessage` callback with no
  parsing. Parsing and routing belong to the store.
- `close`: report `"reconnecting"` with the computed `delayMs`, then schedule the retry.
- `offline`: report `"offline"`.
- `error`: ALWAYS attached, even if it only logs to the console. An unhandled `error` event
  inherits EventEmitter semantics and surfaces in the browser as an uncaught exception that can
  silently abort the rest of shell initialization — producing a blank page with no visible
  reason, the classic misdiagnosis of a wrong WS credential as "the broker is unreachable"
  (RESEARCH.md Pitfall 3). Comment it as deliberate so it is never trimmed.

Report `"connecting"` synchronously before `mqtt.connect()` returns, so the indicator shows
the locked `Connecting…` label from the first frame rather than an empty widget.

This module must contain no DOM access at all: no `document`, no `querySelector`, no
`innerHTML`. It reports state through `onConnectionState` and lets `render-shell.js` (plan
11-07) own the widget. It must also not import or reference the store — `shell.js` wires the
two together.

Create `dashboard/js/state-store.js` as a plain page-scope script exposing the `Store` API from
this plan's interfaces block.

Slots and merge rule — one slot per topic, always a wholesale replace, never an append:
- `lan/devices/{id}/status` sets `Store.devices` for that id; fires the `device` subscriber
  with the hostname.
- `lan/devices/topology` replaces `Store.topology` as a whole object; rebuilds the group index;
  fires `topology`.
- `lan/devices/{id}/history` replaces that id's whole array; fires `history` with the hostname.
- `lan/events/recent` replaces `Store.events` as a whole array; fires `events`.
- `lan/poller/status` replaces `Store.pollerStatus`; fires `pollerStatus`.
Appending client-side is forbidden: the poller publishes the complete bounded array every time
it changes (20 history entries, 50 events), so appending would double-bound incorrectly and
leak memory on a long-lived kiosk tab. Add a comment saying so and pointing at
`scripts/mqtt_poller.py`'s `append_bounded()` as the place where bounding actually happens.

Tombstones: a zero-length payload on a status or history topic is MQTT's defined "clear this
retained topic" semantic, published by the poller's `publish_tombstone()` when a host is deleted
from Checkmk. Delete that id from `Store.devices` and `Store.history`, drop it from the group
index, and fire `deviceRemoved` with the hostname. Do not treat it as a malformed payload.

Defensive parsing, mirroring `query_devices()`'s per-field guards and
`_normalise_restored_node()`'s defensive-get discipline:
- Wrap `JSON.parse` in try/catch. On a parse failure, return immediately and keep the
  last-known-good value for that slot. No user-facing error and no toast: UI-SPEC's Copywriting
  Contract deliberately specifies no string for this case, matching the poller's own tolerance.
- Reject a payload whose type does not match its topic's contract: status and topology and
  pollerStatus must be non-null objects and not arrays; history and events must be arrays.
  A type mismatch is discarded like a parse failure.
- Guard against an oversized payload before parsing: if the raw buffer length exceeds a sane
  ceiling (define it as a named constant in this file, sized generously against the real
  contract — 50 events and 20 history entries are the largest legitimate payloads), discard it
  and log once. An unbounded `JSON.parse` of a forged megabyte payload is a live hang risk on
  a kiosk tab, and the broker's 1883 listener is LAN-published.
- Tolerate a payload from an older poller build that lacks `staleness` or `host_state_raw`:
  never assume either key exists. Consumers read them through the helpers in plan 11-06, which
  handle absence, so the store must not synthesize defaults that would hide the absence.
- Ignore a device id containing `+`, `#` or `/`. The poller's `is_publishable_device_id()`
  already rejects those at publish time, so such a topic segment can only arrive from a forged
  publish; discarding it here costs nothing and keeps a crafted id out of the store that render
  modules and URL builders read from.

Group index (RESEARCH.md Pitfall 5): maintain `Map<groupLabel, Set<hostname>>` for both grouping
modes, rebuilt from the topology payload — topology is the only topic carrying `folder` and
`device_type` for the whole fleet. `Store.groupIndex(mode)` returns the index for
`"device_type"` or `"folder"`. Without this, recomputing "which hosts are in group X" on every
single status message is an O(fleet) scan per update; with it, a group roll-up is O(group size).
It is harmless at 21 hosts and is built now because Phases 12 and 13 grow both the fleet and the
update rate against this same store. Handle a host present in `devices` but absent from
`topology` (a status message that arrived before the topology message) by falling back to that
device payload's own `folder` / `device_type` values rather than dropping the host.

Subscriber mechanism: a small `Map<eventName, Array<fn>>` with `Store.subscribe(name, fn)` and
an internal emit. Wrap each subscriber call in its own try/catch so one throwing render module
cannot stop the others from updating — the same blast-radius reasoning the poller applies when
it swallows a single publish failure rather than aborting a cycle.

This module must contain no DOM access: no `document`, no `innerHTML`, no `querySelector`. It
must not reference `MqttConnection` either; `shell.js` passes `Store.handleMessage` in as the
`onMessage` callback.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| broker to browser | Every retained payload is untrusted input from the browser's perspective; the dashboard cannot verify who published it |
| LAN publisher to broker's 1883 listener | 1883 is LAN-published and requires `poller` credentials; a rogue publisher holding those credentials could forge any `lan/#` payload |
| browser to broker over WS | `wsreader` credentials are readable from `config.js`; read-only by ACL |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-11-14 | Denial of Service | state-store.js JSON.parse | mitigate | A named maximum-payload-bytes constant is checked against the raw buffer length before `JSON.parse` runs, so a forged oversized retained payload cannot hang the tab. `JSON.parse` itself is wrapped in try/catch and a failure keeps the last-known-good slot value |
| T-11-15 | Denial of Service | reconnect loop | mitigate | Backoff is exponential and capped at `RECONNECT_MAX_DELAY_MS`, with a 0.5-to-1.0 random jitter multiplier, so neither a single tab nor several kiosk tabs observing the same broker restart can hammer mosquitto in lockstep. Exactly one pending timer can exist at a time |
| T-11-16 | Tampering | forged device id in a topic segment | mitigate | The store rejects any id containing `+`, `#` or `/` before writing it to a slot. The poller's own `is_publishable_device_id()` already rejects these at publish time, so any such id is necessarily forged; discarding it keeps a crafted id out of the data that render modules and URL builders later read |
| T-11-17 | Tampering | unhandled mqtt error event | mitigate | `client.on('error', ...)` is always attached and commented as deliberate. Without it, a wrong credential or unresolvable host surfaces as an uncaught exception that aborts shell initialization and renders a blank page with no diagnosable cause |

| T-11-SC | Tampering | npm/pip/cargo installs | mitigate | No package installs. `mqtt.js` 5.15.2 was vendored, hash-recorded and legitimacy-audited (`slopcheck` verdict `[OK]`) in plan 11-02; this plan only calls into it |
