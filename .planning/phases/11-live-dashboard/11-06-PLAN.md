Create `dashboard/js/staleness.js` as a plain page-scope script exposing the four functions in
this plan's interfaces block. Every function is pure and takes an explicit `nowMs` defaulting to
`Date.now()`, so behavior is deterministic and inspectable rather than clock-dependent.

`isDeviceStale(devicePayload, nowMs)`:
- Prefer Checkmk's own value: when `devicePayload.staleness` is neither `null` nor `undefined`
  and is a finite number, return `staleness >= STALENESS_FACTOR`. Checkmk's staleness is already
  expressed in check-interval multiples, which is the same shape as its own "Staleness value to
  mark hosts / services stale" setting — that is precisely why D-12 stores the dashboard's
  threshold as a factor rather than as a number of seconds. Comment this, because comparing an
  interval-multiple against a seconds value would be a silent and very plausible bug.
- Otherwise fall back to timestamp age: return
  `(nowMs - Date.parse(devicePayload.timestamp)) / 1000 >= STALENESS_FACTOR * POLL_INTERVAL_SECONDS`.
  Comment that this path covers two real cases: a payload retained by a poller build from before
  D-17 landed, and a site where the `--check-columns` probe found `staleness` unavailable.
- Treat an unparseable or missing `timestamp` as stale, not as fresh. A reading whose age cannot
  be established must never be presented as live — that is the whole point of DASH-04.
- Return a boolean only. Do not return a state string; whether a stale device also carries a
  CRIT fill is the caller's composition (D-15), not this function's business.

`isPollerStale(pollerStatusPayload, nowMs)`:
- Return true when the payload is missing or null (nothing retained yet, or cleared).
- Return true when `status === "offline"` — that is the LWT or the graceful-stop value.
- Return false when `last_poll` is null: that is the birth message, published before the first
  cycle completed, and it is not yet evidence of staleness.
- Otherwise apply the same 3x factor to `last_poll`'s age. D-13 reuses the factor deliberately:
  the scope differs (one grey row versus every reading on screen being suspect) but the timing
  does not. Comment that this is what catches a stalled poll loop whose network thread keeps the
  TCP socket alive, which the LWT alone cannot detect — the reason `publish_poller_status()`
  refreshes `last_poll` every cycle at all.

`formatAge(fromIsoOrMs, nowMs)`: return a short human string for tooltips and for the
poller-offline banner's `{N} minutes old` slot. Accept either an ISO string or an epoch
milliseconds number. Handle an unparseable input by returning a clearly non-numeric marker such
as `unknown`, never `NaN minutes`.

`stalenessThresholdSeconds()`: return `STALENESS_FACTOR * POLL_INTERVAL_SECONDS`, so the tooltip
string `Last update {N} ago — exceeds the {threshold} staleness window.` can be built without
recomputing the arithmetic in a render module.

No DOM access, no MQTT access, no module-level mutable state. This module must not import
grouping.js: `grouping.js` depends on `staleness.js`, not the reverse, and the HTML loads
staleness.js first for exactly that reason.

Create `dashboard/js/grouping.js` as a plain page-scope script exposing the eight names in this
plan's interfaces block. All pure functions; no DOM, no MQTT, no mutable module state.

`SEVERITY_RANK` exactly as RESEARCH.md specifies:
`{ OK: 0, PEND: 0, WARN: 1, UNKNOWN: 2, CRIT: 3, UNREACH: 3, DOWN: 4 }`. Comment that this
mirrors the poller's own `compute_overall_state()` ordering, where a host-level DOWN or
UNREACHABLE always wins outright over any service state, and that the two tables live in
different languages and must be kept conceptually in sync by hand.

`effectiveState(devicePayload)`: return `"UNREACH"` when `host_state_raw === "UNREACH"`,
otherwise return `devicePayload.state`. This is the single place the UNREACH promotion happens,
and every render module must go through it. Comment the reason explicitly: the `state` field
structurally cannot contain `"UNREACH"` because `compute_overall_state()` collapses raw host
states 1 and 2 into `"DOWN"`, so a switch statement keyed on `state` alone would compile, run,
and silently never reach its UNREACH branch (RESEARCH.md Pitfall 6). Tolerate a payload lacking
`host_state_raw` entirely — an older poller build — by falling through to `state`.

`stateClass(stateString)`: map a state string to the matching CSS class from
`dashboard/css/dashboard.css`'s `.state-*` family, with a defined fallback for an unrecognized
value. Keep it a lookup table rather than string concatenation so an unexpected state value can
never produce a class name that does not exist in the stylesheet.

`displayName(devicePayload)`: return `alias` when it is a non-empty string after trimming,
otherwise return `id` (D-18). The wizard's Phase 4 and 10.1 alias prompts exist precisely so an
operator can give a host a human name; the hostname stays separately visible in the detail panel
and the device table's Host column, so this function is about the label, not about hiding the id.

`deviceTypeGlyph(deviceTypeString)`: look the value up in `DEVICE_TYPE_GLYPHS` and return its
`{ glyph, label }`. For an unrecognized value — a device type added to `device_types.json`
without a glyph being added to `config.js` — return the same neutral entry `other` uses rather
than an empty string, so no host ever renders with a missing icon slot. The `label` exists
because UI-SPEC's Accessibility section requires every emoji to carry a `title` and an
`aria-label` naming the thing in words; a bare unlabeled emoji is not acceptable.

`hasUnknownDeviceType(store)`: return true when any device's `device_type` is the literal
`"unknown"`. Per `extract_device_type()`'s own docstring, that value means the Checkmk
`device_type` tag group does not exist on the site at all — Phase 10 was never run there. It is a
site-configuration warning, never a device category beside `other`, and it is what drives D-16's
dismissible banner. Comment that distinction so a later reader does not add `unknown` to the
glyph table as though it were a real category.

`buildGroups(store, mode)`: return an ordered array of `{ label, hostIds }` using
`Store.groupIndex(mode)`, where `mode` is `"device_type"` or `"folder"` (D-05; default mode is
`device_type` and the toggle's persistence is render-shell.js's job, not this module's). Rules:
- When `mode` is `device_type` and `hasUnknownDeviceType(store)` is true, degrade every
  unknown-typed host into a single group labelled `untyped` rather than emitting one group per
  unknown value (D-16). Do not emit a group labelled `unknown`.
- When `mode` is `folder`, a host whose `folder` is the empty string — which happens when the
  poller's REST folder lookup never succeeded, a documented degradation — must still appear,
  under an explicitly labelled ungrouped bucket, never silently dropped.
- Order groups deterministically so the tree and the overview never reshuffle between renders
  on a live dashboard: sort by label, with `other` first when the mode is `device_type` to match
  `device_types.json`'s own guaranteed ordering.

`rollUpGroup(hostIds, store, nowMs)`: implement D-06 and D-15 together, following RESEARCH.md's
code example:
- Iterate only the ids passed in — never the whole `Store.devices` map. That is the entire point
  of the group index (Pitfall 5): a roll-up must be O(group size), not O(fleet).
- For each child, if `isDeviceStale(device, nowMs)` is true, set `hatched` and `continue` — a
  stale child contributes nothing to worst-of, because its last known value is not evidence about
  now.
- For every fresh child, rank `effectiveState(device)` through `SEVERITY_RANK` and keep the
  worst; count every non-OK fresh child toward `nonOkCount`.
- Return `{ worst, nonOkCount, total, hatched }`. `total` is the child count so the badge can
  render `N non-OK / total` per UI-SPEC.
- The combination is the point: a group with one CRIT and three stale children returns
  `worst: "CRIT"` AND `hatched: true`, which the CSS renders as red-and-hatched — "something is
  broken AND we are partly blind", both facts preserved. Collapsing them into one visual loses
  information the operator needs. Comment this so a later simplification does not discard one
  half.
- A group whose every child is stale returns `worst: "OK"` with `hatched: true`. Comment that
  this is correct and deliberate: the group is not being asserted healthy, it is being asserted
  unknown, and the hatch is what carries that.

Do not add any localStorage access, any DOM access, or any reference to a render module. The
grouping-mode toggle's persistence lives in render-shell.js (plan 11-07).
  </action>
