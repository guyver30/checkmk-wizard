ViewModule contract — each render-*.js registers itself at load time:
  Shell.registerView(name, viewModule)
     name is one of "index" | "devices" | "details"
     viewModule is an object with:
       mount(mainEl, params)   called when this view becomes active; params carries
                               { id } for the details view, taken from the query string
       unmount()               called before another view mounts; must remove any listener
                               the view attached to a DOM node it did not create
       onStoreChange(event, arg)  called for every store event while this view is active;
                               event is one of the six store subscriber names, arg is the
                               hostname where the store supplies one
     A view whose module is not registered is simply not rendered; the shell must not throw.

Shell navigation helpers the views call instead of touching location directly:
  Shell.openDevice(hostId)      swap to the details view in place and pushState
  Shell.navigate(viewName)      swap to index or devices in place and pushState

Create `dashboard/js/render-shell.js` as a plain page-scope script that owns every element of
the persistent chrome. It renders into the ids plan 11-03 created and never creates or replaces
any of those container elements themselves.

Connection indicator (DASH-05): expose a function `shell.js` passes as `onConnectionState`. Map
the four connection states to UI-SPEC's exact locked labels and dot colors:
`connecting` renders `Connecting…` with the muted dot; `connected` renders `Connected` green;
`reconnecting` renders `Reconnecting in {N}s…` amber, where N counts down from the `delayMs` the
connection module supplies; `offline` renders `Disconnected — retrying` red. Always set the dot
and the text together — a dot-only indicator violates UI-SPEC's rule that color is never the
sole signal. Drive the countdown with a single interval timer that is cleared on every state
change, so repeated close events cannot accumulate timers.

Poller-offline banner (D-13, D-14): re-evaluate `isPollerStale(Store.pollerStatus)` on every
`pollerStatus` store event and also on a periodic tick, because the condition becomes true by
the passage of time rather than by an arriving message — a poller that simply stopped publishing
sends nothing to react to. When true, unhide `poller-banner` and fill it with the locked template
`Poller offline since {HH:MM} — data is {N} minutes old`, using `Store.pollerStatus.last_poll`
(or `since` when `last_poll` is null) for the time and `formatAge` for the age. Simultaneously
apply the `is-stale` class to every rendered row and tile so nothing on screen can be mistaken
for live, while leaving the last known values legible — the operator may well be looking at the
dashboard precisely because something broke. There is no dismiss button: this is a live fact, not
a notice. Clear the banner and the global hatch when the condition clears.

Tag-group banner (D-16): when `hasUnknownDeviceType(Store)` is true, unhide `tag-group-banner`
with its locked string already present in the markup. Wire its dismiss button to hide it for the
rest of the page's life. Do not persist the dismissal — there is no backend, and UI-SPEC
explicitly accepts that it reappears on the next page load.

Grouping toggle (D-05): read the mode from `localStorage` at startup, defaulting to
`device_type`, and write it back on change. Validate the stored value against the two allowed
strings and fall back to the default for anything else, so a corrupted or hand-edited
localStorage entry cannot break the tree. Changing the mode must re-render both the tree and the
currently mounted view, because D-05 requires the sidebar and the overview to never disagree
about how the fleet is grouped — fire the view's `onStoreChange` with the `topology` event to
achieve that rather than reaching into the view's internals.

Sidebar tree (DASH-06, D-06, D-07, D-10): build it from `buildGroups(Store, mode)`. Each group
row shows its label, a fill from `stateClass(rollUp.worst)`, the `is-stale` class when
`rollUp.hatched`, and a count badge rendering `nonOkCount` against `total`. Each host row shows
`displayName(device)`, the `stateClass(effectiveState(device))` fill, the `is-stale` class when
`isDeviceStale(device)`, and — when the effective state is `DOWN` — the `⛔` glyph prepended to
the label (D-10). When the mode is `folder`, each host row also carries its `deviceTypeGlyph`
icon; when the mode is `device_type`, the host's folder is not shown at all, because the group
already carries the only classification that matters in that mode (D-07). Every glyph element
gets both a `title` and an `aria-label` from the glyph entry's `label`, and `role="img"` — an
unlabeled emoji leaves a screen reader with nothing.

Update the tree in place, never by rebuilding it wholesale on each message. A `device` store
event must repaint that one host's row and recompute only its own group's roll-up — that is what
DASH-01's and DASH-02's "merge in place rather than re-rendering" require, and it is why the
store maintains a group index. A full tree rebuild is correct only on a `topology` event or a
grouping-mode change, which are structural changes rather than streaming updates. Key host rows
by a `data-id` attribute so a single row can be found and replaced.

Event-history panel: render `Store.events` newest-first on every `events` store event, using
UI-SPEC's resolved row format — an event icon, the timestamp in the mono font, the host's display
name, and the transition rendered as old-arrow-new. Replace the panel's children wholesale here:
the poller already sends the complete bounded array of at most 50 entries, so a wholesale replace
of a 50-row list is cheap and is the only correct merge for a topic that ships a full snapshot.
Preserve the panel's scroll position across that replace, because this panel is read during an
incident and must not jump. Render the locked empty-state string
`No events yet — state changes will appear here as they happen.` when the array is empty.

Sidebar toggle: wire `sidebar-toggle` to toggle the `is-open` class on the sidebar, which the
single 900px media query in `dashboard.css` acts on. Nothing more — anything beyond "not broken"
below 900px is DASH2-01, deferred to v2.

Host-row clicks call `Shell.openDevice(hostId)`. This module must not touch `location`,
`history` or the main area directly; navigation is the shell's job.

Every string that originated in Checkmk — a hostname, an alias, a folder label, an event field —
must reach the DOM through `textContent` or `document.createTextNode`, never through `innerHTML`
string interpolation. Build elements with `createElement` and `replaceChildren`. An operator can
type anything into a Checkmk alias, and a rogue LAN publisher holding the poller's 1883
credentials could forge any payload field, so this is the one mitigation standing between a
forged payload and script execution in the operator's browser. Do not add a hand-rolled escaping
helper as an alternative: `textContent` is the mitigation.

Create `dashboard/js/shell.js` as the page's single entry point, exposing the `Shell` API from
this plan's interfaces block. It composes modules and routes; it contains no rendering code and
no business logic, mirroring how `wizard.py`'s `run()` composes every module without absorbing
their responsibilities.

Startup sequence, run once on DOM ready:
1. Initialise the shell chrome through `render-shell.js` (indicator set to `connecting`,
   grouping toggle restored from localStorage, both banners hidden, sidebar toggle wired).
2. Determine the active view from `location.pathname`'s filename: `index.html` or an empty path
   maps to `index`, `devices.html` to `devices`, `details.html` to `details`. Read the details
   view's target host from the query string with `URLSearchParams` (D-19).
3. Register store subscribers for all six event names. Each one forwards to `render-shell.js`'s
   corresponding handler and then to the active view's `onStoreChange`. Both must receive it: the
   tree and event panel always update, and the main area updates only if its view is mounted.
4. Mount the active view if a module registered under that name exists. If none did — which is
   the state after this plan and before plans 11-08 and 11-09 land — leave the main area's static
   empty-state markup in place and do not throw.
5. Start the connection last, passing `Store.handleMessage` as `onMessage` and
   `render-shell.js`'s indicator setter as `onConnectionState`. Starting last means the shell is
   already able to render before the first retained message arrives on SUBACK.

Routing (D-21, D-23):
- Intercept clicks on the three in-app nav links and on anything the views route through
  `Shell.openDevice` / `Shell.navigate`. Call `preventDefault`, `history.pushState` the new URL,
  unmount the outgoing view, mount the incoming one, and leave the topbar, tree and event panel
  untouched. Never assign to `location` and never reload: a reload would unmount the event-history
  panel and re-subscribe it, losing scroll position mid-incident — the exact failure D-23 exists
  to prevent.
- `Shell.openDevice(hostId)` pushes `details.html?id=` plus the URL-encoded host id and mounts
  the details view in place with `{ id: hostId }`. Use `encodeURIComponent` on the id.
- Handle `popstate` by re-deriving the view and params from the new URL and swapping again, so
  browser back and forward work across in-app navigation.
- Hold the nav links' real `href` attributes intact so each URL still loads cold and stays
  bookmarkable; interception is an enhancement over working HTML, not a replacement for it.

Query-parameter handling (D-19, defence in depth): before using the `?id=` value for anything,
reject any value containing `+`, `#` or `/`, or one longer than a sane hostname limit. The
poller's `is_publishable_device_id()` already guarantees no real device id contains those
characters, so such a value can only come from a crafted URL. The store is keyed by hostname and
this module never builds a subscription topic from the parameter, so the realistic impact is
low — but a URL is the most attacker-reachable input surface this page has, and an unknown id
must land on the locked empty state rather than anywhere else.

Expose `Shell.registerView(name, viewModule)` and `Shell.groupingMode()`. `registerView` must
tolerate being called before or after shell startup, because the render modules load before
`shell.js` in the HTML script order — collect registrations into a map and read that map at
mount time rather than assuming registration order.

Wrap each view lifecycle call (`mount`, `unmount`, `onStoreChange`) in try/catch and log a
failure without rethrowing. One broken view must not take down the tree and the event panel,
which are the operator's fallback view of the fleet — the same blast-radius reasoning the poller
applies when it warns on a single publish failure instead of aborting the cycle.

Do not write any DOM markup here beyond clearing and handing the main container to a view, do
not attach any listener to the raw mqtt client (the connection module owns those), and do not
parse any MQTT payload (the store owns that).

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Checkmk-sourced strings to the DOM | Hostnames, aliases, folder labels and event fields all cross from untrusted storage into rendered markup here for the first time in this phase |
| URL query string to application state | `details.html?id=` is the most attacker-reachable input surface on the page |
| localStorage to application state | A per-browser value an attacker with local access, or the operator, can hand-edit |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-11-24 | Elevation of Privilege | DOM-based XSS via an operator-set alias, a folder label, or a forged event field | mitigate | Every Checkmk-sourced string reaches the DOM through `textContent` or `createTextNode`, with elements built by `createElement` and `replaceChildren`. `innerHTML`, `outerHTML`, `insertAdjacentHTML` and `document.write` are absent, enforced by an acceptance criterion grepping for all four. The realistic attacker is a rogue LAN publisher holding the poller's 1883 credentials, which the read-only `wsreader` ACL does not prevent, so this is the sole control standing between a forged payload and script execution in the operator's browser |
| T-11-25 | Tampering | crafted `details.html?id=` value | mitigate | The id is rejected if it contains `+`, `#` or `/` or exceeds a hostname length limit, and it is `encodeURIComponent`-encoded on the way into any URL. The shell never builds an MQTT subscription topic from the parameter, so no wildcard escalation path exists; an unknown id resolves to the locked empty state |
| T-11-26 | Tampering | corrupted localStorage grouping mode | mitigate | The stored value is validated against the two allowed strings and falls back to the `device_type` default otherwise, so a hand-edited or corrupted entry cannot produce an undefined grouping mode or a broken tree |
| T-11-27 | Denial of Service | one broken view or subscriber taking down the page | mitigate | Every view lifecycle call is wrapped in try/catch and logs without rethrowing, and the store already isolates each subscriber. | T-11-SC | Tampering | npm/pip/cargo installs | mitigate | No package installs and no third-party code in either file |
