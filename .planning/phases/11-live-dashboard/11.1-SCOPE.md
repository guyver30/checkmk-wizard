# Phase 11.1 — Dashboard Layout and Light Palette

**Status:** scoped, not planned. Operator-directed after reviewing a running preview
of the Phase 11 build on 2026-09-16.

**Scope fence:** layout and palette ONLY. Every data-platform and "wow" capability
discussed in the same session (service-impact framing, root-cause collapse, kiosk
mode, MinIO rollups, a time-series database, Grafana, failure prediction, AI
narration) is explicitly OUT of this phase — see `.planning/ROADMAP.md` Phase 14.

---

## Why this phase exists

Phase 11 shipped against a UI contract that the operator rejected on sight once it
was running. The contract was not wrong when written; it was written against
reference mockups (`docs/DMC-networkmap.png`, `docs/DMC-server.png`) whose dark,
split-sidebar layout the operator does not want for a KONE-branded product. Rather
than patch the shipped build, Phase 11 was allowed to close against its own
requirements and this phase carries the redesign with its decisions revised
properly.

## Decisions this phase must REVISE

These are locked Phase 11 decisions that the new layout contradicts. They must be
formally superseded in `11-CONTEXT.md`, not silently ignored.

| Decision | Currently says | Must become |
|---|---|---|
| **D-22** | Layout is "dark, dense, panel-based"; left column split vertically, tree on top and event panel beneath | Light/white; left column is ALL tree, full height; the event panel moves to the bottom of the centre |
| **D-24** | `index.html` is the stats-by-state strip plus a grouped fleet overview | The centre's default view; the stats strip / overview / map question is settled here |
| **D-11** | Fixes the MEANING of each state colour (not its value) | Unchanged in meaning; the light palette re-derives the values |

## Requirement affected

**DASH-01** currently reads: *"`index.html` shows an at-a-glance stats strip (counts
by state) above a grouped fleet overview, merging incoming updates in place."*

Moving the event history into the centre and making the map the default overview
changes what the centre shows by default. DASH-01 must be re-scoped or re-worded
before this phase is planned — it cannot simply be left unmet.

## Scope

### 1. KONE light palette

Replace the dark palette with the light one. A complete, contrast-audited palette
already exists as a preview override; it should be lifted into `dashboard.css`
rather than re-derived.

Sourcing rule: every value comes from KONE's own
`web_assets/kone-design-system-main/packages/kone-ds-tokens/input/design-tokens.json`,
which ships an explicit light set with semantic names (`bg primary`,
`bg blue secondary`, `border`, `text`, `inactive`, `disabled`) plus an
`l80..base..d80` ramp per hue. KONE marks `bg green/orange/red` as **"(don't use)"** —
those are avoided.

Two measured facts drove the structure and must survive into the plan:

1. KONE's BASE greens/oranges/yellow are unusable as text on white — green.base
   2.00:1, orange.base 2.04:1, yellow 1.30:1. Anything rendering a state as text or
   an icon must use a d-shade.
2. On a solid state fill, ink (`#141414`) beats white on every KONE hue (green 9.23
   vs 2.00, yellow 14.12 vs 1.30). The dark theme's "white text on every fill" rule
   **inverts**.

Structural decision that keeps this cheap: `--state-*` keeps the SATURATED value in
both palettes, because three places read it directly as a MARK — the connection dot
(set inline by `render-shell.js`), the Phase 12 gauge arcs, and the topology map's
nodes. The pale behind-text tint goes into a NEW `--state-*-fill` token, and only the
seven `.state-*` background rules re-point at it. **Net effect: a light theme with
zero JavaScript changes.**

Also required, all found while building the preview:
- `.is-stale` is a white 6%-alpha hatch, invisible on pale fills — needs dark ink.
  Must stay `background-image` only (D-15 composability).
- `.brand-logo` sits on a white chip for contrast against navy; on a white page that
  chip is invisible padding.
- Panels using `--color-surface-raised` become white-on-white and need a border.

**Acceptance:** every text/background pair ≥ 4.5:1 and every non-text mark ≥ 3.0:1,
demonstrated by a computed audit, not by eye. The preview's audit covers 20 pairs
and all pass; re-run it against the final stylesheet.

### 2. Three-pane layout

- **Left:** tree only, full height (today it is split 58/42 with the event panel).
- **Centre top:** map by default; a device's details when one is selected.
- **Centre bottom:** event history, always visible.

`#sidebar-events` moves out of the sidebar. The centre becomes a two-row grid.

**Implementation note from the preview:** wrapping `#main` in a new grid cell rather
than nesting inside it lets `shell.js`'s `getElementById("main")` and every view
module's `ensureContainer()` keep working unchanged.

### 3. Panes resizable and collapsible

All three panes (left tree, centre top, centre bottom) must be **resizable** by the
operator and **collapsible**. Not yet designed.

Open questions for the discussion pass:
- Does pane size persist across reload? If so it must follow the guarded-storage
  precedent already established in `render-shell.js` `groupingMode()` — storage
  reads can THROW, and an in-memory value must be the source of truth for the
  session or the interaction silently fails when a write is refused.
- Keyboard operability: the dashboard now has a keyboard-activation precedent
  (`shell.js` `handleKeydown`, Enter/Space via `navigateTo`). Drag handles need a
  keyboard equivalent or they are a WCAG 2.1.1 failure.
- Does collapsing a pane change what the remaining panes show, or only their size?

### 4. Grouping control becomes a combo + severity checkbox

Replace the current two-state "Group by type" toggle button with:

- a **select** offering `Group by type` / `Group by folder` (extensible — the
  operator explicitly anticipates more filters later, so this must not be
  hard-coded to two options), and
- a **checkbox: "Order by severity"** — when checked, devices and groups with the
  most severe hosts sort to the top.

Notes:
- `grouping.js` already provides `SEVERITY_RANK`, `effectiveState` and
  `rollUpGroup`, so the ordering primitive exists.
- The current toggle stores its state via `localStorage` behind a guarded read plus
  an in-memory override (`groupingModeOverride`). The combo and checkbox must follow
  the same pattern; see the Phase 11 fix that established it.
- `renderTree()` rebuilds on every store change, so sort order must be derived on
  each rebuild, not held in the DOM — the same trap the tree-collapse work hit.
- The tree's collapse state (`collapsedGroupKeys`) must survive a re-sort.

### 5. Event history ordering — VERIFY, do not "fix"

The operator reported oldest-events-on-top. **The shipped code is correct** —
`renderEvents()` reverses because `mqtt_poller.py` appends chronologically
(`state.events + events_this_cycle`), and the function carries a comment saying so.
The fault was in the preview harness's synthetic feed, which reversed the array
before publishing and cancelled the display reversal out.

**Action for this phase: confirm newest-first against the LIVE poller, and add a
regression test for the ordering contract.** Do not reverse the render again.

### 6. Already done in Phase 11 — do not redo

- The `Details` nav link is removed (`7537910`); `details.html` itself remains a
  real, bookmarkable, cold-loadable page per D-19/D-21.
- Tree groups already expand/collapse with keyboard support.
- Four shipping defects found by operator screenshots are fixed: the dead `.topbar`
  selector, `[hidden]` losing to ID specificity, the wiped `ViewModules` registry,
  and the entirely unstyled nav.

## Added 2026-09-16 after live verification

Live verification against the real Checkmk site found four more defects, all
fixed in Phase 11 (they were functional, not stylistic). Two leave follow-on work
for this phase:

### 7. Stale flips should toggle classes, not rebuild structure

A page-wide clock now re-renders time-derived surfaces every 12s, because nothing
re-rendered when the poller stopped publishing — the one moment staleness matters
is the one moment guaranteed to produce no new message.

But `renderTree()` and both view modules respond to a poller-stale flip with a
FULL rebuild, each justified in-comment as "an infrequent event". The clock made
that premise false. Scroll position and focus are now preserved around `tick()` as
a contained fix, but the right design is for a stale flip to toggle `.is-stale` on
existing nodes rather than rebuild them. That touches all three modules' render
paths, which is why it belongs here rather than in a defect fix.

Also revisit `CLOCK_TICK_MS` (12s) once the panes are resizable — a taller tree
means more nodes rebuilt per tick.

### 8. Event rows must identify their device

Reported from a live screenshot: at 280px of sidebar, `.event-device-name`
truncates to `1...` for every host, because they are all `192.168.0.x` and the
distinguishing part is at the END. The row becomes unreadable exactly when it
matters.

Moving the event panel to the centre (item 2) widens it and largely fixes this by
accident. Do not rely on that — make it a requirement that an event row identifies
its device, whether by middle-truncation (`192.168…213`), preferring the alias, or
a tooltip.

### Deployment note, not a code change

`dashboard/js/config.js` still ships `CHECKMK_BASE_URL = "http://<HOST_IP>:8080"`
on the live deployment. The "View in Checkmk" link correctly disables itself while
that placeholder is present (D-20), so it will look broken until an operator edits
it. Worth surfacing in the deployment doc more prominently than it currently is.

## Operator decisions, 2026-09-16 (settle these before planning)

### D-25 — the centre's default view is the stats strip ABOVE the map

Operator-chosen over "map only" and "stats + cards with the map behind a toggle".

The counts (`17 OK · 0 WARN · 3 DOWN · 0 STALE`) stay as a thin strip; the map
fills the space beneath them. Both the at-a-glance numbers and the topology are
visible without a control.

**Consequence for DASH-01, and it is a good one:** the requirement reads
*"`index.html` shows an at-a-glance stats strip (counts by state) above a grouped
fleet overview, merging incoming updates in place rather than re-rendering from
scratch"*. Under this decision only the words *"grouped fleet overview"* become
*"topology map"* — the stats strip, the "above", and the merge-in-place clause all
survive verbatim. **DASH-01 is re-worded, not re-scoped**, and the merge-in-place
half is unaffected.

The grouped fleet overview (`render-index.js`'s cards/chips) is therefore
superseded as the default centre view. Decide during planning whether that code is
deleted or kept reachable — D-24 reserved this slot for the map from the start, so
deletion is the straightforward reading.

### D-26 — panes get drag handles AND collapse buttons

Operator-chosen over collapse-only and over drag-without-persistence.

- **Splitter bars** between the panes, draggable.
- **A collapse control** (chevron) on each pane.
- **Keyboard equivalent is mandatory, not optional.** A focused splitter must
  resize with arrow keys, and the collapse control must be a real button. Without
  this it is a WCAG 2.1.1 failure, and it would undo the keyboard work already done
  this phase (`shell.js` `handleKeydown`).
- Give each splitter `role="separator"` with `aria-orientation` and
  `aria-valuenow`, so assistive technology reports the pane size rather than an
  unlabelled div.

**Persistence:** the operator chose the option that remembers sizes. That makes the
guarded-storage precedent mandatory, not advisory — `localStorage` access THROWS
(not returns null) when site data is blocked, which already took down the whole
shell once this phase (`groupingMode()`). The rule established there applies
unchanged: an in-memory value is the source of truth for the session, storage is
only how it survives a reload, and a refused write must never break the
interaction.

**Interaction with the clock:** `tick()` currently preserves scroll and focus for
`#sidebar-tree`, `#sidebar-events` and `#main`. Resizable panes change which
elements scroll, so that list must be revisited, and a resize must not be undone by
the next tick.
