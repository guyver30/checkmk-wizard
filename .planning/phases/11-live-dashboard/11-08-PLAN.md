Columns, exactly UI-SPEC's resolved set, rendered into the existing `thead` structure:

- Type: the `deviceTypeGlyph` icon plus its label text, with `title`, `aria-label` and

- Location: the folder-derived label, rendered only when `Shell.groupingMode()` is `folder`. When
  the mode is `device_type`, hide the column entirely — both its header cell and every body
  cell — extending D-07's tree and overview rule to the table so all three surfaces agree.
- Last Update: a relative time in the mono font, derived through `formatAge` from the payload's
  `timestamp`.
- Flags: small labelled badges for `in_downtime` and `acknowledged`. Labelled, not icon-only, and
  not sortable — the header cell deliberately has no `data-key`.

Sorting:
- Default sort is state severity worst-first, with host ascending as the secondary key. Rank
  states through `SEVERITY_RANK` — never alphabetically by the state string, which would put CRIT
  before OK before WARN and be meaningless. Worst-first is the operationally useful default for a
  live ops table: it surfaces problems immediately instead of alphabetical noise.
- Wire one click handler per `th[data-key]`. A click on the already-active key flips the
  direction; a click on a new key selects it with the default direction for that key. Maintain the
  `aria-sort` attribute on every sortable header — `ascending`, `descending`, or `none` — so the
  sort state is exposed to assistive technology and not carried by the accent arrow alone.
- Make the header cells keyboard operable: a click handler alone is not reachable by keyboard, and
  UI-SPEC requires native tab order to remain intact. Handle Enter and Space on a focused header.

The per-message versus per-sort split is the substance of DASH-02 and must be implemented exactly
as RESEARCH.md Pattern 2 describes:
- `device` store event: rebuild that one row and replace it in place, found by `data-id`. Do not
  re-sort and do not rebuild the body — a streaming update must not make rows jump under the
  operator's cursor. Handle the case of a device not yet in the table by falling back to a full
  rebuild, since a new host needs a sort position anyway.
- `deviceRemoved`: remove that one row.
- `topology` event, a grouping-mode change, or a user sort click: rebuild the whole body with
  `replaceChildren`. A full rebuild of about 21 rows is trivial and is correct here because these
  are structural changes or explicit user actions, not streaming events.
- Use `CSS.escape` when selecting a row by its `data-id` value, since a hostname is
  externally sourced and goes into a selector string.

Row clicks call `Shell.openDevice(hostId)` so the detail panel swaps into the main area in place
and the event panel stays mounted (D-23). Rows must be keyboard activatable too.

This view must not render the recent-events panel. UI-SPEC places that panel in the persistent
sidebar as a shell fixture rendered identically on all three pages, which is what satisfies both
DASH-02's "recent-events panel" wording and D-22's "always on screen" framing. Re-rendering it
here would duplicate `render-shell.js` and fight it for the same DOM.

Show the locked empty-state copy while `Store.devices` is empty, matching index.html's wording
because topology absence is the shared root cause.

Every Checkmk-sourced string enters the DOM through `textContent` only.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Checkmk-sourced strings to the DOM | Hostnames, aliases, folder-derived group labels and device-type values are all rendered into tiles, chips and table cells here |
| hostname to a CSS selector string | A row is located by its `data-id`, whose value is externally sourced |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-11-30 | Elevation of Privilege | DOM-based XSS via an alias, a folder label or a device-type value | mitigate | Every dynamic string is set with `textContent` on elements built by `createElement`; `innerHTML`, `outerHTML` and `insertAdjacentHTML` are absent from both files, enforced by acceptance criteria. This is the V5 input-validation control RESEARCH.md's Security Domain identifies for a page rendering operator-typed and potentially forged values |
| T-11-31 | Tampering | selector injection through a hostname | mitigate | `CSS.escape` wraps every `data-id` value used in a query selector, so a hostname containing selector metacharacters cannot alter which element is matched. The poller's `is_publishable_device_id()` already blocks the worst characters upstream; this is defence in depth |
| T-11-32 | Spoofing | a stale row reading as a live reading | mitigate | A stale row carries three independent signals: the `is-stale` hatch, the locked `(stale)` suffix on the state word, and a tooltip naming the age and the threshold. The stats strip additionally reports a separate stale count so a stale device is never silently tallied as OK |
| T-11-33 | Denial of Service | full re-render on every streaming message | mitigate | A `device` event patches exactly one chip or one row; a full rebuild is restricted to `topology` events, grouping-mode changes and user sort clicks. That bound is what keeps a long-lived kiosk tab responsive and is enforced by acceptance criteria on both files |
| T-11-34 | Repudiation | misleading sort order hiding problems | mitigate | The default sort ranks through `SEVERITY_RANK` rather than the state string, so CRIT cannot sort between a non-problem and a lesser problem alphabetically. `aria-sort` exposes the active ordering so the operator can always tell what they are looking at |
| T-11-SC | Tampering | npm/pip/cargo installs | mitigate | No package installs and no third-party code in either file; the sortable table is deliberately hand-written rather than pulling a grid library, per RESEARCH.md's Alternatives Considered |
</threat_model>
