Extend `dashboard/js/render-details.js` with the history strip, rendered into `#history-strip`.

Render exactly `HISTORY_MAX_ENTRIES` (20) equal-width segments at 12px wide and 24px tall with a
2px gap, oldest on the left and newest on the right — the conventional uptime-monitor reading
order. Fill each segment from the corresponding entry's `to` state using `stateClass`. When the
host has fewer than 20 known entries, render the remaining slots as `--color-surface`
placeholders rather than omitting them, so the strip's total width is fixed and does not jump as
history accumulates. Give each filled segment a `title` of the form `HH:MM:SS — STATE`.

Read the array from `store.history.get(hostname)`, defaulting to an empty array. Never append to
it client-side: the poller publishes the full bounded array every time it changes, so an
append would double-bound incorrectly and leak memory on a long-lived kiosk tab.

Handle `update("history", hostname)` by rebuilding only the strip when the hostname matches the
mounted one — the strip is 20 small nodes, so a full strip rebuild is cheap and is not the
"re-render from scratch" DASH-01/02 prohibit (those govern the fleet-wide views).

`unmount()` must clear the strip and drop any references to the previously mounted hostname so a
subsequent mount for a different host cannot render the old host's history.
