# Phase 11.1 Plan 09: Grouping Controls and Severity Ordering Summary

**`buildTree()` gains an `orderBySeverity` derivation option (groups by descending worstRank/nonOkCount, devices by descending SEVERITY_RANK, both derived on every call) and a new guarded-storage `useGroupingPrefs` hook backs an extensible `GroupingControls` select+checkbox pair wired above the device tree, with expand state surviving both a re-sort and a mode switch.**

## Accomplishments

- `buildTree(devices, mode, nowMs, { orderBySeverity })` — with the option omitted or false, ordering is unchanged (alphabetical groups, alphabetical devices within a group). With `orderBySeverity: true`, groups sort by descending `worstRank`, then descending `nonOkCount`, then alphabetically; devices within each group sort by descending `SEVERITY_RANK[state]` (imported verbatim from `grouping.ts`, no second ranking table), then alphabetically. Both sorts run fresh on every call — there is no cached order anywhere in the module.
- `useGroupingPrefs()` returns `{ mode, orderBySeverity, setMode, setOrderBySeverity }`, persisted under `dashboard-react.grouping.v1` via `guardedStorage`, mirroring `usePaneLayout`'s lazy-init + per-field-independent-fallback + ignore-refused-write shape. A stored `mode` not in the known list falls back to `"type"` before it can ever reach `groupKeyFor` (T-11.1-12).
- `GroupingControls.tsx` renders `kone-design-system`'s `Select` (driven by an exported `GROUPING_OPTIONS: SelectOption[]` — "Group by type" / "Group by folder") and `Checkbox` ("Order by severity"). The component contains no literal `"type"`/`"folder"` comparison anywhere in its body — the select's `onChange` value flows straight through to `onModeChange` — so a third grouping mode is addable by appending one `GROUPING_OPTIONS` entry with no branching logic to touch.
- `IndexRoute.tsx` replaces the hardcoded `"type"` mode with `useGroupingPrefs()`, passes `{ orderBySeverity }` into `buildTree`, and renders `GroupingControls` above `Tree` inside the tree pane slot. A grouping-mode change prunes `openKeys` to the newly built tree's key set (computed directly in the mode-change handler, not via a `useEffect`); the severity-order checkbox never reaches that pruning code path at all, since it only ever calls `setOrderBySeverity` — proving expand state survives a re-sort structurally, not by coincidence.
- 20 new tests (13 in `treeModel.test.ts`, 7 in `useGroupingPrefs.test.ts`) plus 7 new tests in `GroupingControls.test.tsx` (driven through `IndexRoute`, per the plan's own instruction). Full suite grew from 125 to 144 passing tests, 0 failures.

## Decisions Made

- **`useGroupingPrefs.ts`'s known-mode list is declared locally, not imported from `GroupingControls.tsx`** — the plan's own frontmatter scopes `useGroupingPrefs.ts` to Task 1 exclusively and `GroupingControls.tsx` to Task 2 exclusively; Task 1's commit has to pass its own `<verify>` (a whole-project `tsc -b`) before `GroupingControls.tsx` exists, so a forward import would have broken Task 1's atomic-commit requirement. `KNOWN_MODES: readonly GroupingMode[] = ["type", "folder"]` still satisfies T-11.1-12's actual requirement (array-membership validation, not a hardcoded `=== "type" || === "folder"` chain) — it is a second, independent declaration of the same two-value set `GroupingMode`'s own type union already is, not a duplicated branching structure.
- **`GroupingControls` lives inside `ThreePaneLayout`'s existing `tree` slot content, not a new layout slot** — `ThreePaneLayout.tsx` itself is outside this plan's file list (D-31 reserves it for later plans to fill via props, not restructure), so the control is stacked in a `flex-col` above an inner `overflow-auto` `Tree` container within the slot content `IndexRoute` already owns.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Two GroupingControls tests used `getAllByRole` where zero matches is a valid outcome**
- **Found during:** Task 2, first test run after implementing `GroupingControls`/`IndexRoute` wiring
- **Issue:** `"switching grouping mode does not throw..."` and `"switches grouping mode twice..."` asserted no stale expanded row remains after a mode switch by calling `screen.getAllByRole("treeitem", { expanded: true })` and iterating the result. `getAllByRole` throws when it matches zero elements, and the pruning logic correctly left zero groups expanded in both scenarios (the previously-open group's key does not exist in the new tree) — so the throw was a test-authoring bug flagging correct implementation behavior as a failure, not an implementation defect.
- **Fix:** Changed both assertions to `screen.queryAllByRole`, which returns an empty array instead of throwing, so the `forEach` assertion (checking no stale key text appears) still runs correctly against zero or more results.
- **Files modified:** `dashboard-react/src/components/GroupingControls.test.tsx`
- **Verification:** `npm --prefix dashboard-react test -- src/components/GroupingControls` — 7/7 pass after the fix.
- **Committed in:** `f3d637d` (Task 2 commit) — fixed before the task's own commit.
