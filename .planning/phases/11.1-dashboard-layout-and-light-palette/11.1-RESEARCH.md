## Summary

This research replaces the prior vanilla-JS/CSS-audit research entirely. The operator's 2026-09-21
React pivot (D-40–D-46) keeps every product requirement from Phase 11.1's original scope (three-pane
resizable layout, KONE light palette, extensible grouping, event-ordering verification, two
carried-over defects) but changes the implementation technology to a React + TypeScript + Tailwind
SPA in a new `dashboard-react/` directory, built against the already-vendored `design-system/`
package (`kone-design-system`, committed at `9d29292`, confirmed tracked in git — the "git add it
before planning" action item in D-40 is already done).

The five research questions the operator posed all resolved to concrete, actionable answers:
(1) none of `Badge`/`Chip`/`Banner`/`Message` has a distinct "critical/down" variant separate from a
generic "danger"/"alert" semantic, and `Chip` has no status semantics at all — `Badge` (7 colors × 3
variants) is the only one of the four with enough color slots to cover all 5 device states without
inventing new tokens; (2) the SPA + nginx fallback is a one-line `try_files $uri $uri/ /index.html;`
addition; (2b) `design-system`'s own `USAGE.md` only claims end-to-end verification for the **packed
tarball** method, not the plain local-file-dependency method, which carries a real duplicate-React
risk via symlinks; (3) Zustand's default (non-`replace`) `set()` already gives exactly the
"wholesale-replace-a-named-slice" semantics the vanilla store implements, with no `replace: true`
needed; (4) `Accordion.tsx` is single-open (one `openId` string, not a Set) and has no depth/severity
awareness — it is a pattern to imitate, not a component to wrap, confirming D-45's framing; (5) the
splitter needs pointer events with ref-driven DOM mutation during drag and a single committed
`setState` on release, to avoid re-render thrash.

**Primary recommendation:** Build `dashboard-react/` as a Vite + React 19 + TypeScript SPA using
`react-router` v8 in Declarative Mode (import from `"react-router"`, not `"react-router-dom"`),
Zustand v5 for the MQTT-fed store (default merge semantics, no `replace:true`), consume
`kone-design-system` via a **packed tarball** (not local-file-dependency) to match the only
verified-working consumption path, and build the tree/splitter as new components that copy
`Accordion.tsx`'s markup pattern rather than wrap it. Pin `tailwindcss` to the `^3.4.x` line
(NOT the current default `^4.x`) to keep dashboard-react's own Tailwind config format compatible
with `design-system/tailwind.config.js`'s color-token mapping, which must be duplicated by hand
since the package's public `exports` map does not expose the config.

## D-44 Research Answer: State→Component Mapping

D-44 asked: do `Badge.tsx`, `Chip.tsx`, `Banner.tsx`, or `Message.tsx` expose a variant that
naturally maps to "critical/down" as distinct from a generic "error"? Read directly, here is
each component's actual variant surface (not assumed from the component name):

| Component | Actual status/color props | Distinct "critical/down" vs "error"? | Fit for 5 device states |
|-----------|---------------------------|----------------------------------------|---------------------------|
| `Badge` | `color`: `neutral \| black \| success \| warning \| danger \| info \| purple`; `variant`: `outline \| soft \| solid`; optional `icon` | **No** — only one negative-severity color (`danger`), used for both "error" and "critical" alike | **Best fit.** 7 colors is enough headroom to cover all 5 states without collision: `success`→OK, `warning`→WARN, `danger`→DOWN, and `neutral`/`black` (or `purple`) for STALE/UNKNOWN — see recommended mapping below |
| `Chip` (`FilterChip`, `SelectorChip`) | **No `color`/`status` prop of any kind** — `FilterChip` is a remove-a-filter pill, `SelectorChip` is a radio-style toggle (`selected: boolean` only) | N/A — not a status component at all | **Not usable as-is.** D-44 lists it as a candidate but its actual API has zero status semantics; would need net-new props to repurpose, at which point it is not meaningfully different from building a custom badge |
| `Banner` | `status`: `info \| success \| warning \| danger` (4 values) — full-width, dismissible, page-level alert bar | **No** — same 4-status set as `Message`, no distinct critical tier | **Wrong shape for per-device/per-row state.** Full-width alert bar, not a compact per-row marker. Reserve for page-level conditions (e.g. "poller offline" banner), not per-device state |
| `Message` | `status`: `info \| success \| warning \| danger` (4 values) — card with title/description/confirm/cancel buttons | **No** — same 4-status set as `Banner` | **Wrong shape.** A confirmation/notification card, not a compact status indicator. Not a per-device-state component |

**Answer: no component has a first-class "critical/down" variant distinct from generic
"danger"/"error."** `Badge` is the only one of the four with enough distinct color slots (7) to
represent 5 device states without reusing a color for two different meanings, and it accepts an
`icon` prop — recommended as a **second, non-color-only signal** for STALE vs UNKNOWN (which would
otherwise both have to share a muted/neutral color), consistent with not relying on color alone.

**Recommended mapping (color-only fit, no raw-token extension needed):**

| Device state | `Badge` `color` | Rationale |
|--------------|------------------|-----------|
| OK | `success` | Direct semantic match |
| WARN | `warning` | Direct semantic match |
| DOWN | `danger` | Closest available to "critical" — `danger`'s `solid` variant for maximum emphasis |
| STALE | `neutral` + icon (e.g. a clock glyph via the `icon` prop) | No dedicated "stale" semantic exists; `neutral` avoids implying a health judgment, and the icon disambiguates from UNKNOWN without inventing a new color |
| UNKNOWN | `black` (or `purple`) + icon (e.g. a question-mark glyph) | Distinguishes from STALE by both color and icon; avoids reusing `neutral` for two different meanings |

**Bonus finding — a strong incidental fit for DASH-05's connection indicator (not a device
state):** `Badge.tsx` also exports `StatusBadge`, with `status: connected | low-signal |
entrapment | unknown`, each pairing a colored dot with text. This maps almost directly onto the
MQTT connection-status indicator (`connected`→green dot, `low-signal`/`entrapment`→amber/red dot,
`unknown`→neutral dot) — worth using for DASH-05's connection indicator specifically, separate
from the 5-state device-status mapping above.

**Gap requiring the library's raw color tokens: none identified.** `Badge`'s 7 colors, used with
the icon-disambiguation above, cover all 5 states without needing to reach past the component API
into `--color-*`/`--neutral-*` custom properties. If a future phase needs more than 5 simultaneous
semantic states (unlikely for this milestone), `purple` is the one color left unused and the raw
tokens remain available as a documented fallback (see Pitfall 4).

### Pattern 1: MQTT-fed Zustand store with wholesale-replace semantics

**What:** One Zustand store slice per MQTT topic (`devices`, `topology`, `events`, `pollerStatus`),
each fully replaced (not deep-merged) whenever its topic publishes, mirroring
`dashboard/js/state-store.js`'s per-slot `Map.set()`/reassignment behavior.

**Why `set()`'s default (non-`replace`) behavior already does this correctly:** Zustand's `set()`
merges *shallowly at the top level only* — `set({ devices: newDevicesObject })` replaces the
`devices` key's value wholesale while leaving `topology`, `events`, `pollerStatus`, and all action
functions untouched. This is exactly the "wholesale replace of one slice" behavior D-46 asks for.
Passing `set(partial, true)` (the `replace` flag) would instead replace the **entire store**,
wiping out the other slices and every action function — the wrong tool here [VERIFIED: zustand
`create()`/`setState` semantics, cross-checked against pmndrs/zustand docs and GitHub search
results, 2026-09-21].

**Where the mqtt.js client lives relative to the store:** as a module-level singleton created once
outside any React component (`src/store/mqttClient.ts`), not inside a custom hook's `useEffect`.
This is deliberate, not just a style choice — see the StrictMode pitfall below.

```typescript
// src/store/useAppStore.ts
import { create } from "zustand";

interface AppState {
  devices: Record<string, DevicePayload>;
  topology: TopologyPayload | null;
  events: EventEntry[];
  pollerStatus: PollerStatusPayload | null;
  handleMessage: (topic: string, payload: Uint8Array) => void;
}

export const useAppStore = create<AppState>((set) => ({
  devices: {},
  topology: null,
  events: [],
  pollerStatus: null,
  handleMessage: (topic, payload) => {
    // port dashboard/js/state-store.js's handleMessage() topic-routing + parsePayload()
    // defensive-parsing logic here; each branch calls set({ devices: {...} }) etc.,
    // never set({...get(), devices: {...} }, true).
  },
}));
```

```typescript
// src/store/mqttClient.ts — module-level singleton, connects once at import time
import mqtt from "mqtt";
import { useAppStore } from "./useAppStore";

let client: ReturnType<typeof mqtt.connect> | null = null;

export function connect() {
  if (client) return; // guards StrictMode's double-invoke and any accidental re-call
  client = mqtt.connect(`ws://${location.hostname}:${WS_PORT}`, {
    username: WS_USERNAME,
    password: WS_PASSWORD,
    reconnectPeriod: 0, // ported: drive jittered backoff manually, same as dashboard/js/mqtt-connection.js
  });
  client.on("message", (topic, payload) => useAppStore.getState().handleMessage(topic, payload));
  // ...connect/close/offline/error handlers port unchanged from mqtt-connection.js
}
```

### Pattern 2: SPA + nginx fallback (D-41)

**Minimal `vite.config.ts` for an SPA (no special config needed beyond the React plugin):**
```typescript
// Source: https://vite.dev/guide/ (standard React SPA setup) + design-system/vite.config.ts as a working local example
import { defineConfig } from "vite";
import react from "@vitejs/plugin-react";

export default defineConfig({
  plugins: [react()],
  resolve: {
    dedupe: ["react", "react-dom"], // defensive against duplicate-React from a symlinked local dependency — see Common Pitfalls
  },
});
```

**Exact nginx directive** (add inside the `dashboard` service's `location /` block in
`deploy/compose.yaml`'s eventual `dashboard-react/dist/`-serving nginx config, or in a mounted
`nginx.conf` if the plain `nginx:alpine` image's default config is kept):
```nginx
location / {
    try_files $uri $uri/ /index.html;
}
```
[VERIFIED via WebSearch cross-referencing multiple nginx SPA-deployment guides, 2026-09-21] This
tries the literal requested file, then the path as a directory, then falls back to `/index.html`
for react-router to take over client-side. The `?id=<hostname>` query string on `/details` is
irrelevant to `try_files` matching — nginx's `$uri` excludes the query string, so
`/details?id=foo` and `/details` resolve identically for fallback purposes; react-router reads the
query string client-side via `useSearchParams()`.

**Consequence for D-42's parity-then-cutover plan:** today's `dashboard` nginx service uses the
stock `nginx:alpine` image with no mounted custom `nginx.conf` (only a volume mount for static
files, per `deploy/compose.yaml` lines ~197-207). The stock image's default `server` block does
NOT include a `try_files ... /index.html` fallback. At cutover, either (a) mount a custom
`nginx.conf` alongside the `dashboard-react/dist/` volume, or (b) switch to a purpose-built image
(e.g. a minimal `Dockerfile` copying `dist/` plus a custom conf). This is a cutover-time
concern, not something this phase's `dashboard-react/` build needs to solve immediately (D-42:
`dashboard/` keeps running unchanged during development; only the eventual cutover needs the nginx
config change) — but the plan should track it as a required task, not an afterthought.

### Pattern 3: Custom multi-open tree, built by imitating `Accordion.tsx`

**What `Accordion.tsx` actually provides (read directly, not assumed):** a single `openId: string
| undefined` state — **only one item can be open at a time** within one `<Accordion>` instance. No
`className` prop (can't be extended with an outer style hook), no recursion support in its own
API, `rounded-md border` applied only to the outer wrapper (a nested `<Accordion>` inside a
content slot would render a second full border/radius box, not tree-indentation).

**Why it's a pattern to imitate, not a component to wrap (confirms D-45):**
1. A device tree needs an arbitrary combination of groups open simultaneously (e.g., every group
   containing a DOWN host auto-expanded) — `Accordion`'s single `openId` cannot represent that; a
   tree needs a `Set<string>` of open node ids.
2. Severity-based per-node styling (D-11's color meanings) needs a `severity` prop threaded per
   node, which `AccordionItemData` (`{ id, title, content }`) has no slot for.
3. No depth-aware indentation exists — recursion via `content: <Accordion items={...} />` would
   structurally work (content is just `ReactNode`) but would visually nest boxes-in-boxes rather
   than an indented tree.

**Recommended shape** — copy the exact button/chevron/`aria-expanded` JSX pattern from
`Accordion.tsx` (it's the correct accessible foundation: real `<button>`, `aria-expanded`,
`aria-hidden` on the decorative chevron) into a new `TreeNode` component that takes a recursive
`children: TreeNodeData[]` and an `openIds: Set<string>` + `onToggle` from the parent (lifted
state, not local `useState`, so "expand every group with a DOWN host" and "collapsed-group survives
a re-sort" — D-32's requirement — are both just store/derived-state operations, not per-node
internal state).

### Anti-Patterns to Avoid
- **Wrapping `<Accordion items={[{ content: <Accordion .../> }]} />` for nesting:** structurally
  possible but produces nested bordered boxes, not tree indentation, and inherits the single-open
  limitation at every level. Build `TreeNode` fresh instead.
- **`useEffect(() => { mqtt.connect() }, [])` inside a component:** React 18/19 `StrictMode`
  double-invokes effects in development, which would open two MQTT connections. Connect from a
  module-level singleton with an idempotency guard instead (see Pattern 1).
- **`set(newState, true)` (replace-the-whole-store) for a single MQTT topic update:** wipes out
  every other slice and all action functions. Use the default merge behavior with a single-key
  `set({ devices: ... })` call instead.

|---------|-------------|-------------|-----|
| Client-side routing, `?id=` query param handling | A custom `window.location`/`popstate` router | `react-router` (Declarative Mode) | Battle-tested history handling, `useSearchParams()` already gives the `?id=<hostname>` read D-41 needs, back/forward button support for free |

## Common Pitfalls

### Pitfall 1: Duplicate React instances from a symlinked local dependency
**What goes wrong:** `npm install ../design-system` (D-40's "local-file-dependency" option) creates
a symlink under `dashboard-react/node_modules/kone-design-system` pointing at the real
`design-system/` directory. If `design-system/node_modules/react` also exists (it will, since
`react`/`react-dom` are its own `devDependencies` for its demo app), Node's module resolution for a
symlinked package resolves relative to the **real** path, which can pick up `design-system`'s own
copy of React instead of `dashboard-react`'s — the classic "Invalid hook call. Hooks can only be
called inside the body of a function component" bug from two React copies existing in one page.
**Why it happens:** npm's default behavior for `file:`/relative-path dependencies is a symlink, not
a copy; Vite's dependency pre-bundling (esbuild) does not always resolve symlinks back to the
importer's `node_modules`.
**How to avoid:** prefer the **packed tarball** method (`npm pack` + `npm install
../design-system/kone-design-system-0.1.0.tgz`), which npm installs as a real, un-symlinked
directory copy — this is also the only method `design-system/USAGE.md` claims was verified
end-to-end. If the local-file-dependency method is used anyway, add `resolve.dedupe: ["react",
"react-dom"]` to `vite.config.ts` as a defensive measure.
**Warning signs:** "Invalid hook call" errors that only appear after installing
`kone-design-system`, or React DevTools showing two separate React instances in the component tree.

### Pitfall 2: `design-system/dist/` is gitignored — a fresh checkout has no build output
**What goes wrong:** `design-system/.gitignore` excludes both `node_modules/` and `dist/`. `dist/`
happens to exist in the current working tree (built at some point this session) but is **not**
committed to git. A fresh `git clone` + `cd dashboard-react && npm install ../design-system` (or
`npm pack`) would fail or install a stale/empty package, because there is nothing at
`design-system/dist/` until `npm run build` runs there first.
**Why it happens:** compiled output is correctly gitignored (it's a build artifact), but nothing in
this phase's plan yet encodes "build the dependency before consuming it" as an explicit,
repeatable step.
**How to avoid:** any task that installs `kone-design-system` into `dashboard-react/` must first
run `cd design-system && npm ci && npm run build` (or equivalent) as a precondition, not assume
`dist/` already exists. This also matters for the eventual D-42 cutover: whatever process builds
`dashboard-react/dist/` for the nginx mount must build `design-system/dist/` first as a dependency
step.
**Warning signs:** `npm install ../design-system` or `npm pack` succeeding but producing a package
with no `dist/index.js`; import errors for `kone-design-system` that only reproduce on a clean
checkout, not the current dev machine.

### Pitfall 3: Tailwind major-version mismatch breaks the token-copying strategy
**What goes wrong:** a bare `npm install tailwindcss` today installs **v4.3.3** (the current
`latest` dist-tag), not the `v3.4.x` line `design-system/tailwind.config.js` is written for.
Tailwind v4 uses a CSS-native `@theme`/`@import "tailwindcss"` configuration model with no default
`tailwind.config.js` file at all — copying `design-system/tailwind.config.js`'s
`theme.extend.colors` JS object (the planned approach for giving new custom components the same
`bg-alert-light`/`text-fg-primary`/etc. utility classes) does not translate directly to v4's format.
**Why it happens:** Tailwind's major-version jump (v3 → v4) happened after `design-system` was
built and pinned; nothing stops `npm install tailwindcss` from grabbing the new default.
**How to avoid:** explicitly pin `tailwindcss@^3.4` (there is a maintained `v3-lts` dist-tag
currently resolving to `3.4.19`) whenever Tailwind is installed inside `dashboard-react/`.
**Warning signs:** a `tailwind.config.js` that Tailwind silently ignores (v4 doesn't error on an
unused config file, it just doesn't apply it), custom-component utility classes rendering
unstyled.

### Pitfall 4: `dist/style.css`'s CSS variables ARE already resolved — don't re-fetch the raw token JSON needlessly
**What goes wrong:** D-44's "if there's a gap, extend using the library's own raw color tokens"
language could be read as "go read
`web_assets/kone-design-system-main/.../design-tokens.json`." Reading `design-system/src/index.css`
(`@import "./tokens.css"` before the three `@tailwind` directives) and grepping the actual built
`dist/style.css` confirms the resolved `:root { --color-*: ... }` and `[data-theme="dark"] {
--color-*: ... }` custom-property definitions are already present in the compiled, importable
`kone-design-system/style.css` — there is no need to go back to the raw JSON source for any color
value that already has a `--color-*`/`--neutral-*` variable name in `tailwind.config.js`'s
`theme.extend`.
**Why it happens:** the canonical_refs note in CONTEXT.md correctly says the raw JSON is "no longer
read directly by this phase's own code," but doesn't state explicitly that the compiled CSS already
carries the resolved variables — an implementer could waste time re-deriving values that are one
`grep` away.
**How to avoid:** for any state/color gap, `grep` the imported `kone-design-system/style.css` (or
`design-system/dist/style.css` directly during development) for the relevant `--color-*` variable
name first.
**Warning signs:** none directly — this is a wasted-effort risk, not a correctness bug.

### Pitfall 5: `dashboard-react`'s own new Tailwind classes aren't automatically in the imported `style.css`
**What goes wrong:** `kone-design-system/style.css` (per `USAGE.md`) contains "every utility class
the **components** use" — i.e., Tailwind's v3 CLI scanned only `design-system/src/**/*.{ts,tsx}`
at build time (per `design-system/tailwind.config.js`'s `content` array). A brand-new custom
component in `dashboard-react/` that reaches for a utility class combination the library's own
components happen never to use (verified: none of the six read components use anything like
`grid-cols-*`, `cursor-col-resize`, or `hover:bg-alert-light`) will not find that class in the
imported CSS — Tailwind only emits classes it finds in scanned source files.
**Why it happens:** the compiled `style.css` is scoped to what the library itself renders, not a
general-purpose Tailwind reset for arbitrary consumer code.
**How to avoid:** decide explicitly (see Open Questions) whether `dashboard-react/` runs its own
Tailwind build (duplicating the color-token `theme.extend` block) so any new utility class it
writes gets compiled, or whether new custom components use plain CSS/CSS Modules referencing the
already-globally-available `var(--color-*)` custom properties directly, sidestepping the need for a
second Tailwind install entirely.
**Warning signs:** a utility class that visibly does nothing in the browser (no matching CSS rule
exists anywhere) despite being spelled correctly.

     only the tarball method carries `USAGE.md`'s own "verified end-to-end" claim, and the
     local-file method has a documented duplicate-React failure mode via symlinks.
   - What's unclear: whether the operator has a workflow preference (e.g., `npm link` for active
     side-by-side development of both packages, which trades the symlink risk for faster
     iteration during this phase's build).
   - Recommendation: default to the packed-tarball method for the initial build; if iteration
     speed on `design-system` itself becomes a bottleneck during Phase 11.1 execution, switch to
     `npm link` (option 2) rather than plain `npm install ../design-system` (option 1), since
     `npm link` is explicitly a different code path from a relative-path `file:` install and was
     not evaluated for the same duplicate-React risk in this research.

2. **(RESOLVED — own Tailwind v3 install, tokens duplicated) Does `dashboard-react/` get its own
   Tailwind install, or do new custom components use plain CSS referencing the imported
   `var(--color-*)` tokens directly?**
   - What we know: D-45 says custom components are "styled with the library's Tailwind
     tokens/utility classes," which reads as an expectation that Tailwind utility-class syntax is
     used; but the package boundary means dashboard-react's own Tailwind config must duplicate
     `design-system/tailwind.config.js`'s color mapping by hand (Pitfall 3/5, Assumption A3), a
     real (if small) maintenance-drift risk.
   - What's unclear: whether the operator would accept plain CSS/CSS Modules for the tree and
     splitter (referencing the same underlying `var(--color-fg-primary)` etc. custom properties,
     which are already globally available once `kone-design-system/style.css` is imported) as
     satisfying the spirit of "use the library's tokens" without literally writing Tailwind
     `className` strings.
   - Recommendation: install Tailwind v3 in `dashboard-react/` and duplicate the token mapping —
     it matches D-45's literal wording and keeps a single consistent styling idiom across both
     packages — but flag the duplication as a known drift risk in a code comment pointing back at
     `design-system/tailwind.config.js`.

3. **(RESOLVED — tracked as a follow-on, not built now) Nginx config for the eventual D-42
   cutover**
   - What we know: the current `dashboard` service uses the stock `nginx:alpine` image with only a
     volume mount, no custom `nginx.conf`; the stock default lacks a `try_files ... /index.html`
     fallback.
   - What's unclear: whether the cutover step (out of this phase's immediate build, but flagged in
     D-41/D-42) will mount a custom conf file or switch to a purpose-built Dockerfile — not
     something this phase needs to resolve now, but the plan should carry it as a tracked
     follow-on task rather than silently assume the stock image "just works" once
     `dashboard-react/dist/` is swapped in.

## Security Domain

`security_enforcement` is absent from `.planning/config.json` (treated as enabled per policy), but
this phase adds no server-side application, no authentication, and no new network-facing service —
REQUIREMENTS.md's Out of Scope table explicitly excludes multi-user accounts/login ("static,
backend-less dashboard on a trusted LAN; broker-level ACL is the only access control layer"). The
applicable ASVS surface is therefore narrow.

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |
|----------------|---------|-------------------|
| V2 Authentication | No | Explicitly out of scope (REQUIREMENTS.md); broker-level ACL (BRK-03) is the only access boundary, owned by Phase 8, not this phase |
| V3 Session Management | No | No sessions — static SPA, no login |
| V4 Access Control | No | No privilege levels in this UI |
| V5 Input Validation | Yes | MQTT payloads are attacker-adjacent only in the sense of "malformed/unexpected JSON from a compromised or buggy poller" — `dashboard/js/state-store.js`'s existing defensive `parsePayload()`/`isPlainObject()` pattern (drop-and-keep-last-known-good, never throw) is the standard control here and must be ported unchanged, not weakened, into the Zustand store's `handleMessage` |
| V6 Cryptography | No | No crypto operations in this UI; MQTT-over-WS is plaintext `ws://` today (unchanged from Phase 11 — not this phase's scope to add `wss://`) |

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|-----------------------|
| Reflected/stored XSS via device alias, folder name, or event text rendered from MQTT payloads | Tampering / Elevation of Privilege (via XSS) | React's default JSX text-node escaping already mitigates this for any value rendered as `{value}` rather than `dangerouslySetInnerHTML` — confirm no new code path introduces `dangerouslySetInnerHTML` when porting `dashboard/js/render-*.js`'s string-building logic into JSX |
| Malformed/oversized MQTT payload crashing the render | Denial of Service | Port `state-store.js`'s parse-and-drop-on-failure pattern verbatim (see V5 row above) — never let a single bad payload throw out of the `handleMessage` call and blank the whole SPA |
