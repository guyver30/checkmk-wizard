# Phase 11.1: Dashboard Layout and Light Palette - Research

**Researched:** 2026-09-16
**Domain:** Static vanilla-JS dashboard layout/CSS redesign (no framework, no build step)
**Confidence:** HIGH (all findings from direct code reading in this repo; palette values pending token-file read)

## Summary

Phase 11.1 is a pure frontend redesign of an already-shipped static dashboard (`dashboard/`,
vanilla JS ES5-style modules, no bundler). The work has three technically distinct pieces: (1) a
token-level palette swap that D-28 deliberately engineers to require **zero JS changes** by
splitting `--state-*` (kept saturated, read as a mark by three consumers) from a new
`--state-*-fill` (pale, background-only); (2) a layout restructuring that wraps `#main` in a new
grid cell per D-31 so `shell.js`/`ensureContainer()` contracts are untouched; and (3) a genuinely
new capability — accessible, persisted, resizable/collapsible panes — that this codebase has never
built before and has no library to borrow (no-framework constraint holds).

The codebase already has two precedents the plan must reuse rather than reinvent: the
guarded-storage pattern (`groupingMode()`/`groupingModeOverride` in `render-shell.js`) for anything
persisted to `localStorage`, and the `tick()` scroll/focus-preservation pattern around full
rebuilds. Both precedents exist *because* a prior bare `localStorage` access and a prior full
rebuild-on-every-poll each caused a real regression already fixed once in Phase 11 — the plan must
not reintroduce either failure mode for pane state or for stale-flip rendering.

**Primary recommendation:** Implement the redesign as CSS Grid `#main`-wrapping (D-31) + a new
`--state-*-fill` token layer (D-28) + a hand-rolled `pointerdown`/`setPointerCapture` splitter
component keyed by CSS custom properties on the grid container, with pane sizes and collapse state
held in a small in-memory module (mirroring `groupingModeOverride`) that guards every
`localStorage` read/write. Do not add a JS test runner for the event-ordering regression (D-33) —
pin it in `tests/test_mqtt_poller.py` (Python/pytest, already the project's only test harness).

## 1. The Real Code — File-by-File Map

### `dashboard/js/shell.js` (236 lines)

- Entry point loaded last on every page; owns the pushState router and the `ViewModules` composition.
- `mountView(view, params)` (line 86): calls `document.getElementById("main")` (line 99) to hand the container to the active `ViewModule.mount()`. **This is the exact seam D-31 protects** — as long as `#main` still exists and is still reachable by `getElementById("main")`, nothing here needs to change for the three-pane wrap.
- `handleKeydown(event)` (line 155): Enter/Space activation for `[data-host]` elements (WCAG 2.1.1 precedent D-26 must not regress). Routes through `navigateToHost()` → `navigateTo()`, never a raw `location.href` assignment.
- `navigateTo(view, params, url)` (line 117): `history.pushState(...)` then `mountView(...)`. No change needed for the pane work — panes are shell-level chrome, not part of the view-module contract.
- `dispatchStoreChange(changeKind, arg)` (line 176): fans `store` events out to `renderShell.*` functions and to `currentModule.update(...)`. `"poller"` → `renderShell.renderBanners()` only (not `renderTree()` directly — that only happens conditionally inside `renderPollerBanner()` when staleness *changes*, see below). This is the dispatch table D-34's "toggle don't rebuild" fix must thread through without adding a new `changeKind`.
- `renderShell.onTick(fn)` (line 218): shell.js registers exactly one tick listener that fans `tick()`'s cadence to the active view module via `currentModule.update("poller", undefined)`. **Not owned by shell.js** — `tick()` itself and `CLOCK_TICK_MS` live in `render-shell.js` (see below); shell.js only consumes the callback.

### `dashboard/js/render-shell.js` (722 lines) — the module most of this phase touches

- `groupingMode()` / `groupingModeOverride` (lines 75–95) — **the guarded-storage precedent, quoted verbatim below** (see section 5).
- `collapsedGroupKeys` (line 68): a `Set`, module-level, **not** DOM state — declared explicitly *because* `renderTree()` rebuilds the whole tree on every store change and DOM-held collapse state would reset every rebuild. This is the exact pattern the new pane-size/collapse state must copy.

- `renderTree()` (line 452): full rebuild — `container.replaceChildren()` on `#sidebar-tree`, called on `"topology"` store changes, on a `pollerStale` flip (inside `renderPollerBanner`, line 244), and unconditionally every `tick()` (line 622). **This is the exact trap named in D-32's four binding constraints and in D-34** — sort order must be derived fresh on every call (never cached), and per D-34 this full-rebuild-on-stale-flip is the thing that must become a class toggle instead.
- `renderTreeDevice(hostname)` (line 482): the patch-in-place counterpart — used only for a single-device `"device"` store change, never for topology/poller changes. Falls back to `renderTree()` when the row doesn't exist yet or the device was tombstoned.
- `renderEvents()` (line 552): **the ordering contract (D-33)** — `events.slice().reverse()` because the poller appends chronologically (comment at line 562, matches `mqtt_poller.py`'s actual code, verified below). Do not touch this reversal.
- `tick()` (line 604) and `CLOCK_TICK_MS = 12000` (line 53): the scroll/focus-preservation list is `SCROLL_CONTAINERS = ["sidebar-tree", "sidebar-events", "main"]` (line 585, **quoted exactly** — this is the literal array the D-26/D-34 "revisit which elements scroll" note refers to). `tick()` snapshots `scrollTop` for each of those three ids before `renderBanners()`/`renderTree()`/`tickListeners.forEach(...)`, then restores it after; it also finds `document.activeElement`'s closest `[data-host]` and restores focus by `data-host` lookup (node identity cannot survive a rebuild). **Consequence for the three-pane layout:** once `#sidebar-events` moves out of `.sidebar` and into its own centre-bottom pane, and centre-top becomes its own scrollable region, `SCROLL_CONTAINERS` must be updated to name whatever new element ids own those scroll regions — the ids `"sidebar-tree"` and `"sidebar-events"` are very likely to change or be joined by a fourth id (the centre-top pane) depending on how D-31's grid wrapping is implemented. **This list is a single array literal at one line — trivial to update, easy to forget.**
- `init()` (line 660): wires the grouping toggle, sidebar hamburger toggle, tag-group-banner dismiss button, then calls `renderConnection`/`renderBanners`/`renderTree`/`renderEvents`/`startClock()` once. New splitter/collapse wiring for D-26 belongs here, following the exact same "grab element by id, guard for null, addEventListener" shape already used for every other control in this function.

## 3. The Contrast Audit (D-30) — Recommendation

**Recommendation: a `uv run --script` standalone Python script, not a pytest test.**

Rationale:
- **Repo convention** is `uv run` for every Python invocation — a script satisfies this directly
  and needs no new dependency (`re`/`json` from the standard library is enough to parse
  `:root { --token: #hex; }` out of `dashboard.css`; no CSS parser package needed for a file this
  regular).
- **Not a pytest test**, despite `tests/` being the project's only existing harness, because: (a)
  this check has nothing to do with the wizard's `pytest`/`pytest-asyncio`/`respx` suite and would
  be the only "browser CSS" test living among Python-CLI unit tests, an awkward fit for
  `tests/test_*.py`'s 1:1-with-source-module naming convention (no `dashboard.css` "source module"
  in the Python sense exists to mirror); (b) a contrast audit is naturally a **report** (which pairs
  pass/fail and by how much), not a boolean assertion — a script that prints a table and exits
  non-zero on any failure is more useful standalone (`uv run scripts/contrast_audit.py`) than
  buried in pytest's dot-per-test output; (c) D-30's own acceptance language — "a committed,
  runnable check... reproducible by anyone who checks out the repo" — describes a script's
  contract, not a hidden assertion. If the plan wants CI-style enforcement too, the script can
  still be wrapped in one `tests/test_contrast_audit.py::test_dashboard_css_passes_contrast` that
  shells out to it or imports its `main()` and asserts exit code 0 — cheap to add either way, but
  the script itself should be the primary, human-runnable artifact.
- Lives at `scripts/contrast_audit.py` (this repo's existing convention for operational tooling —
  see `scripts/mqtt_poller.py`, `scripts/smoke_test_broker.py` — not `dashboard/` itself, since it
  is a dev-time check, never shipped to the browser).

**Implementation shape:**
1. Read `dashboard/css/dashboard.css`, regex-extract every `--token-name: #rrggbb;` (or `rgba(...)`)
   declaration inside the `:root { ... }` block into a `dict[str, str]`.
2. Define the list of (foreground, background, role) triples the audit must check — this is
   **exactly the "20 pairs" the preview's own audit already enumerated** (per CONTEXT.md's
   Specific Ideas — that artifact is gone with the session-local `scratchpad/preview/`, so the pair
   list must be reconstructed from the actual CSS rules in `dashboard.css`: every place a `color`
   is set against a `background-color`/`background` in the same selector or a parent/child pair
   (e.g. `.state-label` on `.tree-host-row.state-ok`, `--color-text` on `--color-surface`, the
   connection dot on the topbar, etc.). Do this by reading the CSS rules directly, not by
   guessing — this research's own extraction (section 2 above) is a starting point but is not
   exhaustive of every rendered pairing.
3. Implement the WCAG relative-luminance + contrast-ratio formula exactly as below (no external
   dependency needed — the formula is ~15 lines of Python, already validated in this research
   against D-29's published numbers).
4. For each pair, compute the ratio, compare against 4.5:1 (text) or 3.0:1 (non-text/large-text/UI
   component), print PASS/FAIL with the computed ratio, and track an overall failure count.
5. `sys.exit(1)` if any pair fails; `sys.exit(0)` otherwise. This makes it usable as a pre-commit
   or CI gate without any additional wrapping.

**The WCAG relative-luminance formula** (so the planner/implementer does not need to look it up):

```python
def _channel(c: int) -> float:
    """c is 0-255 sRGB channel value."""
    c_srgb = c / 255
    if c_srgb <= 0.03928:
        return c_srgb / 12.92
    return ((c_srgb + 0.055) / 1.055) ** 2.4

def relative_luminance(r: int, g: int, b: int) -> float:
    return 0.2126 * _channel(r) + 0.7152 * _channel(g) + 0.0722 * _channel(b)

def contrast_ratio(hex_a: str, hex_b: str) -> float:
    """Both args are '#rrggbb'. Returns a ratio >= 1.0 (lighter+0.05)/(darker+0.05)."""
    def to_rgb(h: str) -> tuple[int, int, int]:
        h = h.lstrip("#")
        return int(h[0:2], 16), int(h[2:4], 16), int(h[4:6], 16)
    l1 = relative_luminance(*to_rgb(hex_a))
    l2 = relative_luminance(*to_rgb(hex_b))
    lighter, darker = max(l1, l2), min(l1, l2)
    return (lighter + 0.05) / (darker + 0.05)
```

This exact implementation was used to independently reproduce all five of D-29's published numbers
in section 2 above (all matched to 2 decimal places), so it is a validated reference, not
speculative code.

## 4. Resizable/Collapsible Panes With No Library (D-26) — the largest unknown

No existing precedent in this codebase — this is genuinely new capability. The no-framework/
no-bundler constraint (repo CLAUDE.md, `11-UI-SPEC.md` Design System table) rules out any
splitter/resizer npm package even if one were vendored (D-03's own vendoring precedent is for
exactly one file, `mqtt.js`, copied and committed — a splitter library would be a much larger,
harder-to-audit vendoring surface for a capability that is ~150 lines to hand-roll).

### The accessible splitter pattern (WAI-ARIA APG "Window Splitter")

`[CITED: training knowledge of the WAI-ARIA Authoring Practices Guide window-splitter pattern —
not independently re-fetched this session; the shape below is standard and stable, but the planner
should treat the exact attribute names as MEDIUM confidence and spot-check against
https://www.w3.org/WAI/ARIA/apg/patterns/windowsplitter/ before implementation if time allows.]`

- The splitter itself is a focusable element with `role="separator"`, **not** `role="slider"`
  (a slider implies a value being set directly; a separator implies it is moving a boundary between
  two regions — this is exactly D-26's own literal instruction: `role="separator"`).
- `aria-orientation="horizontal"` or `"vertical"` — **note the ARIA orientation is about the
  splitter's own axis, i.e. a vertical divider between a left/right pane pair has
  `aria-orientation="vertical"`**, which is the tree/centre divider in this phase's layout; the
  divider between centre-top and centre-bottom (stacked panes) has `aria-orientation="horizontal"`.
  This is a common point of confusion — verify against the spec's own example before committing to
  a mnemonic in code comments.
- `aria-valuenow`, `aria-valuemin`, `aria-valuemax` — expressed as the adjustable pane's size (in
  px or as a percentage of the container), not as an abstract 0–100 slider value; must be kept in
  sync on every resize (drag or keyboard).
- `aria-controls` pointing at the id of the pane the splitter primarily resizes (recommended, not
  strictly required by every implementation, but cheap and improves AT navigation).
- `tabindex="0"` so the splitter is reachable by Tab.
- Arrow-key behaviour: the perpendicular arrow keys (Left/Right for a vertical splitter, Up/Down for
  a horizontal one) adjust the size by a fixed step (D-26 leaves the exact step size to Claude's
  Discretion — a step of ~16–24px, or ~5% of the container, is a typical, unsurprising default).
  Home/End optionally jump to `aria-valuemin`/`aria-valuemax`. **This exact keyboard contract is
  what D-26 calls "keyboard equivalence is mandatory, not optional"** — without it, the pane
  resize feature would be a literal WCAG 2.1.1 regression against the keyboard-navigation work
  `shell.js`'s `handleKeydown` already established in Phase 11.

### Minimal pointer-based drag implementation

**Use Pointer Events (`pointerdown`/`pointermove`/`pointerup`) with `setPointerCapture`, not mouse
events (`mousedown`/`mousemove`/`mouseup`).** Rationale, concrete and specific to this codebase:
- Pointer Events unify mouse, touch and pen input behind one API — this dashboard already has a
  responsive breakpoint at 900px with an off-canvas sidebar drawer (`dashboard.css` lines 880–892),
  implying touch/tablet use is already a first-class target; mouse-only events would silently break
  dragging on a touchscreen kiosk, which is exactly the kind of device this dashboard is likely to
  run on long-term (the codebase's own comments reference "a long-lived kiosk tab").
- `element.setPointerCapture(event.pointerId)` on `pointerdown` guarantees all subsequent
  `pointermove`/`pointerup` events keep targeting the splitter element even if the pointer moves
  faster than the browser can hit-test (a fast drag can otherwise "escape" the element and land on
  a sibling, losing the drag) — this is the single biggest practical advantage over the classic
  `mousemove` listener attached to `document` pattern, and needs no manual cleanup-listener
  bookkeeping (`pointerup`/`pointercancel` auto-release capture).
- Minimal shape:
  ```js
  splitterEl.addEventListener("pointerdown", function (event) {
    splitterEl.setPointerCapture(event.pointerId);
    var startPos = event.clientX; // or clientY for a horizontal splitter
    var startSize = currentPaneSizePx();
    function onMove(moveEvent) {
      var delta = moveEvent.clientX - startPos;
      setPaneSizePx(clamp(startSize + delta, MIN_SIZE_PX, MAX_SIZE_PX));
    }
    function onUp() {
      splitterEl.removeEventListener("pointermove", onMove);
      splitterEl.removeEventListener("pointerup", onUp);
      persistPaneSize(); // guarded localStorage write, see section 5
    }
    splitterEl.addEventListener("pointermove", onMove);
    splitterEl.addEventListener("pointerup", onUp);
  });
  ```
  This shape needs no `document`-level listeners and no manual capture-release — `pointerup`/
  `pointercancel` release capture automatically, and the `pointermove`/`pointerup` listeners are
  scoped to `splitterEl` itself (only fire while captured).

### Expressing pane sizes: CSS Grid custom property vs. flex-basis

**Recommend CSS Grid `grid-template-columns`/`grid-template-rows` driven by a CSS custom property**,
not flexbox `flex-basis`. Rationale specific to this layout:
- D-31's whole finding is "wrap `#main` in a new grid cell" — the existing `.shell` is **already**
  a CSS Grid (`display: grid`, `dashboard.css` line 369) with named row/column tracks sized by
  custom properties (`--layout-sidebar-width`, `--layout-topbar-height`,
  `--layout-sidebar-tree-fraction`) exactly this same technique. Continuing with Grid for the new
  three-pane wrapper is the path of least resistance and reuses a pattern already proven in this
  file, rather than mixing two different layout systems (outer Grid, inner Flex) for what is
  conceptually one continuous layout problem (sidebar width, then within the remaining space a
  centre-top/centre-bottom split).
- Shape: the new wrapper (say `#centre`, replacing the direct grid-cell occupancy `#main` has
  today) gets `display: grid; grid-template-rows: var(--pane-top-size) auto var(--pane-bottom-size);`
  where the middle `auto` row is the splitter itself (a real grid track, not an absolutely
  positioned overlay — this makes the splitter's own hit-target trivially sized by CSS rather than
  computed in JS), and `--pane-top-size`/`--pane-bottom-size` are custom properties set via
  `element.style.setProperty(...)` from the drag handler shown above. A `1fr`/flexible unit on one
  side (rather than fixing both) lets the browser absorb rounding/overflow without JS having to
  compute the complementary size on every drag frame — set one pane's size as a fixed px/percent
  custom property and let the other side be `1fr` (or vice versa), rather than trying to keep two
  independently-set sizes numerically consistent.
- Same technique applies to the sidebar-tree/splitter/(nothing — sidebar is now single-pane per
  D-22) relationship, N/A here since the sidebar itself is no longer split; but the **sidebar's own
  width becomes resizable too** if D-26's "all three panes" (tree, centre-top, centre-bottom) is
  read literally — re-read D-26/11.1-SCOPE.md's "3. Panes resizable and collapsible" item, which
  says "All three panes (left tree, centre top, centre bottom) must be resizable" — so the sidebar
  width itself needs a splitter on its right edge, in addition to the centre-top/centre-bottom
  splitter. `--layout-sidebar-width` (currently a fixed `280px` constant) becomes the third
  JS-settable custom property.

### Minimum sizes and collapse vs. resize-to-zero

**Collapse must be a distinct state from "resized to its minimum," not merely resize-to-zero.**
Concretely: define a `MIN_PANE_SIZE_PX` (e.g. 120–160px — small enough to still show a
recognisable sliver of content, large enough that the collapse chevron and any header controls
remain usable) that dragging can never cross; **collapse** is a separate boolean applied via a
class (e.g. `.pane.is-collapsed`) that sets the pane's grid track to a small fixed "collapsed rail"
size (e.g. 32–40px, just enough for the chevron button) and hides the pane's inner content
(`[hidden]` or `visibility: hidden` — **not** `display: none` on the whole pane if the chevron
button itself must remain visible/focusable inside the collapsed rail). This distinction matters
because: (a) a drag that reaches `MIN_PANE_SIZE_PX` should stop there, not silently collapse the
pane — a user dragging to "make it small" and a user clicking "collapse" are different intents; (b)
the persisted size (guarded storage, section 5) should store the **pre-collapse** size so
expanding restores the size the operator actually chose, not `MIN_PANE_SIZE_PX`.

### State that must live outside the rebuilt DOM (surviving `tick()`)

Per `render-shell.js`'s existing pattern (`collapsedGroupKeys`, a module-level `Set`, **not** read
from the DOM), pane size/collapse state must be **module-level JS variables**, not attributes read
back off the DOM at render time. Concretely, whatever new module owns the splitters needs its own
`var paneState = { sidebarWidthPx: ..., topHeightPx: ..., bottomHeightPx: ..., sidebarCollapsed:
false, topCollapsed: false, bottomCollapsed: false };`-shaped object (or one entry per pane in a
`Map`), written by the drag/collapse handlers, and **applied to the DOM via
`element.style.setProperty(...)` on the grid wrapper** rather than left for CSS to "remember" on
its own. This matters concretely for `tick()`'s 12-second cadence: `tick()` calls
`renderBanners()`/`renderTree()` (full DOM rebuilds of `#sidebar-tree`) every 12 seconds — **the
grid wrapper and its custom properties are NOT rebuilt by `tick()`** (they are outside
`#sidebar-tree`/`#sidebar-events`/`#main`'s subtrees), so as long as pane sizing is expressed as
custom properties on a stable, never-rebuilt wrapper element (not as inline styles on elements
`renderTree()` recreates), a resize naturally survives `tick()` with **no extra code** — this is
the same "outside the rebuilt subtree" reasoning that already makes `collapsedGroupKeys` durable
across `renderTree()`'s rebuilds. Verify this holds once `SCROLL_CONTAINERS`/the pane wrapper
elements are finalized in the plan — the risk is only real if pane-size state is accidentally
attached to an element that another render path rebuilds.

## 5. Guarded Storage — the Exact Precedent to Reuse

Quoted **verbatim** from `dashboard/js/render-shell.js` (lines 70–95) — this is the pattern every
new persisted value (pane sizes/collapse state, the grouping-select value, the severity-checkbox
value) must copy, not reinvent:

```js
// Set whenever the operator toggles grouping, and the source of truth for
// the rest of the session; storage is only how the choice SURVIVES a reload.
// Without this, a browser that refuses the write would leave groupingMode()
// re-reading the old stored value on the very next renderTree(), so the
// toggle would flip its aria-pressed state and then silently not regroup.
var groupingModeOverride = null;

// Storage access is wrapped because reading it can THROW, not just return
// null: a browser with site data blocked, a private window, or an embedded
// frame with restricted storage all raise on access. groupingMode() runs
// during init() and again on every renderTree(), so an unguarded throw here
// took down the whole shell -- the sidebar, banners and event panel never
// rendered -- over a remembered toggle position. D-07's device_type default
// is the correct fallback when the preference cannot be read.
function groupingMode() {
  if (groupingModeOverride !== null) {
    return groupingModeOverride;
  }
  var stored = null;
  try {
    stored = localStorage.getItem(GROUPING_MODE_KEY);
  } catch (err) {
    stored = null;
  }
  return stored === "folder" ? "folder" : "device_type";
}
```

And the write side (from `init()`, lines 664–677):

```js
groupingToggle.addEventListener("click", function () {
  var next = groupingMode() === "device_type" ? "folder" : "device_type";
  // In-memory first, so the regroup below happens whether or not the
  // write lands. The preference is a convenience; losing it across a
  // reload is acceptable, losing the interaction is not.
  groupingModeOverride = next;
  try {
    localStorage.setItem(GROUPING_MODE_KEY, next);
  } catch (err) {
    /* preference not persisted -- the toggle still applies this session */
  }
  groupingToggle.setAttribute("aria-pressed", next === "folder" ? "true" : "false");
  renderTree();
});
```

**The three-part shape to replicate for every new persisted value:** (1) a module-level
`xOverride`/in-memory variable that is the single source of truth read by every consumer during the
session; (2) a getter that checks the in-memory override first, and only falls back to a
`try { localStorage.getItem(...) } catch (err) { ... }`-guarded read when the override is still
`null`/unset, defaulting to a known-good value on any failure; (3) a setter that writes the
in-memory value **first, unconditionally**, then attempts the `localStorage.setItem(...)` write
inside its own `try/catch` that silently drops the error. **Never let a `localStorage` read or
write — in either direction — execute unguarded on the path that also drives a live interaction**
(this is precisely what took the whole shell down once, per the comment). This applies identically
to pane sizes (numeric, not a string enum, but the same three-part shape) and to the new grouping
`<select>`/severity `<checkbox>`, per D-32's explicit "same guarded read + in-memory override
pattern" requirement.

  numeric rank (0–4) needed to sort groups worst-first. `sortedGroupKeys()` currently only does
  `a.localeCompare(b)` — the new severity-sort mode needs a **second comparator function** (not a
  new severity-computation primitive) that, given the already-built `groupIndex`, computes each
  key's `rollUpGroup(...).worstRank` once and sorts descending by rank (tie-broken by
  `localeCompare` for a stable secondary order, matching `render-devices.js`'s own existing
  `compareIds()` pattern of falling back to `displayName(...).localeCompare(...)` on a tie).
- **Host-level severity order** (within a group, or in the flat device table): `SEVERITY_RANK` is
  directly indexable by `effectiveState(payload)` — exactly the pattern `render-devices.js`'s
  `compareValueFor(payload, "state")` (line 236) already uses for the device table's own default
  "state severity worst-first" sort. The tree's `groupElement()` and the (deleted) overview's
  `cardElement()` currently hardcode `.sort((a,b) => displayName(...).localeCompare(...))` — this
  needs the same conditional swap: sort by `SEVERITY_RANK[effectiveState(...)]` descending when the
  checkbox is on, else the existing alphabetical sort.
- **No changes needed inside `grouping.js` itself** — `SEVERITY_RANK`, `effectiveState` (via
  `display.js`) and `rollUpGroup` are all already exported/global and already carry everything the
  new sort modes need. The new code lives in the *callers* (`render-shell.js`'s `groupElement()`/
  `renderTree()`, and `render-devices.js`'s `compareValueFor()`/`currentSort`), as a new comparator
  option, not as new domain logic.
- **D-32's own trap, confirmed real by reading `renderTree()`:** since `renderTree()` rebuilds the
  whole tree from `buildGroupIndex()`/`sortedGroupKeys()` on every call (topology change, poller
  stale flip, every 12s tick), the sort mode (alphabetical vs. severity) must be read from the same
  guarded in-memory override (section 5) **inside** `renderTree()`/`groupElement()` on every
  rebuild — never cached in a variable computed once at `init()` time, or a later grouping/severity
  toggle would not take effect until the next unrelated store change.
- **`collapsedGroupKeys` surviving a re-sort**: already true structurally — `collapsedGroupKeys` is
  keyed by group **key** (folder path or device_type string), not by position/index, and
  `groupElement(key, idsSet, mode)` looks up `collapsedGroupKeys.has(key)` by that same key
  regardless of where the key falls in the now-resorted `keys` array `renderTree()` iterates over.
  Re-sorting the keys array changes iteration *order*, not the *keys* themselves, so this already
  works correctly with zero additional code — confirm this in the plan rather than adding
  unnecessary defensive code.

## 7. Event Ordering (D-33) — VERIFY, Regression Test Placement

**Confirmed by direct reading of `scripts/mqtt_poller.py` (lines 1097–1098):**
```python
if events_this_cycle:
    state.events = (state.events + events_this_cycle)[-config.events_max_entries :]
    publish_events(client, state.events)
```
`events_this_cycle` is built by three `.append(...)` calls in cycle order (lines 1053, 1064, 1077 —
tombstone events, state-change events, added-device events, in that source-code order within one
cycle) and concatenated **onto the end of** the existing `state.events`, i.e. **oldest-first,
append-only, chronological** — confirmed matching `render-shell.js`'s own comment at
`renderEvents()` (`events.slice().reverse()`, line 566: "Newest-first: the poller appends
chronologically"). This is self-consistent and correct as shipped; D-33's directive to "VERIFY, do
not fix" is well-founded by this reading.

**No existing test pins array *order*.** Read `tests/test_mqtt_poller.py` in full for every
`events`-related test (lines 734–1115): every existing assertion either checks (a) that an event
with a specific `device_id` exists somewhere in the published array (`next(e for e in entries if
e["device_id"] == "b")`, line 1051) or (b) the array's **last** element (`entries[-1]`, lines 1034,
1072 — correct for single-event-per-cycle tests, but does not prove chronological order across
*multiple* events accumulated across *multiple* cycles). **This is exactly the gap D-33 asks the
plan to close**: no test currently proves that two events from two different `run_cycle()` calls
land in the correct oldest-first order in the concatenated, bounds-truncated array.

**Recommendation: pin the regression test in `tests/test_mqtt_poller.py` (Python/pytest), not a new
JS test runner.** Confirmed this session: `find . -iname package.json` returns nothing anywhere in
the repo, and `pyproject.toml`'s only test dependencies are `pytest`/`pytest-asyncio`/`respx` — this
codebase has **no JS test runner of any kind**, committed or implied (`node` itself happens to be
present in this *development* environment, `v24.20.0`, but is not a repo dependency, is not
referenced by any committed file, and the `shell.js`/`render-index.js` code comments describing
"11-07 and 11-08... each proving it with a two-script `vm.runInContext` simulation" describe an
**ad hoc verification technique used during planning/development**, not a persisted, committed test
harness — no such script exists in the repo today). Given "no build step" and "simplicity first"
(repo CLAUDE.md), introducing a JS test runner (even a zero-dependency one like Node's built-in
`node --test`) purely to pin one ordering contract would be new infrastructure for a single
assertion, when the *producer* of the guarantee (`mqtt_poller.py`) already has a full pytest
harness that can assert the exact array shape published over MQTT — **the contract is a backend
guarantee that the frontend merely trusts (and does not re-verify at runtime)**, so pinning it at
the producer is both sufficient and idiomatic for this repo. Concretely: add a test calling
`run_cycle()` twice in sequence (two different state transitions on two different mock devices, or
two sequential transitions on the same device across two cycles) and assert the **full array order**
(not just `[-1]`) of the published `lan/events/recent` payload is oldest-first — e.g.
`assert [e["device_id"] for e in entries] == ["a", "b"]` after cycle 1 then cycle 2 each contributes
one event, or equivalent for two events in a single cycle from the three `.append()` call sites.
This directly exercises the same code path `renderEvents()`'s `.reverse()` assumes, without needing
any browser/JS test infrastructure.

## 8. Pitfalls Specific to This Change

### Pitfall: `renderTree()` rebuilds on every store change — the pre-existing trap

**What goes wrong:** any new state (sort mode, severity-checkbox value) that is only read once (at
module init, or cached in a closure variable) instead of freshly on every `renderTree()` call will
silently stop responding to toggles the moment any *other* store event triggers a rebuild — because
`renderTree()` itself, not the toggle handler, is what actually redraws the DOM. **Why it happens:**
the toggle handler and the render function are decoupled (the handler sets state and calls
`renderTree()` directly, but `renderTree()` is *also* called independently on `"topology"` changes
and every `tick()`) — any code path that reads the toggle's value must be inside `renderTree()`'s
own call graph, not cached alongside the handler. **How to avoid:** read `groupingMode()`/the new
severity-mode getter fresh, every single call, exactly as `renderTree()` already does today (line
458: `var mode = groupingMode();`, called at the top of the function body, not hoisted to module
scope). **Warning signs:** a toggle that visually flips its own control state (aria-pressed,
checkbox `checked`) but the tree/table doesn't re-sort until an unrelated event (the next `tick()`,
12 seconds later) fires — this exact symptom is what the tree-collapse work in Phase 11 already hit
once (per D-32's own text).

### Pitfall: `collapsedGroupKeys` surviving a re-sort — already safe, confirmed above (section 6)

Confirmed by reading `groupElement(key, idsSet, mode)` — collapse state is keyed by group *key*
string, sort order only changes *iteration order* over those same keys, so this composes correctly
with zero new code, as long as the new severity-sort comparator sorts the same `keys` array
`sortedGroupKeys()`/its caller already produces and does not introduce a second, differently-keyed
data structure.

### Pitfall: `[hidden]` losing to ID specificity — already fixed in Phase 11, must not regress

`dashboard.css` lines 122–136 carry a dated bug-fix comment: the browser's built-in
`[hidden] { display: none }` (specificity 0,0,1,0) previously **lost** to
`#poller-banner, #tag-group-banner { display: flex }` (specificity 1,0,0,0), so both banners
rendered permanently visible regardless of the `.hidden` property JS set. The fix is a global
`[hidden] { display: none !important; }` rule. **Any new pane/splitter markup that uses the
`hidden` attribute for collapse (as opposed to a `.is-collapsed` class + explicit CSS) is already
protected by this existing global rule** — but if new ID-selector rules are added for the pane
wrapper (`#centre-top`, `#centre-bottom`, etc.) with `display: grid`/`display: flex` at the same
`1,0,0,0` specificity as the old broken banner rule, and something ever tries to toggle a pane via
`element.hidden = true` instead of the `.is-collapsed` class this research recommends (section 4),
the exact same class of bug can recur on a *new* pair of selectors. **Prefer the `.is-collapsed`
class mechanism for pane collapse** (section 4) precisely to sidestep this whole specificity
category, rather than relying on `[hidden] !important` bailing the plan out a second time.

### Pitfall: `.is-stale` must stay `background-image`-only for D-15 composability

Already true in the current CSS (`.is-stale { background-image: repeating-linear-gradient(...); }`,
no `background-color`) — the palette swap only needs to change the gradient's own colour stop
(`rgba(255,255,255,0.06)` → a dark-ink equivalent, e.g. `rgba(20,20,20,0.08)`) and must **not**
introduce a `background-color` on `.is-stale` itself, or it will silently override whichever
`--state-*-fill` colour the element's own `.state-*` class set (CSS `background-color` and
`background-image` are separate properties and composite correctly today specifically *because*
`.is-stale` only ever touches the `-image` half).

### Pitfall: `--state-*` must keep its SATURATED value — three consumers read it as a mark (D-28)

Confirmed by grep (section 2): only **one** of the three named consumers (connection dot) exists in
shipped code today; gauge arcs and map nodes are Phase 12/13 and do not exist yet. **The risk is
inverted from what D-28's text might suggest**: it is not that three live call sites need careful
coordination today — it is that **only one does**, and the temptation during implementation will be
to "simplify" by repointing `--state-*` itself to a lighter value (since nothing *currently* seems
to depend on it staying saturated besides one 8px dot) and only discovering the breakage when
Phase 12/13 build the gauge arc/map node against an already-repointed token. **Do not repoint
`--state-*` itself under any circumstance** — introduce `--state-*-fill` (and, per this research's
synthesis, `--state-*-ink`) as wholly new custom properties instead, leaving all eight existing
`--state-*` declarations' *values* untouched (their meaning already matches D-11 and needs no
re-derivation — the light theme reuses the same saturated hexes the dark theme already uses,
consistent with green.base already being the *same* `#1ed273` in both this research's proposed
light palette and the current dark `dashboard.css`).

### Pitfall: the connection-dot's saturated mark may fail 3:1 non-text contrast on a light topbar

New finding from this research (section 2), not named in CONTEXT.md: `green.base`/`orange.base`
against a white/near-white topbar measure 2.00:1/2.04:1, **below** D-30's own 3.0:1 acceptance
threshold for non-text marks. The connection dot is always paired with a redundant text label
("Connected"/"Reconnecting…"/etc — an existing, unchanged accessibility rule), which mitigates the
*information-conveyance* risk (WCAG 1.4.1) but does not, on a literal reading, satisfy 1.4.11's
non-text-contrast requirement for the dot itself if it is considered a "graphical object required to
understand content." **The plan should either:** (a) accept and document this as a known,
pre-existing-pattern trade-off (the dark theme's dot-on-navy-surface combination was never audited
against 3:1 either, per the 11-UI-SPEC.md's own "measured this session at approximately 3.8:1"
caveat for a *different* pair), or (b) add a thin `border: 1px solid var(--color-border)` (or
similar) ring around `.connection-dot` so the dot's edge, not its fill-vs-background contrast alone,
carries the boundary — a one-line CSS change. Either way, **this must be a decision the plan states
explicitly and the D-30 audit script should include this exact pair**, since it is the one concrete
case in the whole palette where the literal acceptance criterion is not met by the "keep `--state-*`
saturated" design as CONTEXT.md states it.

   - What we know: the exact computed numbers (section 2/8) — `green.base`/`orange.base` are
