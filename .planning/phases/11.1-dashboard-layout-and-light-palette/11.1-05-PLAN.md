`devices: Record<string, DevicePayload>`, `history: Record<string, HistoryEntry[]>`,
`events: EventEntry[]`, `topology: TopologyPayload | null`,
`pollerStatus: PollerStatusPayload | null`, `lastKnownPollerTimestamp: string | null`,
`connection: { phase: "connecting" | "connected" | "reconnecting" | "disconnected"; delayMs?: number }`.
Use plain `Record` objects rather than `Map`s so Zustand's referential-equality selectors work
normally — the vanilla store's `Map` was an implementation detail, not part of the contract.

Actions: `handleMessage(topic: string, payload: Uint8Array)` and
`setConnection(status)` (consumed by Task 3).

Port `state-store.js`'s topic routing verbatim: split the topic on `/` and match by segment
position (`parts[1] === "devices" && parts[3] === "status"`, likewise `history`), then exact-match
`lan/devices/topology`, `lan/events/recent`, `lan/poller/status`. Segment matching is deliberate —
the device-id segment is arbitrary text sourced from Checkmk host names and must not be regexed.

Port `parsePayload` and `isPlainObject` unchanged in behavior: a zero-length payload returns
`{ok:true, value:null}` (tombstone), a `JSON.parse` failure returns `{ok:false}`, and every handler
drops a `{ok:false}` or wrong-shaped payload while keeping last-known-good. This handler must never
throw — a single bad payload blanking the SPA is the Denial-of-Service threat in the register below,
and it is the same defensive posture `scripts/mqtt_poller.py::_normalise_restored_node()` applies.

Every write uses Zustand's DEFAULT merge: `set({ devices: { ...get().devices, [id]: payload } })`.
Do NOT pass the second `replace` argument (`set(partial, true)`) — that replaces the ENTIRE store
including the other slices and every action function (RESEARCH Pattern 1). The
wholesale-replace-a-slot semantics D-46 asks for are what default `set()` already gives at the top
level; the per-device object itself is also replaced, never deep-merged.

Port the `lastKnownPollerTimestamp` handling and its 2026-09-16 bug-fix comment: the poller's MQTT
will is the fixed payload `{"status":"offline"}` with no timestamp (a will is captured at connect
time, so any timestamp in it would be the time the poller STARTED), so the last payload that DID
carry `last_poll`/`since` must be remembered here rather than discarded.

Write `useAppStore.test.ts` covering every behavior above. Use
`useAppStore.setState(initialState, true)` in `beforeEach` to reset between tests, or export a
`createInitialState()` helper — pick one and note the choice in a comment. Build payload buffers
with `new TextEncoder().encode(JSON.stringify(...))` and a zero-length `new Uint8Array(0)` for the
tombstone case.

  <behavior>
    - Calling `connect()` twice creates exactly one underlying client (the StrictMode double-invoke guard).
    - On `connect`, the client subscribes to all five topics and the store's connection phase becomes `"connected"`, and the retry attempt counter resets to 0.
    - On `close`, a reconnect is scheduled with delay `min(30000, 1000 * 2**attempt) * (0.5 + random*0.5)` and the phase becomes `"reconnecting"` carrying that delay.
    - Successive `close` events without an intervening `connect` produce strictly growing base delays (1000, 2000, 4000...) capped at 30000 before jitter.
    - On `offline`, the phase becomes `"disconnected"`.
    - An `error` event is logged and does NOT rethrow (an unhandled error event would abort page init and leave a silent blank page).
    - Each `message` event calls `useAppStore.getState().handleMessage(topic, payload)`.

body. React 18/19 StrictMode double-invokes effects in development, which would open two MQTT
connections (RESEARCH anti-pattern). Hold `let client: MqttClient | null = null` at module scope
and return early from `connect()` when it is already set.

Export `connect(deps?)`, `disconnect()`, and the constants `BASE_DELAY_MS = 1000`,
`MAX_DELAY_MS = 30000`, `SUBSCRIBE_TOPICS` (the exact five from `mqtt-connection.js`:

`lan/poller/status`). Make the module testable without a broker by accepting an optional injected
dependency object `{ connectFn?, randomFn?, setTimeoutFn? }` defaulting to `mqtt.connect`,
`Math.random` and `globalThis.setTimeout` — this is the minimum seam needed to unit-test the
backoff formula deterministically; do not add configurability beyond it.

Build the broker URL as `ws://${location.hostname}:${WS_PORT}` at call time (D-02 — the browser
derives the broker host from the page's own origin so the dashboard works unchanged from any LAN
device). Pass `username: WS_USERNAME`, `password: WS_PASSWORD`, `clean: true`, and

`reconnectPeriod` is a FIXED interval with no growth and no jitter, so it cannot satisfy DASH-05,

Attach all five listeners here and nowhere else — this module is the single choke point, exactly
as `mqtt-connection.js` is today. `connect` resets `attempt` to 0, clears the pending timer,

calls `console.error` and returns — never rethrow. `message` calls
