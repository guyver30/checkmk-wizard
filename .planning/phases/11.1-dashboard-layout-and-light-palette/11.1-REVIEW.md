# Phase 11.1: Code Review Report

## Summary

Reviewed the `dashboard-react/` React+TypeScript+Tailwind rewrite of the live dashboard
(components, hooks, store, lib modules and their tests), plus the two non-`dashboard-react`
files in scope (`dashboard/css/dashboard.css` and the Podman setup doc). The codebase is
disciplined overall — pure functions in `lib/` are defensively parsed and well tested, the
MQTT store normalizes malformed payloads instead of throwing, and accessibility (ARIA
separator contract, `role=status`/`role=log`, keyboard operability) is deliberately engineered
and largely covered by tests.

The one finding that matters: `usePaneLayout`'s `commit()` reads pane sizes from a closure
variable instead of from the value it is called with, and `Splitter`'s keyboard handler calls
`onResize` and `onResizeCommit` synchronously in the same event — so every keyboard-driven pane
resize (arrow keys, and especially Home/End) persists the *pre-resize* size to `localStorage`,
not the new one. No existing test exercises this specific call sequence (the hook test always
lets a render flush between `setSize` and `commit`), so the regression is currently invisible
to the suite. Three further warnings and two info-level notes are attached below.

The gsd-tools convention-check module was not present in this environment
(`$CLAUDE_PLUGIN_ROOT`/plugin cache path did not resolve to a `bin/gsd-tools.cjs`), so the
automated CONVENTION-tier pass could not run; no findings are emitted under that tier as a
result other than the one manually-observed deviation noted under Info.

## Critical Issues

### CR-01: Keyboard-driven pane resize persists the pre-resize size, not the new one

**File:** `dashboard-react/src/components/Splitter.tsx:104-111` and
`dashboard-react/src/hooks/usePaneLayout.ts:94-104`

**Issue:** `Splitter.handleKeyDown` calls `onResize(clamped)` immediately followed by
`onResizeCommit?.(clamped)` in the *same* synchronous event handler:

```tsx
// Splitter.tsx
const clamped = clamp(next, min, max);
onResize(clamped);
onResizeCommit?.(clamped);
```

`ThreePaneLayout` wires `onResize={(next) => setSize("tree", next)}` and
`onResizeCommit={commit}`, where `commit` comes from `usePaneLayout()`:

```ts
// usePaneLayout.ts
function commit() {
  writeJson(STORAGE_KEY, {
    treeWidth: state.sizes.tree,
    eventsHeight: state.sizes.events,
    treeCollapsed: state.collapsed.tree,
    eventsCollapsed: state.collapsed.events,
  });
}
```

`commit()` takes no argument and instead reads `state` — the `usePaneLayout()` hook's
`useState` value captured in the closure for the render that is currently executing. `setSize`
schedules a `setState` update; it does not synchronously mutate `state`. Because `onResize` and
`onResizeCommit` are invoked back-to-back within one keydown handler, `commit()` always writes
the size from *before* this keypress, not the one `setSize` just computed. Concretely: pressing
`End` on the "Resize device tree" separator visually jumps the pane to `max` (640px), but
`localStorage`'s `dashboard-react.paneLayout.v1` is written with the pre-jump `treeWidth`
(e.g. 320px). On reload, the pane silently reverts. Every `Arrow*` press has the same problem —
persisted state permanently lags the visible state by one keystroke — and because `commit()`
always writes *both* `sizes.tree` and `sizes.events` together, a keyboard resize of either pane
also re-persists the other pane's now-stale-but-unrelated size.

This is invisible to `usePaneLayout.test.ts`'s own `commit` test because that test calls
`setSize` and `commit` in two *separate* `act()` blocks, letting React re-render (and rebind
`commit` to the fresh `state`) between them — the exact call pattern `Splitter.tsx` actually
uses (both calls inside one handler, no render in between) is never exercised by any test in
this file set. Pointer-drag resize is not affected in practice because `pointermove`/`pointerup`
are separate native events with a render in between, so `commit`'s closure is fresh by the time
`pointerup` fires.

**Fix:** Have `onResizeCommit` pass the value through to the persistence call instead of
re-reading stale hook state — either give `commit` a parameter and use it directly, or fold the
value into the `setState` updater so the write reflects the value actually being committed:

```ts
// usePaneLayout.ts
function commit(overrides?: Partial<PaneSizes>) {
  const sizes = { ...state.sizes, ...overrides };
  writeJson(STORAGE_KEY, {
    treeWidth: sizes.tree,
    eventsHeight: sizes.events,
    treeCollapsed: state.collapsed.tree,
    eventsCollapsed: state.collapsed.events,
  });
}
```

```tsx
// ThreePaneLayout.tsx
onResizeCommit={(next) => commit({ tree: next })}
...
onResizeCommit={(next) => commit({ events: next })}
```

(Or equivalently, have `setSize` itself perform the write inside its `setState` updater, since
that updater has direct access to the just-computed `clamped` value and is guaranteed to be
in sync.) Whichever approach is chosen, add a regression test that calls `setSize` then `commit`
synchronously within a single `act()` (mirroring `Splitter`'s real call sequence) to catch this
class of bug in the future.

## Warnings

### WR-01: `mqttClient.scheduleReconnect` can leak/duplicate a pending reconnect timer

**File:** `dashboard-react/src/store/mqttClient.ts:50-59`

**Issue:** `scheduleReconnect()` unconditionally overwrites the module-level `reconnectTimer`
without clearing any timer already scheduled:

```ts
function scheduleReconnect(): void {
  const growth = BASE_DELAY_MS * 2 ** attempt;
  const capped = Math.min(MAX_DELAY_MS, growth);
  const delay = capped * (0.5 + activeRandomFn() * 0.5);
  attempt += 1;
  useAppStore.getState().setConnection({ phase: "reconnecting", delayMs: delay });
  reconnectTimer = activeSetTimeoutFn(() => {
    client?.reconnect();
  }, delay);
}
```

`reconnectTimer` is only cleared inside the `"connect"` handler
(`client.on("connect", () => { ... clearTimeout(reconnectTimer); ... })`). If the underlying
mqtt.js client emits `"close"` more than once before a previously scheduled reconnect fires
(e.g. a flapping connection, or the broker closing the socket again shortly after a prior
close), the old timer is orphaned rather than cancelled, and both the old and new timers will
eventually call `client?.reconnect()` — potentially firing a duplicate reconnect attempt and
skewing `attempt`'s growth relative to what the UI/backoff delay communicated to the user via
`setConnection`.

**Fix:** Clear any existing timer before scheduling a new one:

```ts
function scheduleReconnect(): void {
  if (reconnectTimer) {
    clearTimeout(reconnectTimer);
  }
  ...
}
```

### WR-02: `StatsStrip`'s `DISPLAY_ORDER` contradicts its own "worst-first" comment and restates severity instead of reusing `SEVERITY_RANK`

**File:** `dashboard-react/src/components/StatsStrip.tsx:9-12`

**Issue:** The module comment states: `// Display order: worst-first among the non-OK states,
OK always first.` But `DISPLAY_ORDER` is:

```ts
const DISPLAY_ORDER: (keyof StateCounts)[] = ["OK", "DOWN", "CRIT", "UNREACH", "WARN", "UNKNOWN", "STALE", "PEND"];
```

Compared against `grouping.ts`'s own `SEVERITY_RANK` (`WARN: 1, UNKNOWN: 2, CRIT: 3, UNREACH: 3,
DOWN: 4`), a genuinely worst-first ordering of the non-OK states would put `UNKNOWN` (rank 2)
ahead of `WARN` (rank 1); `DISPLAY_ORDER` puts `WARN` ahead of `UNKNOWN` instead, so the tile
strip's ordering does not actually match "worst-first" as claimed, and is inconsistent with the
tree's own worst-of ordering (`treeModel.ts`, which imports `SEVERITY_RANK` "verbatim... never
restated here" per its own comment, D-32's binding constraint). `StatsStrip.tsx` restates its
own hand-written severity ordering instead of deriving it from `SEVERITY_RANK`, which is exactly
the kind of duplicated severity table the rest of the codebase deliberately avoids elsewhere.

**Fix:** Either derive `DISPLAY_ORDER`'s non-OK portion by sorting `SEVERITY_RANK` descending
(with a fixed tie-break, e.g. alphabetical, mirroring `treeModel.ts`'s own tie-break rule), or
correct the comment to describe the actual (curated, not strictly rank-derived) intended order
if the WARN-before-UNKNOWN placement is deliberate design rather than an oversight.

### WR-03: `Splitter`'s pointer drag state does not track `pointerId`

**File:** `dashboard-react/src/components/Splitter.tsx:51-81`

**Issue:** `handlePointerDown` calls `e.currentTarget.setPointerCapture(e.pointerId)` but
`DragState` never records which `pointerId` started the drag:

```ts
interface DragState {
  startPos: number;
  startValue: number;
  lastValue: number;
}
```

`handlePointerMove`/`handlePointerUp` act on `dragRef.current` unconditionally without checking
`e.pointerId` matches the one captured in `handlePointerDown`. Under normal single-pointer mouse
interaction this is harmless, but on a touch-capable device where a second contact point
generates its own `pointermove`/`pointerup` events for the same element (pointer capture is
per-pointer-id, not exclusive across all pointers), a second finger could feed unrelated
`clientX`/`clientY` deltas into the same `dragRef`, corrupting the resize in progress.

**Fix:** Store `pointerId` in `DragState` and early-return in `handlePointerMove`/
`handlePointerUp` when `e.pointerId !== dragRef.current.pointerId`.

## Info

### IN-01: Disposable broker credentials committed in source

**File:** `dashboard-react/src/lib/config.ts:25-26`

**Issue:** `WS_USERNAME`/`WS_PASSWORD` are hardcoded literal credentials
(`"wsreader"`/`"wsreader"`) shipped in a source file that is bundled into the client-side
JavaScript. This is called out extensively in the file's own comment block and in
`docs/Podman setup for checkmk, minio, mosquitto, worker.md` §3/§6 as a deliberate,
already-established convention (matching `dashboard/js/config.js`, `cmkadmin`/`cmkadmin`,
`minioadmin`/`minioadmin`) with a read-only ACL grant bounding the blast radius, and an explicit
operator instruction to rotate before exposing beyond a trusted LAN. Flagging for completeness
per standard review practice — no action expected beyond what's already documented, since the
precedent and mitigation are already recorded in-repo.

### IN-02: `dashboard/js/config.js`-vanilla vs. `dashboard-react` drift risk is self-acknowledged but unenforced

**File:** `dashboard-react/README.md:76-81`, `dashboard-react/src/lib/config.ts:20-22`

**Issue:** Both `dashboard-react/README.md` §6 and `src/lib/config.ts`'s header comment note
that `POLL_INTERVAL_SECONDS`/`STALENESS_FACTOR`/`HISTORY_MAX_ENTRIES` in `config.ts` must be
kept in step by hand with `scripts/mqtt_poller.py`'s own defaults, and that
`tailwind.config.js`'s `theme.extend` block must be kept in step by hand with
`design-system/tailwind.config.js`. Both are explicitly documented as manual-sync risks with no
automated check (e.g. a test asserting the two constant sets match, or a build-time import).
This is not a defect in the current diff — it's flagged here only because "kept in step by
hand" duplicated-constant risk is exactly the failure mode WR-02 above independently surfaced
for `SEVERITY_RANK`/`DISPLAY_ORDER`; consider a lightweight guard (e.g. a comment-adjacent test
fixture, or importing the values where the language boundary allows it) if this becomes a
recurring source of drift.
