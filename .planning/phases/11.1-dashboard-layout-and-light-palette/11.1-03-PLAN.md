<objective>
Replace the dark palette with KONE's light palette, expressed as three tiers of state tokens, with
zero JavaScript changes.

Purpose: D-28 engineers this as a CSS-only theme swap by keeping `--state-*` saturated (it is read
as a *mark*) and introducing a new pale `--state-*-fill` tier that only the seven `.state-*`
background rules consume. D-38 adds the third `--state-*-ink` tier because D-29 measured that
KONE's BASE greens/oranges/yellow are unusable as text on white (2.00:1 / 2.04:1 / 1.30:1) — a
literal two-tier reading cannot satisfy both locked decisions.
Output: an edited `dashboard/css/dashboard.css`. Nothing else.

**Do not repoint `--state-*` itself under any circumstance.** Research flags this as the single
most likely implementation mistake: only ONE consumer (the 8px connection dot) reads the saturated
token in shipped code today, so "simplifying" by lightening it looks harmless and silently breaks
Phase 12's gauge arcs and Phase 13's map nodes months later.
</objective>

Four CSS-only fixes. Still zero JS changes.

**1. `.is-stale` hatch (D-29 defect 1).** Change only the gradient's colour stop from
`rgba(255,255,255,0.06)` to a dark-ink equivalent, `rgba(20,20,20,0.08)`. Do **not** add a
`background-color` to `.is-stale` and do not change any other property in that rule: D-15
composability works precisely because `background-color` (set by the `.state-*` class, now a pale
`-fill`) and `background-image` (set here) are separate properties, so a stale-AND-crit element
shows both facts. Keep and extend the existing "background-image ONLY — never background-color"
comment with a dated note saying the white hatch was invisible on the new pale fills.

**2. `.brand-logo` (D-29 defect 2).** The `background: #ffffff` chip exists only because the dark
navy topbar needed a light square behind the logo's own baked-in white background. On a light
topbar it is invisible padding. Remove the `background` and the `padding: 4px 6px` (and the now-
pointless `box-sizing: content-box` if it becomes dead), OR replace the white fill with
`border: 1px solid var(--color-border)` if the logo still needs to read as deliberately framed.
Choose one, and record which and why in a comment — the repo convention is to explain the *why*.

**3. `--color-surface-raised` consumers (D-29 defect 3).** With `--color-surface-raised: #ffffff`,
every raised surface is white-on-white. The prescribed fix is a **border, not a distinct fill**
(the KONE `border` semantic token `#d0d0d0` is already `--color-border`). Add
`border: 1px solid var(--color-border)` to `#tag-group-banner` and `.count-badge`. For
`#device-table tr:hover`, a white-on-white hover is a no-op — re-point that one rule to
`var(--color-surface)` (`#f3f6fe`, 1.08:1 against white, which is the intended barely-there hover
tint) rather than to a border, because a border on hover would shift row heights. Also re-check
`#poller-banner`'s `background-color: rgba(114, 114, 114, 0.2)` — that alpha was composited over
the dark `--color-bg`; on white it must still read as a banner and its text must still clear 4.5:1,
so either raise the alpha or give the banner a border. State which you chose and why.

**4. Connection-dot ring (D-39, LOCKED).** `.connection-dot` is an 8px circle whose
`background-color` is set inline by `render-shell.js` to `var(--state-ok)` / `var(--state-warn)` /
`var(--state-crit)`. Against a white topbar `--state-ok` (`#1ed273`) measures **2.00:1**, below
D-30's own 3.0:1 non-text-mark line. Add `border: 1px solid var(--color-border);` to
`.connection-dot` so the mark gains a compliant edge. **Do NOT desaturate the dot** and **do NOT
record this as a waived exception** — D-39 forbids both. Keep the 8px `width`/`height` (add
`box-sizing: border-box` if the ring must not grow the dot). Comment that plan 11.1-04's audit
checks the RING against the topbar, not the fill.

Surgical edits only — do not restyle adjacent rules that are not in this list.
