  <action>
**Group-level severity order.** `sortedGroupKeys(groupIndex)` in `grouping.js` is pure alphabetical
and stays that way. In `renderTree()`, after building the group index, branch on
`severityOrder()` — read fresh at the top of the function body, exactly as `groupingMode()` already
is. When on, sort the SAME `keys` array `sortedGroupKeys()` produced, descending by
`rollUpGroup(idsSet, store.devices).worstRank`, tie-broken by `localeCompare` for stability
(mirroring `render-devices.js`'s existing `compareIds()` fallback). Compute each key's rank ONCE
per rebuild into a lookup rather than calling `rollUpGroup` inside the comparator, which would
re-roll on every comparison.

**Host-level severity order.** In `groupElement()`, make the existing alphabetical
`displayName(...).localeCompare(...)` sort conditional: when `severityOrder()` is on, sort by
`SEVERITY_RANK[effectiveState(payload)]` descending with `displayName` `localeCompare` as the
tie-break. Do not add a second severity table — `SEVERITY_RANK` already mirrors the poller's
`compute_overall_state()` worst-of ordering, and its own header comment warns that the two tables
are hand-kept in sync across languages. A third copy would drift from both.

**The trap, stated explicitly.** `renderTree()` rebuilds the whole tree from scratch on every store
change, so the sort mode must be read INSIDE `renderTree()`/`groupElement()`'s own call graph on
every invocation. Never hoist it to module scope, never cache it at `init()` time, never read it
back off a DOM attribute. The symptom of getting this wrong is specific and recognisable: the
checkbox visually flips but the tree does not re-sort until 12 seconds later when an unrelated
`tick()` fires. Phase 11's tree-collapse work hit this exact bug once.

**`collapsedGroupKeys` across a re-sort.** Research confirmed this already composes correctly with
zero new code: collapse state is keyed by group key string, and re-sorting changes iteration order,
not the keys. **Confirm it by test, and do NOT add defensive code for it** — collapse two groups,
tick the severity checkbox, and verify the same two groups are still collapsed. If that passes, the
existing structure is correct and anything added would be unnecessary complexity.

**Device table.** `render-devices.js` already defaults to `currentSort = { key: "state", direction:
"desc" }`, i.e. severity-worst-first. Decide and state what the checkbox means for the table: the
minimal honest reading is that it forces `currentSort` to the `state`/`desc` pair when switched on,
while leaving the operator's column-header click free to override afterwards. Do not silently do
nothing there — the checkbox is a page-level control and must have a defined effect on both views.
  </action>
