  <behavior>
    - `buildTree(devices, mode, nowMs)` with no options still orders groups alphabetically (the existing default is unchanged).
    - `buildTree(devices, mode, nowMs, { orderBySeverity: true })` orders groups by descending `worstRank`, then by descending `nonOkCount`, then alphabetically as the tie-break.
    - With `orderBySeverity: true`, devices inside each group order by descending severity rank of their state, then alphabetically by label.
    - Ties produce a deterministic, stable order across repeated calls with identical input.
    - `useGroupingPrefs()` returns `{ mode: "type", orderBySeverity: false }` on first run with empty storage.
    - A stored record is restored on mount; a corrupt record falls back to the defaults without throwing.
    - A stored `mode` value not present in the known option list falls back to `"type"` rather than being passed through.
    - `setMode`/`setOrderBySeverity` update the returned values immediately even when `localStorage.setItem` throws.
  </behavior>
  <action>
Extend `buildTree` with an optional fourth parameter `options?: { orderBySeverity?: boolean }`.
When true, sort groups by `worstRank` descending, then `nonOkCount` descending, then `label`
ascending; sort each group's devices by `SEVERITY_RANK[node.state] ?? SEVERITY_RANK.UNKNOWN`
descending, then `label` ascending. Import `SEVERITY_RANK` from `./grouping` — do not restate the
ranking anywhere in this file. `worstRank` and `nonOkCount` are already produced by `rollUpGroup`,
so this adds a sort, not a second severity computation (D-32's second binding constraint).

Because ordering is a parameter of the derivation function and not component state, D-32's "sort
order must be derived on each rebuild, never held in the DOM/component state" constraint is
satisfied structurally. Record that in a comment on the new parameter.

Create `src/hooks/useGroupingPrefs.ts` returning `{ mode, orderBySeverity, setMode,
setOrderBySeverity }`, backed by `guardedStorage` under the versioned key
`"dashboard-react.grouping.v1"` holding `{ mode: string; orderBySeverity: boolean }`. Mirror
`usePaneLayout`'s shape exactly: lazy `useState` initialiser for the read, per-field validation
with independent fallbacks, in-memory state as the session source of truth, and a write whose
`false` return is deliberately ignored because a refused write must never break the interaction.
Validate `mode` against the exported option list (Task 2) rather than a hardcoded union so adding
an option does not require touching validation.
  </action>
