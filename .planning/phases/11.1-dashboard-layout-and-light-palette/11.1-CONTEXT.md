<domain>
## Phase Boundary

Phase 11 shipped a working dashboard against a UI contract the operator rejected on sight
once it was running: dark, dense, with the event history buried in a 280px sidebar. The
contract was not wrong when written — it was written against the `docs/DMC-*.png` reference
mockups — but it is not what a KONE-branded product should look like. Phase 11 was allowed
to close against its own requirements; this phase carries the redesign, with the decisions
it contradicts formally superseded rather than silently ignored.

**This phase was scoped as layout and palette ONLY** — no new data source, no new topic, no
new poller field, no new capability, every byte already arriving over MQTT today. **On
2026-09-21 the operator raised the bar on HOW that gets built**: the dashboard must strictly
follow the company's own `kone-design-system` React component library, which means this
phase now also carries a full technology rewrite (vanilla JS/CSS → React + TypeScript +
Tailwind SPA) alongside the original layout/palette redesign. The *product* scope (below)
is unchanged; only the implementation technology is not "vanilla JS" anymore. See the
"React Pivot" decisions for what that changes and what it doesn't.

Concretely, it delivers:

1. The KONE light palette and visual identity, now sourced from `kone-design-system`'s own
   components/tokens rather than a hand-rolled, computationally contrast-audited CSS palette.
2. A three-pane layout — tree left (full height), centre top, event history centre bottom.
3. All three panes resizable and collapsible, mouse and keyboard, sizes persisted.
4. The "Group by type" toggle becomes an extensible select plus an "Order by severity" checkbox.
5. Verification (not "fixing") of newest-first event ordering, with a regression test.
6. Two follow-on defects from Phase 11's live verification: stale flips that rebuild instead
   of toggling, and event rows that cannot be told apart at narrow widths.
7. **(Added 2026-09-21)** The above is delivered as a React SPA in a new `dashboard-react/`
   directory, built against `kone-design-system`, running alongside the existing vanilla
   `dashboard/` until it reaches parity and is cut over (D-40–D-46).

### React Pivot (operator-directed, 2026-09-21) — read this section first

The operator introduced a hard requirement mid-milestone: the dashboard must **strictly
follow the company's own design system**, `design-system/` (untracked in git at the time of
this decision — `git add` it before planning), a real installable React + TypeScript +
Tailwind component library (`kone-design-system`, built via `tsup` + the Tailwind CLI, see
`design-system/USAGE.md`). This is a full-app rewrite, not an incremental port, confirmed
explicitly by the operator over the alternative of extracting tokens only into the existing
vanilla-JS dashboard.

- **D-40 (NEW, operator-chosen):** the dashboard is rewritten as a **React + TypeScript +
  Tailwind SPA** consuming `kone-design-system` directly (per `design-system/USAGE.md`'s
  local-file-dependency or packed-tarball method — planner's choice). This **supersedes**
  the vanilla-JS/no-build-step architecture Phase 11 shipped and Phase 11.1 wave 1 already
  built on top of (state-token palette, connection-dot ring). It also retires half of a
  project-level constraint: `.planning/PROJECT.md` and `./CLAUDE.md`'s "No new backend for
  the dashboard" constraint has been edited — "no server-side application" still holds (the
  React app still builds to static assets with no new API), but "static HTML/CSS/JS only, no
  build step" is retired. Phase 11's D-19/D-20/D-21 are marked superseded in
  `.planning/phases/11-live-dashboard/11-CONTEXT.md` accordingly (done in this session).

- **D-41 (NEW, operator-chosen):** app structure is a **single-page app with a client-side
  router**, not a Vite multi-page build. The router renders the equivalent of
  `index`/`devices`/`details` as routes. D-19's `?id=<hostname>` query-string convention for
  the detail view survives unchanged, now attached to a route instead of a second real HTML
  file. **Consequence:** a cold-load of a non-root route (e.g. a bookmarked `/details?id=...`
  link) needs an nginx rewrite (`try_files $uri /index.html`) added to the dashboard's nginx
  config in `deploy/compose.yaml` — the current config serves three real files and has no
  such rule.

- **D-42 (NEW, operator-chosen):** the React app is built in a **new `dashboard-react/`
  directory**, kept separate from the existing vanilla `dashboard/` (which keeps running,
  deployed exactly as today) **until the React build reaches feature parity**, at which point
  `deploy/compose.yaml`'s dashboard nginx mount is swapped from `dashboard/` to
  `dashboard-react/dist/` and the vanilla directory is deleted. Both may run side-by-side on
  different ports during development. This is a parity-then-cutover migration, not a
  big-bang replace.

- **D-43 (NEW, operator-chosen) — what carries forward vs. what's dropped.** Confirmed
  explicitly: supersede the *technology*, keep the *product behavior*.
  - **Dropped** (superseded by "use the design-system's own components/tokens," see D-44):
    D-28, D-29, D-30, D-38, D-39 — the hand-rolled 3-tier `--state-*`/`-fill`/`-ink` token
    system, the committed contrast-audit script, and the connection-dot ring engineering.
    None of this is built for the React version.
  - **Kept as product requirements**, now implemented in React rather than vanilla JS/CSS:
    - D-25/D-27/D-31 — stats strip above a sized, labelled topology-map placeholder pane;
      three-pane grid (tree / centre / event history).
    - D-26 — resizable AND collapsible panes, keyboard-equivalent (arrow-key resize, real
      `<button>` collapse controls), `role="separator"` + `aria-orientation` +
      `aria-valuenow` on splitters, sizes persisted via guarded storage (an in-memory value
      is the source of truth for the session; a refused write must never break the
      interaction — same rule, now a `localStorage` read/write wrapped the same defensive
      way inside a React effect/hook rather than in `render-shell.js`).
    - D-32 — grouping becomes an extensible `<select>` (`type` / `folder`, room for more)
      plus an "Order by severity" checkbox; sort order is derived on every render from
      current state, never held as stale DOM/component state, and any collapsed-group
      tracking must survive a re-sort. The severity-rank comparator logic itself
      (`SEVERITY_RANK`, `effectiveState`, `rollUpGroup` from `dashboard/js/grouping.js`) is
      the reference to port, not re-derive.
    - D-33 — newest-first event ordering is a **verified, already-correct** contract
      (`state.events + events_this_cycle` in `scripts/mqtt_poller.py`, unmodified); pin it
      with a regression test regardless of which frontend consumes it.
    - D-34 — a stale flip must not discard scroll position, focus, or tree-expand state.
      React's reconciler makes "toggle a class instead of rebuilding" less of a manual
      concern than in vanilla DOM manipulation, but the underlying requirement — a stale poll
      tick must be a visual-only change, never a remount that loses UI state — still holds
      and must be verified against React's actual re-render behavior, not assumed away by
      the framework.
    - D-35 — event rows must legibly identify their device even when many hosts share a
      long common IP prefix (middle-truncation, alias-first display, or a tooltip).
    - D-37 — the `CHECKMK_BASE_URL`-equivalent placeholder-config deployment-doc callout
      still applies; the config file's name/location moves into `dashboard-react/` but the
      operator-facing problem (a stale placeholder silently disables the Checkmk deep link)
      is unchanged.
    - D-11 (Phase 11) — state *meanings* (which of OK/WARN/DOWN/STALE/UNKNOWN a color
      represents) are unchanged; only where the color *values* come from changes (D-44).

- **D-44 (NEW, operator-chosen) — palette/contrast: trust the design-system.** No separate
  contrast audit is built for 11.1's device states. `kone-design-system` is the company's own
  vetted library — its tokens and components are assumed to already meet the company's
  accessibility bar. Device states (OK/WARN/DOWN/STALE/UNKNOWN) are mapped onto the library's
  existing status-bearing primitives (`Badge.tsx`, `Chip.tsx`, `Banner.tsx`, `Message.tsx` are
  the candidates — `design-system/src/components/`) rather than a hand-rolled state-token
  system. **Open item for research/planning:** read those four components' actual variant
  props to confirm which semantic states they expose natively (the library may not have a
  first-class "critical/down" variant distinct from "error") and decide, if there's a gap,
  how to extend it using the library's own raw color tokens rather than inventing a parallel
  palette — this is a research question, not re-litigated here.

- **D-45 (NEW, operator-chosen) — missing components are custom-built on the design-system's
  primitives, no new UI dependency.** The library has no tree view, no resizable-pane
  splitter, no gauge arc, and no map component. Build all four as custom React components
  styled with the library's Tailwind tokens/utility classes — `Accordion.tsx` is a candidate
  base for the collapsible tree groups (planner/researcher to confirm fit). D-26's full
  keyboard/ARIA contract for splitters applies regardless of this choice. The gauge arc
  (Phase 12) and map placeholder (Phase 13, D-27) are out of this phase's build scope but the
  component *pattern* (custom-on-primitives, no new dependency) is decided now so Phase 12/13
  don't re-litigate it.

- **D-46 (NEW, operator-chosen) — state management: Zustand.** MQTT-fed state (device list,
  topology, event log — the "wholesale-replace on message" store `dashboard/js/state-store.js`
  implements today) is held in a Zustand store rather than plain hooks+Context or Redux.
  `mqtt.js` remains the WebSocket client (already vendored per Phase 11's D-05/DASH-05
  jittered-backoff requirement); a single hook/module owns the connection lifecycle and
  writes into the Zustand store on each message. The replace-the-whole-tree-on-message
  semantics of the vanilla store are the reference behavior to preserve, not the
  implementation.

### Palette

**SUPERSEDED by D-43/D-44 (2026-09-21): the entire hand-rolled token/contrast-audit approach
below (D-28, D-29, D-30, D-38, D-39) is dropped for the React rewrite.** `kone-design-system`'s
own tokens and components are trusted instead. Kept here as historical record of the vanilla
implementation's reasoning — not applicable to planning going forward.

- **D-28 (NEW) — the token split that makes this a zero-JavaScript-change theme.**
  `--state-*` **keeps the SATURATED value** in both palettes, because three places read it
  directly as a **mark**: the connection dot (set inline by `render-shell.js`), the Phase 12
  gauge arcs, and the Phase 13 map nodes. The pale behind-text tint goes into a **new
  `--state-*-fill` token**, and **only the seven `.state-*` background rules** re-point at
  it. Net effect: a light theme with no JS edits.

- **D-29 (NEW) — two measured facts that invert the dark theme's rules.** Both were measured
  against KONE's own tokens and must survive into the implementation:
  1. KONE's **BASE** greens/oranges/yellow are unusable as text on white — `green.base`
     2.00:1, `orange.base` 2.04:1, `yellow` 1.30:1. **Anything rendering a state as text or
     as an icon must use a d-shade.**
  2. On a solid state fill, **ink (`#141414`) beats white on every KONE hue** (green 9.23 vs
     2.00, yellow 14.12 vs 1.30). The dark theme's "white text on every fill" rule
     **inverts** — do not carry it over.

- **Sourcing rule (locked):** every value comes from KONE's own
  `web_assets/kone-design-system-main/packages/kone-ds-tokens/input/design-tokens.json`,
  which ships an explicit light set with semantic names (`bg primary`, `bg blue secondary`,
  `border`, `text`, `inactive`, `disabled`) plus an `l80..base..d80` ramp per hue. KONE marks
  `bg green` / `bg orange` / `bg red` as **"(don't use)"** — those are avoided. A complete,
  contrast-audited palette already exists as the preview override; **lift it rather than
  re-derive it.**

- **D-30 (NEW) — the contrast audit is a committed, runnable check, not an eyeball pass.**
  Acceptance is **every text/background pair ≥ 4.5:1 and every non-text mark ≥ 3.0:1,
  demonstrated by computation.** The preview's audit covers 20 pairs and all pass; it must be
  re-run against the **final** `dashboard.css` and its output must be reproducible by anyone
  who checks out the repo.

- **Three palette-adjacent defects found while building the preview, all in scope:**
  - `.is-stale` is a white 6%-alpha hatch — **invisible on pale fills.** Needs dark ink. It
    must stay `background-image`-only, because D-15 composability depends on that.
  - `.brand-logo` sits on a white chip for contrast against the navy topbar; on a white page
    that chip is invisible padding.
  - Panels using `--color-surface-raised` become white-on-white and need a border.

### Palette — resolved at plan time from research findings

Both of these close a **computed contradiction between two locked decisions**, surfaced by
`11.1-RESEARCH.md`. They are operator-chosen, not planner discretion.

- **D-38 (NEW, operator-chosen):** the state tokens are **three tiers, not two.** D-28 names
  only `--state-*` (saturated mark) and `--state-*-fill` (pale background); D-29 requires a
  d-shade for anything rendering a state as text or an icon. A literal two-tier reading
  cannot satisfy both, because on white `green.base` is 2.00:1 and `orange.base` 2.04:1 as
  text. A third **`--state-*-ink`** tier carries the d40 shades (`--state-ok-ink: #087827`,
  `--state-crit-ink`/`--state-down-ink: #a14120`, `--state-unknown-ink`/`--state-unreach-ink`:
  `#a1681d`, `--state-pend-ink`/`--state-stale-ink`: `#141414`). This is a minimal extension
  of D-28's own naming convention and **preserves D-28's zero-JavaScript-change promise** —
  the saturated `--state-*` values are untouched, so the connection dot's inline assignment,
  the Phase 12 gauge arcs and the Phase 13 map nodes all keep reading what they read today.

- **D-39 (NEW, operator-chosen):** the **connection dot gets a border ring.** The dot is an
  8px circle inline-styled to `var(--state-ok)`; against a white topbar that measures
  **2.00:1**, so as designed it **cannot pass D-30's own "every non-text mark >= 3.0:1"
  criterion**. Ship a 1px ring (`--color-border`, or the matching `--state-*-ink` d-shade)
  around the dot: the mark gains a compliant edge while keeping the saturated fill D-28
  protects, and the audit passes honestly rather than by exception. Do **not** desaturate the
  dot and do **not** record this as a waived exception.

  **Note for D-30's audit:** the audit must therefore check the dot's *ring*, not its fill,
  as the mark's contrast-bearing edge. Research also computed that `--state-down`
  (`#f51414`, 4.21:1 on white) is the tightest colour in the palette and that
  `grayscale."300 disabled"` (`#959595`) sits exactly at 3.00:1 — both need to be asserted
  explicitly rather than assumed.

  **Yellow has no `l80..d80` ramp** in KONE's tokens — only the single flat `#ffe141`. The
  derivation of `--state-warn-fill` is left to the planner (research proposes an ~18%
  yellow-on-white alpha blend, `#fff9d9`), provided D-30's audit covers the result.

### Panes

- **D-26 (operator, locked):** panes get **drag handles AND collapse buttons** — chosen over
  collapse-only and over drag-without-persistence.
  - **Splitter bars** between the panes, draggable.
  - **A collapse control** (chevron) on each pane.
  - **Keyboard equivalence is mandatory, not optional.** A focused splitter resizes with
    arrow keys; the collapse control is a real `<button>`. Without this it is a **WCAG 2.1.1
    failure**, and it would undo the keyboard work already done in Phase 11
    (`shell.js` `handleKeydown`).
  - Each splitter gets `role="separator"` with `aria-orientation` and `aria-valuenow`, so
    assistive technology reports the pane size rather than an unlabelled div.

- **Persistence (locked by D-26):** the operator chose the option that remembers sizes. That
  makes the **guarded-storage precedent mandatory, not advisory.** `localStorage` access
  **THROWS** (it does not return null) when site data is blocked, and that already took down
  the whole shell once during Phase 11 (`render-shell.js` `groupingMode()`). The rule
  established by that fix applies unchanged: **an in-memory value is the source of truth for
  the session, storage is only how it survives a reload, and a refused write must never break
  the interaction.**

- **Interaction with the clock (locked by D-26):** `tick()` currently preserves scroll and
  focus for `#sidebar-tree`, `#sidebar-events` and `#main`. Resizable panes change **which
  elements scroll**, so that list must be revisited — and **a resize must not be undone by
  the next tick.**

### Grouping control

- **D-32 (NEW):** the two-state "Group by type" toggle button is replaced by
  **a `<select>`** offering `Group by type` / `Group by folder`, **plus a checkbox
  "Order by severity"**. When the checkbox is on, devices and groups with the most severe
  hosts sort to the top. Four binding constraints:
  - The select must be **extensible** — the operator explicitly anticipates more filters
    later. It must not be hard-coded to exactly two options.
  - `grouping.js` **already provides** `SEVERITY_RANK`, `effectiveState` and `rollUpGroup`.
    The ordering primitive exists; use it rather than writing a second one.
  - Both controls follow the **same guarded read + in-memory override** pattern the current
    toggle uses (`groupingModeOverride`), for the reason in D-26's persistence note.
  - `renderTree()` **rebuilds on every store change**, so sort order must be **derived on
    each rebuild**, never held in the DOM — this is the exact trap the Phase 11 tree-collapse
    work hit. And the tree's `collapsedGroupKeys` **must survive a re-sort.**

### Carried-over defects

- **D-33 (NEW) — event ordering: VERIFY, do not "fix".** The operator reported
  oldest-events-on-top. **The shipped code is correct.** `renderEvents()` reverses because
  `mqtt_poller.py` appends chronologically (`state.events + events_this_cycle`), and the
  function carries a comment saying so. The fault was in the **preview harness's** synthetic
  feed, which reversed the array before publishing and cancelled the display reversal out.
  **Action: confirm newest-first against the LIVE poller, and add a regression test that
  pins the ordering contract. Do NOT reverse the render again.**

- **D-34 (NEW) — a stale flip toggles classes; it does not rebuild structure.** A page-wide
  clock now re-renders time-derived surfaces every 12s, because nothing re-rendered when the
  poller stopped publishing — the one moment staleness matters is the one moment guaranteed
  to produce no new message. But `renderTree()` and both view modules answer a poller-stale
  flip with a **full rebuild**, each justified in-comment as "an infrequent event". **The
  clock made that premise false.** Scroll and focus preservation around `tick()` was the
  contained fix; the right design is for a stale flip to **toggle `.is-stale` on existing
  nodes**. That touches all three modules' render paths, which is why it lives here and not
  in a defect fix. **Also revisit `CLOCK_TICK_MS` (12s)** once panes are resizable — a taller
  tree means more nodes per tick.

- **D-35 (NEW) — an event row must identify its device.** From a live screenshot: at 280px
  of sidebar, `.event-device-name` truncates to `1...` for **every** host, because they are
  all `192.168.0.x` and the distinguishing part is at the END. The row becomes unreadable
  exactly when it matters. Moving the event panel to the centre widens it and largely fixes
  this **by accident — do not rely on that.** Make it a requirement: middle-truncation
  (`192.168…213`), preferring the alias, or a tooltip.

- **D-37 (NEW) — deployment doc, not a code change.** `dashboard/js/config.js` still ships
  `CHECKMK_BASE_URL = "http://<HOST_IP>:8080"` on the live deployment. The "View in Checkmk"
  link correctly disables itself while that placeholder is present (D-20), so it looks broken
  until an operator edits it. Surface this in the deployment doc **more prominently than it
  currently is.**
