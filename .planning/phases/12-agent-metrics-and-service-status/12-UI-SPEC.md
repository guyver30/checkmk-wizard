# Phase 12 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Scope Boundary (read first)

Per `12-CONTEXT.md`'s Canonical References ("Integration Points"), this phase's sole UI
integration point is `dashboard-react/src/routes/DetailsRoute.tsx`, and its scope is
explicitly three additions: **the gauge row, the SMART badge, and the service `Table`**.

This contract covers exactly those three additions, plus the minimum page chrome
(header/title, not-found/empty states) needed for the route to be usable on its own.

**Explicitly NOT re-specified here** (flagged, not silently assumed complete):
- The bounded per-device status-history strip and the "link out to Checkmk's own UI"
  (originally DASH-03, Phase 11 scope). `DetailsRoute.tsx` is currently a bare stub with
  neither built — `REQUIREMENTS.md`'s traceability table still lists DASH-03 as Pending
  against the vanilla (pre-React-pivot) dashboard. Whether DASH-03's React implementation
  is silently folded into this phase or remains a separate follow-up is a planning decision,
  not a design-contract one — flagged for the planner/orchestrator to confirm explicitly.
  `CHECKMK_BASE_URL` / `isCheckmkLinkConfigured()` already exist in `lib/config.ts` (D-20)
  ready to be consumed whenever that link is built.
- Navigation INTO `/details?id=` (e.g. making `Tree`/`TreeNode` rows clickable). No such
  wiring exists today (`TreeNode.tsx` device rows have no `onClick`); the route is reachable
  only via a bookmarked/typed `?id=` URL (D-19/D-41). Not this phase's stated scope per
  Canonical Refs, but the feature is unreachable from the UI without it — flagged for the
  planner to confirm ownership (this phase, or a fast-follow).

**Correction to `12-CONTEXT.md` D-10's component name:** D-10 says "kone-design-system's
existing `Table` component (exported alongside `StatusBadge`...)". `Table` is correct.
`StatusBadge` is NOT the right badge for the service list: `kone-design-system`'s own
`StatusBadge` (`Badge.tsx`) has a fixed status enum of `connected | low-signal | entrapment |
unknown`, which does not cover Checkmk's `OK/WARN/CRIT/UNKNOWN` service states. The
established, tested pattern for rendering a Checkmk state is `StateBadgeForState` (
`dashboard-react/src/components/StateBadge.tsx`, driven by `stateMapping.ts`'s
`badgeForState()`) — this is also what `TreeNode.tsx` already uses for device state. Use
`StateBadgeForState(state)` for every service row's status cell, not the design-system's
`StatusBadge`.

## Spacing Scale

The project's Tailwind config remaps `text-*` sizes to CSS vars (see Typography) but spacing
utilities are plain Tailwind defaults (4px base unit). Existing components already use
compact half-steps (6px, 10px) for dense controls — declared here as inherited exceptions,
not reintroduced by this phase.

| Token | Value | Usage (this phase) |
|-------|-------|-------|
| xs | 4px | Badge dot/icon gaps (inherited from `Badge`/`StateBadge`, not new) |
| sm | 8px | Gap between a gauge ring and its label; gap between the two Disk-column badges |
| md | 12px | Service `Table` cell padding (`px-3 py-2.5`/`py-3`, matches the existing `Table` component exactly — do not override it); gap between gauge-row card and the service `Table` below it |
| lg | 16px | Page-level side padding on `DetailsRoute`'s `<main>` |
| xl | 24px | Gauge-row card internal padding (top/bottom/sides) |
| 2xl | 32px | Gap between the three gauge columns (CPU / RAM / Disk) on desktop widths |

Exceptions: `Table`'s own internal padding (`px-3 py-2.5` header, `px-3 py-3` body — 10px/12px)
and `Badge`'s internal padding (`px-2.5 py-1` — 10px/4px) are inherited from
`kone-design-system` verbatim; do not re-pad rows/badges at the call site.

## Typography

The project's Tailwind config maps `text-*` utilities to `design-system/src/tokens.css`
custom properties, which do **not** match Tailwind's own defaults — `text-sm` is 13px here,
not Tailwind's stock 14px. Use the utility classes below, not raw pixel values.

| Role | Size | Weight | Line Height | Utility |
|------|------|--------|-------------|---------|
| Body / service output | 13px | 400 (regular) | 1.5 | `text-sm` (no explicit font-weight class) |
| Label (gauge captions, badge text) | 13px | 600 (semibold) | 1.4 | `text-sm font-semibold` |
| Heading (device title) | 20px | 600 (semibold) | 1.2 | `text-xl font-semibold` |
| Display (gauge value — see override below) | 28px | 600 (semibold) | 1.2 | `text-2xl font-semibold` |

**Gauge value override (new for this phase):** `ProgressCircle`'s built-in `showValue` prop
renders the percentage at a fixed `text-xs font-medium` (12px) — too small to serve as the
"headline" number the DMC-server.png reference and D-01/D-04 call for. Do not modify
`Progress.tsx` (shared library component, out of this phase's scope). Instead: render
`ProgressCircle` with `showValue={false}`, wrap it in a `relative` container, and overlay a
custom `absolute inset-0 flex items-center justify-center text-2xl font-semibold
text-fg-primary` span showing `{value}%`. This is the same "wrap a primitive with extra
markup" pattern `StateBadge.tsx` already uses around `Badge`.

Font weights used project-wide: 400 (default/unstyled), `font-medium` (500, inherited from
existing `Badge`/icon usage — do not introduce new 500-weight uses this phase), and
`font-semibold` (600). This phase's new elements use only 400 and 600, per the table above.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#ffffff` (`--neutral-0`, `bg-canvas`/`bg-surface`) | Page background, gauge-row card background, `Table` background |
| Secondary (30%) | `#f2f2f4` (`--neutral-100`, `bg-subtle`); `#e2e2e7`/`#d5d5dc` (`--neutral-150`/`--neutral-200`) for hairline borders | `Table` row dividers/hover, gauge-row card's subtle inner divider (if used), the "no data" placeholder background |
| Accent (10%) | `#1450f5` (`--blue-500`, `--color-fg-brand`) | Reserved for: focus rings on interactive elements (inherited from the design system's global focus style), and — if the deep-Checkmk-link is added in this phase's scope — the link/button itself. **Never** used for gauge rings: gauges signal metric health, and brand blue would visually compete with the success/warning/danger severity meaning already established for state (D-11's colors). |
| Destructive | `#e5252a` (`--red-500`, `--color-fg-danger`/`bg-alert`) | CRIT-state service badges, danger-state gauge rings (D-04, value ≥ crit threshold), SMART-fail badge. No destructive *action* exists in this read-only phase (no delete/confirm buttons). |

Gauge ring color (D-04) uses the existing `ProgressColor` set from `Progress.tsx` —
`success` / `warning` / `danger` — chosen by comparing the gauge's own `perf_data` value
against ITS OWN warn/crit thresholds (same technique as D-01's disk gauge), never the
Checkmk service's own OK/WARN/CRIT state. Exact CPU/RAM `perf_data` field names and
thresholds are flagged for research (per `12-CONTEXT.md`'s "Claude's Discretion"); the
color-selection rule itself (below-warn → `success`, warn-to-crit → `warning`, ≥crit →
`danger`) is locked by this contract regardless of what research finds.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | None in this phase's scope (read-only view, no form submission). If the Checkmk deep link is built here (see Scope Boundary), its label is **"View in Checkmk"**, opening in a new tab. |
| No device selected (`?id=` absent) | Heading: **"No device selected"** · Body: **"Choose a device from the fleet tree to view its live metrics and service status."** |
| Device not found (`?id=` set, no matching device in the store) | Heading: **"Device not found"** · Body: **"No device with ID '{id}' is currently known. It may have been removed, or the ID may be mistyped."** |
| No agent metrics at all (CPU, RAM, AND Disk services all absent — e.g. a pure network device) | **"No agent metrics available for this device."** — replaces the entire gauge row (new for this phase; per-gauge hiding per D-03/D-06 still applies when only SOME are absent) |
| Service list empty (every service on the host is one of the four gauge-backed services) | **"No additional services."** (single centered row inside the `Table`'s body area, not an error) |
| Service data not yet arrived (device known, `lan/devices/{id}/services` retained message not yet received) | **"Service data has not arrived yet — it should appear within one poll cycle."** |
| Error state | This phase has no user-triggered actions that can fail (no writes, no forms) — "error state" reduces to the not-found/no-data states above. No additional error copy needed. |
| Destructive confirmation | Not applicable — no destructive actions exist in this phase. |

**"Other mounts" badge wording (D-01, new copy):** `"Other mounts: {value}% used"`, colored by
the same success/warning/danger thresholds as the headline Disk gauge. Hidden entirely (not
shown as 0% or N/A) when `/` is the host's only `Filesystem *` service — same hide-on-absence
rule as D-03/D-06.

**SMART badge wording (D-07, Claude's discretion — resolved):** Use a count in BOTH the
pass and fail cases, for a consistent, scannable format: **"SMART: Pass (2/2)"** /
**"SMART: Fail (1/2)"**. (Rejected the bare "SMART: Pass" alternative — an operator glancing
at the badge should not have to infer whether "Pass" covers one disk or five.)

## Layout & Component Inventory (supplementary — not a template section, kept for executor clarity)

**Page chrome:** `<main>` with `px-4` (16px) side padding. Heading: device alias/id (`text-xl
font-semibold`) plus a `StateBadgeForState` for the device's current overall state next to it
(reuses the existing device-state pattern from `Tree`/`TreeNode`, so a device's health reads
the same way everywhere in the app).

**Gauge row card:** a `bg-bg-surface` block, `rounded-lg` (`--radius-lg`, 16px — the same
token already used for "snackbar & message cards"), `shadow-card`, `p-6` (24px) padding.
Inside: a `flex flex-row flex-wrap items-start justify-center gap-8` (32px) row of up to three
gauge columns (CPU, RAM, Disk), each column a `flex flex-col items-center gap-2` (8px) of:
the overlaid `ProgressCircle` (see Typography's "Gauge value override"), the label below it
(`text-sm font-semibold`, "CPU"/"RAM"/"Disk"), and — Disk column only — the "Other mounts"
badge and the SMART badge stacked below the label with `gap-1` (4px). Missing gauges (D-03)
are simply omitted from the row (flex naturally re-centers the remainder); if all three are
missing, the whole card is replaced by the "No agent metrics available" message.

**Suggested gauge size:** `size={96} strokeWidth={8}` — large enough to read as a headline
metric (matching the DMC-server.png reference's visual weight) without overwhelming the
13-16px body-text scale the rest of the dashboard uses.

**Service table:** `kone-design-system`'s `Table`, columns `Service` (name, not sortable),
`Status` (`StateBadgeForState`, not sortable), `Output` (`plugin_output` text, `text-sm`,
allowed to wrap — do not truncate, D-09's whole point is answering "why" without a
click-through). No `onSort`/`sortKey` — ordering is fixed worst-first per D-09, not
user-resortable. Row order: CRIT, WARN, UNKNOWN, then OK (ties broken by service name for
stable rendering).
