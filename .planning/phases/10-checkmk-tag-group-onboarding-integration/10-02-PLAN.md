<objective>
Give the wizard the ability to create the `device_type` host tag group exactly once, with `other` first so every pre-existing host defaults safely, and to report how many hosts that default touched.

Purpose: TAG-01. PITFALLS.md Pitfall 8 is that a new Checkmk tag group silently assigns its first value to every existing host — this plan turns that landmine into a deliberate, reported safe default (D-06, D-08). PITFALLS.md Pitfall 9 is a wrong REST payload shape; plan 10-01 already resolved the real shape against the live site, so this plan writes against a confirmed contract rather than a guess.
Output: two new `CheckmkClient` methods, a validated config loader, an idempotent provisioning helper wired into the wizard flow, and unit coverage for all of it.

Terminology reconciliation: ROADMAP.md SC1 calls the neutral default `unknown`. CONTEXT.md D-06 supersedes that — the neutral value is the string `other`, and what actually matters is that it occupies first position in the tag list. This plan implements `other`; plan 10-06 fixes the upstream wording.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `device_types.json` (checked-in file) -> wizard process | Untrusted-shaped input: an operator may edit or reorder this file, and its first element silently determines the tag value applied to every pre-existing host |
| Wizard -> Checkmk REST API | Authenticated write of site-wide monitoring configuration (a new tag group affecting every host) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-10-05 | Tampering | `_load_device_types()` reading `device_types.json` | mitigate | Validate that the parsed value is a non-empty list of strings whose element 0 is `other`, and raise a `ValueError` naming the path otherwise. A reordered file must abort the run, not silently assign a real device type (e.g. `ACS`) to every pre-existing host. This is PITFALLS.md Pitfall 8's prescribed fix |
| T-10-06 | Tampering | `_ensure_device_type_tag_group` re-running on an existing site | mitigate | Gate creation on `get_host_tag_group` returning 404. RESEARCH.md's anti-pattern list notes a second POST for an existing id either errors or silently replaces the tag list in undocumented ways — never POST unconditionally |
| T-10-07 | Denial of Service | Wizard run aborting on a tag-group provisioning failure | mitigate | Wrap create and count in `except CheckmkAPIError` and print a warning, matching every other provisioning step in `wizard.py`; a monitoring-metadata failure must not strand a half-onboarded site |
| T-10-08 | Information Disclosure | `CheckmkAPIError` text printed on tag-group failure | accept | `CheckmkAPIError` carries method/url/status/body, never the Bearer secret (the header is set once in `CheckmkClient.__init__` and is not part of the exception payload) — same exposure already accepted at every existing `except CheckmkAPIError` print site |
| T-10-SC | Tampering | npm/pip/cargo installs | mitigate | No packages are installed by this plan; `httpx` is a pre-existing pinned dependency and 10-RESEARCH.md's Package Legitimacy Audit records no new install, so no legitimacy checkpoint applies |
