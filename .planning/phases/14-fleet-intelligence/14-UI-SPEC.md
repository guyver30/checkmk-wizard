# Phase 14 — UI Design Contract

> Visual and interaction contract for the incident card list (DASH-14), the dimmed-consequence
> treatment in the tree and topology map (DASH-15), the criticality-tier/per-service-criticality/
> depends-on editor bolted onto the existing "Edit topology" mode (DASH-16), and kiosk/wall mode
> (DASH-17). Generated by bm-ui-researcher from `14-CONTEXT.md` (D-04 through D-14), `14-RESEARCH.md`,
> and the live `dashboard-react/` codebase (kone-design-system, light palette, established since
> Phase 11.1; the Edit-topology/Apply flow established in Phase 13).
>
> **This spec covers only what Phase 14 adds.** State palette, staleness treatment, spacing scale,
> typography roles, the base color system, the map's canvas rendering conventions, and the
> Edit-mode/Apply/idle-timeout machinery are inherited **unchanged** from Phase 11/11.1/13
> (`stateMapping.ts`, `design-system/src/tokens.css`, `13-UI-SPEC.md`) — this document cites their
> exact values rather than re-deriving a second palette or a second edit-mode contract.
>
> **Auto-mode note:** produced without user questions per the orchestrator's Auto Mode (`--auto`
> passed through from `/bm:plan-phase`). Every discretionary call this spec makes is logged in
> "Auto-Mode Design Decisions" at the end, with its rationale, for the checker/planner to audit.

## Spacing Scale

Inherited from the established `dashboard-react` scale (Tailwind defaults + the existing 12px
exception already in use by `GroupingControls`/`TreeNode`/`TopologyToolbar`). No new spacing token
is introduced by this phase.

| Token | Value | Usage in this phase's new UI |
|-------|-------|-------------------------------|
| xs | 4px | Gap between an incident card's icon badge and its title text; gap between a criticality `Badge` and the host label next to it |
| sm | 8px | Gap between stacked incident cards (`gap-2` in the `IncidentList` column); gap between the criticality `Select` and the "Set" action in the per-service criticality row |
| md | 12px | `IncidentList`'s own wrapper padding (`p-3`) — same inherited exception as `GroupingControls`/`TopologyToolbar`'s `p-3`, not a new one |
| lg | 16px | Gap between the `IncidentList` and the toolbar+map stack below it (`gap-4`), matching the existing `centreTop` `gap-2`→`gap-4` pattern already used between `StatsStrip` and the toolbar |
| xl | 24px | Not used by this phase's new UI |

Exceptions: none beyond the inherited 12px.

## Typography

Reuses the four size/weight roles already established (`--font-size-*` tokens, Tailwind
`text-xs`/`text-sm`/`text-xl`/`text-2xl` utilities, as used in `TreeNode.tsx`, `Message.tsx`,
`DetailsRoute.tsx`). No new size or weight is introduced.

| Role | Size | Weight | Line Height | Usage in this phase |
|------|------|--------|-------------|----------------------|
| Label | 12px (`text-xs`) | 400 | 1.5 | Incident card's duration/timestamp line; consequence-count text ("4 confirmed down, 2 not observable"); confidence/history-span footnotes are NOT part of this phase (that belongs to 14.2) |
| Body | 13px (`text-sm`) | 400 | 1.5 | Incident card description body (`Message`'s own `text-sm`, unchanged); criticality-editor labels; depends-on `MultiSelect` labels; kiosk rotation status text |
| Heading | 20px (`text-xl`) | 600 | 1.2 | Not used by new UI this phase introduces — carried for contract completeness (matches the app-wide 4-role set; inventing a use here was not needed) |
| Display | 28px (`text-2xl`) | 600 | 1.2 | Not used by this phase's new UI |

`Message`'s built-in title styling is `text-sm font-semibold` (Body role, semibold) — this phase
does not override it to Heading size; an incident card is a compact list item, not a page header,
and a fleet with several simultaneous incidents must not force the operator to scroll past
oversized cards (kiosk-mode legibility is handled instead by the kiosk-mode font-scale rule below,
not by inflating every card's own type role).

**Kiosk-mode font-scale exception (D-14, discretionary):** on `?kiosk=1` only, the `IncidentList`
and `TopologyMap` panes render inside a wrapper with `text-[1.15em]` (≈ a single, app-wide
15%-larger step applied via a CSS custom-property multiplier, not a new named size token) so a
lobby screen viewed from several metres away stays legible without inventing a fifth type role.
This is the **only** typography deviation this phase makes from the four inherited roles.

## Color

Light theme throughout (unchanged, kone-design-system default). Every hex below is read directly
from `design-system/src/tokens.css` and `design-system/src/components/Badge.tsx`'s `colorMap` —
**not re-derived** — so this phase's new UI stays byte-identical to the app's existing DOM colors.

```css
/* Already-defined tokens this phase reads, does not redefine: */
--color-bg-canvas-default: #ffffff;         /* neutral-0 */
--color-bg-surface-subtle-default: #f2f2f4; /* neutral-100 */
--color-brand-default: #1450f5;             /* blue-500, "KONE Blue" */
--color-alert-default: #e5252a;             /* red-500 */
--neutral-400: #96969f;
--neutral-600: #55555f;
```

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#ffffff` (`--color-bg-canvas-default`, neutral-0) | Page/pane background, unchanged — the `IncidentList` sits directly on this, no card-level surface tint of its own beyond `Message`'s existing `bg-bg-surface` (also `#ffffff`) |
| Secondary (30%) | `#f2f2f4` (`--color-bg-surface-subtle-default`, neutral-100) | The criticality/dependency editor panel's background (matches `TopologyToolbar`'s existing `bg-bg-subtle` row); the kiosk-mode status footer background |
| Accent (10%) | `#1450f5` (`--color-brand-default`, "KONE Blue") | **Reserved for, and only for:** (a) the criticality tier's own "critical" badge is explicitly **not** this color (see Color's Criticality Tier Palette below — accent must never be reused for a severity/business-priority meaning, unbroken since Phase 11 D-11); (b) the "Set" / "Save" action buttons inside the criticality/dependency editor (`Button variant="primary"`, same component, same reserved role Phase 13 already established); (c) kiosk mode's rotation-progress indicator (a thin animated bar showing time-until-next-rotation — decorative chrome only, never a status signal); (d) focus outline on every new interactive element (inherited global rule) |
| Destructive | `#e5252a` (`--color-alert-default`, red-500) | **Reserved for, and only for:** the "confirmed down" consequence count/label inside an incident card (this **is** a legitimate destructive/danger-adjacent use — it reports an actually-down device, the same semantic `StateBadgeForState state="DOWN"` already carries); the "Remove dependency" action in the depends-on editor (mirrors Phase 13's `window.confirm()`-gated delete-edge pattern) |

Accent is never reused for node/incident **severity or business-criticality** meaning — this rule
was locked by Phase 11 D-11 and Phase 13's Color section, and this phase's new criticality-tier
palette (below) is a **second, independent** color dimension from device state, so the same
discipline applies doubly here: a criticality tier must never borrow the state palette's hues
either (an operator must not read "critical" tier as "CRIT state" at a glance).

### Criticality Tier Palette (D-05/D-09, Claude's discretion — new this phase)

Four tiers (`low` / `medium` / `high` / `critical`, per `14-RESEARCH.md`'s Label Design section).
`Badge`'s existing `color` prop has exactly one spare, state-unclaimed hue after OK/WARN/CRIT-DOWN-
UNREACH/UNKNOWN/STALE (green/orange/red/black/neutral) are all already claimed by the state
palette: **`purple`** (`--purple-500`, `#7c6cf0`). Rather than inventing a second red/orange scale
that would collide with the state palette's own danger colors (the exact confusion D-04/D-05 exist
to prevent — a "critical" business tier must never be mistaken for a "CRIT" monitoring state), this
phase uses **`Badge`'s neutral/purple pair plus outline/soft/solid variant weight** to express four
tiers with only one new hue:

| Tier | `Badge` color | `Badge` variant | Rationale |
|------|--------------|------------------|-----------|
| `low` | `neutral` | `outline` | Lightest weight — matches the "unset defaults to low" rule (14-RESEARCH.md Label Design) so an un-triaged host reads as quiet chrome, not an alarming color |
| `medium` | `neutral` | `soft` | Same neutral hue, heavier fill — one step up without introducing a new color |
| `high` | `purple` | `soft` | First use of the reserved spare hue — a deliberate, state-palette-distinct color |
| `critical` | `purple` | `solid` | Same hue, maximum fill weight — the most visually dominant tier, still never red/orange/green |

This exactly mirrors the state palette's own "same hue, escalating variant weight" trick already
used for CRIT/UNREACH/DOWN (`soft`/`outline`/`solid` on the same `danger` red) — reusing an
established pattern rather than inventing a new one, per this codebase's own convention.

### Dimmed Consequence Treatment (DASH-15, new this phase)

A consequence host (in the tree, `TreeNode`'s device row) or node (on the map, vis-network) is
**dimmed, not hidden, and does not carry its own alarm styling** while its incident is open:

| Surface | Dimming mechanism |
|---------|---------------------|
| Tree (`TreeNode.tsx` device row) | `opacity-50` on the row's `<Link>` (Tailwind utility, no new token); the row's own `StateBadgeForState` is replaced with a small neutral `Badge` reading "See incident" (see Copywriting) rather than its raw DOW/UNREACH badge — this is the "does not raise an alarm of its own" half of DASH-15, not just a visual fade |
| Map (vis-network node) | `opacity: 0.4` on the node's `image` and a flat `#96969f` (`--neutral-400`) border, overriding the State palette's per-state border rule from `13-UI-SPEC.md` for consequence nodes only — the root of the same incident keeps its full-opacity, full-alarm styling unchanged |

Clicking a dimmed row/node still navigates to `/details?id={id}` as normal (D-12 says it "points to
the incident instead of raising an alarm," not "becomes unclickable") — the click target additionally
carries an incident deep-link (`/?incident={incidentId}` scrolls/highlights the matching card in the
`IncidentList`, discretionary — see Auto-Mode Design Decisions) rather than only going to the device
detail page, so an operator investigating a dimmed device is one click from the incident that
explains it.

**Only the incident's root** (in the tree and on the map) keeps full-opacity, full alarm styling —
this is the literal DASH-15 requirement ("Only the incident's root shows alarm styling").

## Incident Card List (DASH-14)

**Component:** `IncidentList` renders `IncidentCard[]`, each `IncidentCard` a thin wrapper around
`kone-design-system`'s `Message` component (title/description/icon/status — the closest existing
primitive, per Design System above; no new card primitive is built).

**Per-card mapping onto `Message`'s props:**

| `Message` prop | Value |
|---|---|
| `status` | `"danger"` if the incident has any `confirmed_down` consequence or the root itself is DOWN (not just UNREACH/inferred); otherwise `"warning"` (an all-`not_observable` incident, including every purely-inferred case) — this status choice is itself evidence-respecting: an incident composed entirely of "not observable" hosts must never render with the same visual alarm weight as one with a confirmed-down device |
| `title` | The root line + inferred marker (see Copywriting) |
| `description` | The consequence summary line + worst-affected criticality badge, stacked |
| `icon` | Reuses the device-type icon of the incident's root host (`deviceTypeMaskUrl`, `mapIcons.ts`) at 16px — not a new glyph |
| `onConfirm`/`onCancel` | Neither wired by default (an incident card is not a confirm/cancel dialog); the optional "View devices" expand action (see Copywriting) is a plain inline `<button>` inside `description`, not `Message`'s own confirm slot, to avoid implying the card itself needs confirming |

**Placement (Layout Integration, new):** `IncidentList` sits **above** `StatsStrip`, inside the same
`centreTop` flex column `IndexRoute.tsx` already owns — i.e. the vertical order becomes
`IncidentList → StatsStrip → TopologyToolbar → TopologyMap`. Rationale: DASH-14 says "above the
primary view," and the primary view is the map (with the stats strip already "above" it per DASH-01)
— stacking the incident list as the new outermost-top layer keeps every existing element's own
"above" relationship intact rather than renumbering them.

**Ordering (D-12, locked):** cards sort by **worst criticality tier (descending), then duration
(descending — longest-open first)** — reuses `CRITICALITY_TIERS`'s ordinal index exactly as
`14-RESEARCH.md`'s Pitfall 4 prescribes (one source-of-truth rank table, no ad-hoc comparator).

**Empty state:** when zero incidents are open, `IncidentList` renders the Copywriting Contract's
"No open incidents" heading/body (small, Label-size body text, no `Message` wrapper — an empty
list should read as quiet chrome, not its own alarm-shaped card) and takes minimal vertical space
(no reserved height when empty, matching `TopologyToolbar`'s own "collapse to nothing extra" rule
for its Banner/Button in read-only mode).

**Data source:** subscribes to the new `lan/incidents/+/status` retained topic (per `14-RESEARCH.md`
Pattern 3/Code Examples) via a new Zustand `incidents` slice, wholesale-replace convention
(matches `devices`/`topology`).

## Criticality & Dependency Editor (DASH-16)

**Placement:** this is **not** a separate edit mode. It lives inside the **existing** "Edit
topology" `Switch` (Phase 13's `TopologyToolbar`) — turning that switch on reveals both the
existing map manipulation toolbar (Phase 13, unchanged) **and** a new collapsible panel titled
"Criticality & dependencies" beneath it, scoped to whichever host is currently selected on the map
or clicked in the tree while in edit mode. Reusing the single toggle (rather than adding a second
"Edit criticality" switch) matches D-06's instruction to keep this "the existing Phase 13 edit
mode," not a parallel one, and keeps the idle-timeout/pending-count/Apply machinery singular.

**Panel contents, top to bottom** (all `kone-design-system` primitives, no new component):

1. `Select` — "Host criticality" (four options, Criticality Tier Palette's display labels)
2. A small `Table`-free repeating row per gauge/status-visible service on the selected host —
   each row: service name (plain text) + `Select` — "Per-service criticality" (same four options)
3. `MultiSelect` — "Depends on" (every other known host id, searchable per the component's own
   doc comment)

**Selection model:** the panel only appears once a host is selected (map node click, or tree-row
click, while edit mode is on) — there is no "edit every host's criticality in one giant list" view
this phase; that would duplicate Checkmk's own per-object editing model this project has
consistently avoided rebuilding (per the Out of Scope table's "editable device metadata" history).

**Write path (generalizes, does not duplicate, Phase 13's `checkmkWrite.ts`):** every field change
calls a shared `updateLabels(host, mutate)` helper (per `14-RESEARCH.md`'s Don't-Hand-Roll table,
generalizing `updateHostAttributes`'s existing label-merge shape) and increments the **same**
`pendingCount` state `IndexRoute.tsx` already tracks for map edits — a criticality change and a
map-position drag both count toward the one "N changes not yet applied" `Banner` and are cleared
by the one "Apply changes" `Button`. No second pending-counter, no second Apply button.

**Field-level feedback:** each `Select`/`MultiSelect` write is optimistic (updates the panel's own
local state immediately) and best-effort against the network (mirrors `TopologyToolbar`'s existing
`countPendingChanges` best-effort pattern) — a failed individual field write surfaces via the same
`Snackbar` error-copy pattern (see Copywriting's Error state row), not a per-field inline error,
keeping this consistent with how map-edit failures already surface.

## Kiosk / Wall Mode (DASH-17)

**Entry (D-14, discretionary, resolved here):** `?kiosk=1` query parameter on the existing `/`
route (`IndexRoute`), not a new route path — this is a rendering mode of the same page, per
`14-RESEARCH.md`'s recommendation, so the kiosk view and the operator view can never drift into
two different incident/map implementations.

**Chrome removed under `?kiosk=1`:**
- `AppNav` (`NavBar`) does not render at all.
- The device tree pane, the event-history pane, and pane splitters do not render — kiosk mode is
  full-bleed `IncidentList` + `TopologyMap` only, no `ThreePaneLayout` grid.
- The "Edit topology" `Switch`/toolbar does not render — kiosk mode is read-only by construction,
  independent of `isTopologyEditingConfigured()`'s own gate (defense in depth: even a configured
  editor credential must not expose write controls on an unattended public screen).

**Rotation (D-14, discretionary):** a `useKioskRotation` hook (mirrors `useNowTick`'s "the app's
one periodic timer" role, per `14-RESEARCH.md`'s Don't-Hand-Roll table — this is the **second**
sanctioned timer, gated so it only ever mounts under `?kiosk=1`) alternates the full-bleed view
between `IncidentList` (full height, scrollable if it overflows) and `TopologyMap` (full height)
every **20 seconds** (discretionary default — see Auto-Mode Design Decisions), with a 300ms
opacity-crossfade transition (Tailwind `transition-opacity`, no new animation library). The
Copywriting Contract's small rotation-status label and a thin Accent-colored progress bar
(bottom edge, `width` animated 0→100% over the 20s) indicate which view is showing and how soon it
rotates — chrome, not data, so it never competes with the state/criticality palettes above.

**Fullscreen (Pitfall 3, locked mitigation):** the CSS chrome-free layout above satisfies "no
navigation or edit controls" unconditionally, with no user gesture required. A one-time "Enter full
screen" `Button` (see Copywriting) additionally calls `Element.requestFullscreen()` on click for
the true edge-to-edge case; it is **not** auto-invoked on mount (browsers reject that). The
deployment doc must additionally document launching the browser itself in OS-level kiosk mode
(`chromium --kiosk <url>?kiosk=1`) as the real, sanctioned path for permanently-mounted signage —
this UI-SPEC's fullscreen button is a convenience for ad-hoc use on a shared machine, not the
primary mechanism.

**Idle-timeout note:** kiosk mode never enters Edit-topology mode (the switch does not render), so
`useEditIdleTimeout`'s 5-minute auto-exit is structurally unreachable here — no interaction with
that mechanism to reason about.

## Layout Integration

`ThreePaneLayout`, the sidebar tree, `StatsStrip`, `TopologyToolbar`, `TopologyMap`, and
`EventHistory` are **unchanged in structure** for the non-kiosk route — this phase's only DOM
changes to existing files are:
1. `IndexRoute.tsx`'s `centreTop` gains one new element (`<IncidentList />`) above `<StatsStrip />`.
2. `TopologyToolbar`'s edit-mode-on branch gains the new "Criticality & dependencies" panel
   beneath the existing manipulation toolbar, inside the same conditional render.
3. A new `?kiosk=1` branch in `IndexRoute` (or a thin wrapper component) swaps the entire
   `ThreePaneLayout` for the full-bleed rotation view described above — this is an additive
   conditional at the top of the route, not a parallel route/page to keep in sync by hand.

No resize of the pane splitters, no new breakpoint, no change to `Splitter`/`usePaneLayout`.

## Accessibility

- **Color is never the only signal, extended to criticality:** the criticality tier is always
  paired with its text label ("low"/"medium"/"high"/"critical") inside the `Badge`, never a bare
  color swatch — same rule the state palette already follows.
- **Dimmed consequence rows keep full keyboard/link semantics:** `opacity-50` is a visual-only
  treatment; the `<Link>`/node click-through remains focusable and operable exactly as a
  full-opacity row would (no `aria-disabled`, no `tabIndex={-1}` — a consequence device is still a
  real, navigable device, just visually deprioritized).
- **Incident card "See incident"/dimmed badge carries an accessible name** distinct from a bare
  color chip — `Badge`'s own text content ("See incident") is already the accessible name, no
  extra `aria-label` needed.
- **Kiosk mode's rotation is announced, not silent:** the rotating region uses `aria-live="polite"`
  on the view-name label (Copywriting's "Incidents"/"Topology" text) so a screen reader on an
  attended kiosk still gets a signal when the view flips — the visual crossfade itself carries no
  additional ARIA (a purely decorative transition).
- **Criticality/dependency editor fields** inherit `Select`/`MultiSelect`'s existing accessible
  markup unchanged — no override needed.
- **Enter-full-screen button** is a standard focusable `Button`, keyboard-operable like every other
  `Button` instance in this app.
