**Device-type + alias prompt pattern to reuse verbatim** (`wizard.py:1036-1053`):
```python
        # Choices come from the config loader, not a literal list, so the
        # taxonomy stays site-specific (D-05) — a hardcoded list would need
        # a code change per site. No validation loop needed: the operator

        device_type = await questionary.select(
            f"Device type for {hostname}:",

        alias = raw_alias or None
```
This is the literal "same flow as tagging new hosts" D-01 requires — the retag loop's per-host prompt pair should call `questionary.select(...)` with `_load_device_types()` choices and `questionary.text(...)` for alias in this exact shape, not a re-derived UI.

    choices = [

**ETag-fetch-then-PUT fallback pattern** (`wizard.py:1069-1092`, `_create_or_update_host`):
```python
    try:
        await client.create_host(host_name=host_name, folder=folder, attributes=attributes)
    except CheckmkAPIError:
        resp = await client.get_host(host_name)
        etag = resp.headers.get("ETag")
        if not etag:
            raise
        await client.update_host_attributes(host_name, attributes, etag)
```
For the retag flow the GET-ETag-then-PUT branch is not conditional on a failed create — it is the only path (host already exists). Fetch the ETag immediately before each host's PUT inside the per-host loop, per Pitfall 2/Anti-Pattern 2 in RESEARCH.md — do not fetch all ETags up front.

**Activation call site to reuse** (`wizard.py:1877-1901`, called after Phase 5 and 6 writes — e.g. `phase6_discovery`'s call at `wizard.py:1927` `if not await _activate_pending_changes(client, connection):`):
```python
    if not await _activate_pending_changes(client, connection):
        console.print("[yellow]Continuing to discovery despite the activation failure above — results may be incomplete.[/yellow]")
```
The retag flow's final step must call `_activate_pending_changes(client, connection)` exactly like this — same best-effort "warn, don't raise" degrade posture, not a hard failure.

**Error handling pattern** (module-wide convention, see `_ensure_device_type_tag_group`, `wizard.py:693-755` — best-effort catch of `CheckmkAPIError` with a yellow warning and continue, never letting one host's failure abort the loop):
```python
        except CheckmkAPIError as exc:
            console.print(f"[yellow]could not provision device_type tag group: {exc}[/yellow]")
```
Apply the same shape per-host inside the retag loop: catch `CheckmkAPIError` around each host's GET/PUT, print a yellow warning naming the host, and continue to the next host rather than aborting the whole folder's retag.

## Shared Patterns

### Best-effort / graceful-degradation error handling
**Source:** `src/checkmk_wizard/wizard.py:693-755` (`_ensure_device_type_tag_group`), `wizard.py:1877-1901` (`_activate_pending_changes`), `scripts/mqtt_poller.py:1096-1108` (REST-degrade in `run_forever`)
**Apply to:** the retag flow's per-host GET/PUT loop (TAG-04) and OPS-03's retry loop — catch the narrowest applicable exception (`CheckmkAPIError` in wizard.py, `LivestatusError`/`RestError` in mqtt_poller.py), log/print a warning naming what failed, and continue rather than aborting the whole run. Reserve a hard `return`/raise for only the terminal case (retry tuple exhausted, or no ETag at all).

### Bounded retry via a module-level delay tuple, not a generic retry decorator
**Source:** `src/checkmk_wizard/wizard.py:1874` `_DISCOVERY_RETRY_DELAYS_SECONDS = (10, 20, 30)`
**Apply to:** OPS-03's `_STARTUP_RETRY_DELAYS_SECONDS = (5, 10, 15)` in `scripts/mqtt_poller.py` — same shape (module-level tuple of ints, iterated with `time.sleep(delay)`/`stop_event.wait`), not a new abstraction.

### Activation after any WATO-pending write
**Source:** `src/checkmk_wizard/wizard.py:1877-1901` (`_activate_pending_changes`), called at `wizard.py:1927` from `phase6_discovery`
**Apply to:** the retag flow (TAG-04) — every folder's retag loop must end with a call to `_activate_pending_changes(client, connection)`, using the exact same `force_foreign_changes=True` call already established, otherwise the tag change never reaches Livestatus/the poller/Phase 11's dashboard.

### `questionary.Question.ask_async` monkeypatch test skeleton
**Source:** `tests/test_wizard.py:941-952` and every other prompt-driven test in the file (e.g. lines 179-184, 588-593)
**Apply to:** all new `tests/test_wizard.py` tests for the retag flow and any new entry-point menu prompt — `answers = iter([...])` with an inline comment naming each prompt in call order, `fake_ask(self, patch_stdout=False, kbi_msg="")`, `monkeypatch.setattr(questionary.Question, "ask_async", fake_ask)`.

### respx-mocked REST client unit tests
**Source:** `tests/test_api.py:121-186` (`test_list_hosts_returns_value_array`, `test_update_folder_attributes_sends_update_attributes_and_etag`, `test_list_folders_returns_value_array`)
**Apply to:** any new `test_api.py` assertions on `update_host_attributes`'s sent body shape — `with respx.mock:`, mock the exact URL, assert `route.called`, assert `If-Match` header, assert `json.loads(route.calls.last.request.content)` equals the expected body dict.

## Conventions

The repo-wide deterministic convention-derivation tool (`gsd-tools.cjs verify conventions --derive`) was invoked both scoped to `src/checkmk_wizard` and unscoped (repo-wide) and returned `{"skipped": true, "reason": "no-readable-files"}` in both cases — this tool's file-name/identifier/export/import axis detectors target JS/TS-style codebases (the shared module `gsd-code-reviewer` also uses) and this is a pure-Python repo, so it has no readable files to derive from. Convention derivation skipped (no-readable-files: tool targets JS/TS conventions, repo is Python-only).

In place of the automated 4-axis table, the project's own `CLAUDE.md` "Conventions" section (already read as required project context) is the authoritative, human-curated equivalent for this repo and should be treated as the "named contract" for Phase 10.1's edits:
- File naming: `snake_case.py`, one module per domain concern (`api.py`, `site.py`, `wizard.py`, etc.) — not applicable here since no new files are created by this phase.
- Identifier casing: `snake_case` for functions/locals/parameters, `PascalCase` for classes/dataclasses, `UPPER_SNAKE_CASE` for module-level constants (e.g. `_DISCOVERY_RETRY_DELAYS_SECONDS`, `_STARTUP_RETRY_DELAYS_SECONDS` follows this exactly).
- Export style: no `__all__`/explicit export lists anywhere in the codebase — everything module-public is importable by name; private helpers are single-underscore-prefixed (`_ensure_device_type_tag_group`, `_activate_pending_changes`) and are still imported directly by tests.
- Import style: `from __future__ import annotations` as the first import in every module (already present in all files this phase touches); otherwise plain `import`/`from X import Y`, no path aliases (pure-Python, no bundler).

**Contested hotspots (author's choice):** none identified for this repo — unlike a dual CJS/ESM codebase (where `bin/lib/**` is CJS and `sdk/src/**` is ESM as two internally-consistent-but-mutually-contested halves), this is a single-language, single-style Python repo with no comparable split. If a future phase introduces a second language surface (e.g. a JS dashboard frontend for Phase 11), that surface would become its own internally-consistent-but-repo-wide-contested zone, mirroring that pattern — not a concern for Phase 10.1's edits, which stay entirely inside the existing Python module set.
