## Summary

This phase has two structurally different pieces of work. TAG-04 (the substantive one) is a **new interactive flow**, not a bug fix — the wizard has no branch point today for anything other than the linear 7-phase pipeline (`run()` at `wizard.py:2065-2076` calls `phase1` through `phase7` unconditionally, and `main()` at `wizard.py:2079-2080` has zero CLI argument parsing). Building a folder-scoped bulk retag flow means deciding where a *second* entry point lives, then reusing `list_folders()`, `list_hosts()`, `update_host_attributes()` (all already proven in `api.py`) plus the ETag-fetch-then-PUT pattern already established at `wizard.py:1085-1092` (`_create_or_update_host`'s fallback branch). Critically, `update_host_attributes()`'s PUT body key is `"attributes"` (api.py:220), not `"update_attributes"` like the folder equivalent (api.py:186) — this difference is unverified against live Checkmk behavior for whether it's a **merge** or **full replace**, and is the single highest-risk unknown in this phase (see Pitfall 1). The remaining four gaps (OPS-01..OPS-04) are small, surgical, well-localized fixes each pointing at one exact file/line already identified by Phase 10's own findings, verified again independently in this research pass.

**Primary recommendation:** For TAG-04, add bulk-retag as a **second top-level flow selected by a startup menu prompt** inside `main()`/`run()` (Candidate 2 below), not a new phase function slotted into the existing `phaseN_*` sequence — the existing phases are strictly linear and none of them re-enter earlier state, and TAG-04 explicitly must NOT run promotion or touch monitoring method, so it does not belong inside `phase4_classification`/`phase5_onboarding` at all. For OPS-01..04, apply the four described point-fixes directly; none require new abstractions.

### Pattern 1: TAG-04 entry-point candidates (the planner must choose, not silently pick one)

The wizard's `run()` (`wizard.py:2065-2076`) and `main()` (`wizard.py:2079-2080`) have **no branching today** — `main()` is a bare `asyncio.run(run())` with zero `argparse`/`sys.argv` handling (confirmed: `grep -n "argparse\|sys.argv"` against `wizard.py` returns nothing). `phase1_site_bringup()` already does all the "connect to an existing or new site" work the retag flow also needs (site name prompt, credential bootstrap, `CheckmkClient` construction) — this is the one piece of existing machinery the retag flow should reuse, regardless of which candidate is chosen.

**Candidate A — New CLI flag on the single console-script entry point** (`checkmk-wizard --retag-hosts`)
- Add `argparse` to `main()`, branch before calling `run()`.
- Pro: no interactive prompt added to the default flow at all; scriptable (`checkmk-wizard --retag-hosts` is a clean non-interactive-adjacent invocation for repeat use).
- Con: `main()` currently has zero argparse — this is the first CLI-flag surface in the whole project; sets a precedent the rest of the wizard doesn't follow (every other branch point in this codebase is an interactive `questionary` prompt, per the "Terminal UI is built with questionary" architecture note in `CLAUDE.md`). Also, `pyproject.toml`'s `[project.scripts]` doesn't change — this is purely inside `main()`.

**Candidate B — Startup menu prompt inside `run()`/`main()`** ("What do you want to do? [Full onboarding / Bulk retag existing hosts]")
- `run()` becomes: prompt for mode first, then either the existing 7-phase call chain or a new `retag_hosts(client)` call, both wrapped in the same `phase1_site_bringup()` → `async with CheckmkClient(...)` scaffolding.
- Pro: matches the existing UX convention exactly (interactive `questionary.select`, consistent with every other decision point in the wizard) and needs zero new argparse machinery.
- Con: **every existing `test_wizard.py` test that drives `run()` end-to-end would need its answer iterator to grow one more front-loaded answer** — but a grep of `test_wizard.py` shows `run()` itself is never called directly by any test (only individual `phaseN_*` functions are imported and tested in isolation, per the import list at `tests/test_wizard.py:19-63`). So this candidate's blast radius on existing tests is actually **zero** for the current suite; only new tests for the new menu itself are needed. This is the strongest practical argument for Candidate B.

**Candidate C — Separate top-level function, invoked as a distinct step appended to `phase1_site_bringup()`'s output, but not part of `run()`'s sequence**
- E.g. a standalone `async def retag_hosts(client: CheckmkClient) -> None` function that the operator reaches only by choosing it at the same menu point as Candidate B — functionally this collapses into Candidate B; listed separately only because it clarifies that the retag flow's *internals* (folder select → host list → per-host device_type/alias prompt → PUT) are naturally their own function regardless of which entry mechanism is chosen, mirroring how `phase4_classification`/`phase5_onboarding` are already separate functions from `run()`'s call chain.

**Recommendation:** Candidate B (startup menu prompt), because it has zero blast radius on the existing answer-iterator test suite (confirmed above — `run()` is untested directly) and matches the codebase's exclusively-interactive UX convention. The planner should still explicitly decide this, since it is a genuine architectural choice with real tradeoffs, not a foregone conclusion.

### Pattern 2: Folder-scoped host listing and retag flow shape

```python
# Source: derived from existing api.py methods (list_folders, list_hosts,
# get_host, update_host_attributes, activate_changes — all already present,
# no new CheckmkClient method needed) + wizard.py's existing
# _activate_pending_changes helper (wizard.py:1877-1901)

async def retag_hosts(client: CheckmkClient, connection: CheckmkConnection) -> None:
    folders = await client.list_folders()  # api.py:164 -- [{"id": "/vlan10", ...}, ...]
    folder_choice = await questionary.select(
        "Which folder?",
        choices=[questionary.Choice(f["id"], value=f["id"]) for f in folders],
    ).ask_async()

    all_hosts = await client.list_hosts()  # api.py:209 -- includes extensions.folder + extensions.attributes
    in_folder = [
        h for h in all_hosts
        if h.get("extensions", {}).get("folder") == folder_choice  # live-verified shape, Phase 10-06
    ]
    if not in_folder:
        console.print(f"[yellow]No hosts found in folder {folder_choice}.[/yellow]")
        return

    device_types = _load_device_types()  # wizard.py:633, already exists
    for host in in_folder:
        name = host["id"]
        current_type = host.get("extensions", {}).get("attributes", {}).get("tag_device_type", "other")
        current_alias = host.get("extensions", {}).get("attributes", {}).get("alias", "")
        new_type = await questionary.select(
            f"{name} (current: {current_type}):",
            choices=[questionary.Choice(dt, value=dt) for dt in device_types],
            default=current_type if current_type in device_types else device_types[0],
        ).ask_async()
        new_alias = (await questionary.text(
            f"Alias for {name} (blank to keep '{current_alias}'):", default=""
        ).ask_async()).strip() or current_alias

        # ETag is per-object and expires the instant any other write touches
        # the host — must be fetched immediately before each PUT, not batched
        # up front (see Pitfall 2).
        get_resp = await client.get_host(name)
        etag = get_resp.headers.get("ETag")
        if not etag:
            console.print(f"[red]No ETag for {name} — skipping.[/red]")
            continue
        await client.update_host_attributes(
            name,
            {"tag_device_type": new_type, "alias": new_alias},
            etag,
        )

    # Without this, the tag change sits as a pending WATO change and never
    # reaches Livestatus (what the poller reads) or the Checkmk UI's "OK"
    # state -- the exact same activation step every other write in this
    # codebase already goes through (wizard.py:2013-2020, phase7_activation).
    await _activate_pending_changes(client, connection)
```

**Open question this pattern surfaces, not resolved by existing code:** whether `update_host_attributes`'s PUT body (`{"attributes": {...}}`, api.py:220) is a **merge** (only the given keys change, everything else — `ipaddress`, `snmp_community`, `tag_agent`, etc. — untouched) or a **full replace** of the host's attribute set. This matters enormously here because the whole point of TAG-04 is "must not clobber the existing monitoring method." The only prior use of this method in this codebase (`_create_or_update_host`'s fallback, `wizard.py:1085-1092`) always passes the **full** attribute set it would have used for `create_host()` anyway — so it never tested the "partial update preserves the rest" case. **This must be live-verified as the first task of implementation**, exactly the way Phase 10 itself live-verified its own REST assumptions (10-06-SUMMARY.md). If it turns out to be a full replace, the retag flow must first `GET` the host's full current `extensions.attributes` and merge client-side before PUTting, not just send the two changed keys.

### Anti-Patterns to Avoid
- **Re-scan-and-re-promote as the retag mechanism:** this is the exact anti-pattern TAG-04 exists to eliminate (10-06-SUMMARY.md finding 1) — it overwrites monitoring method. Do not route TAG-04 through `phase3_discovery`/`phase4_classification`/`phase5_onboarding` in any form.
- **Batching all hosts' ETags up front, then PUTting in a loop:** an ETag is a precondition on the object's state at fetch time; if two hosts are unrelated this doesn't cross-contaminate, but if any other process (the Checkmk UI, `omd` cron network-scan) touches a host between fetch and PUT, that host's stale ETag causes a 412 Precondition Failed — fetch-then-immediately-PUT per host, not fetch-all-then-PUT-all.
- **Skipping `_activate_pending_changes`:** a retag flow that writes attributes but never activates leaves the change invisible to Livestatus/the poller/dashboard indefinitely — this would silently fail TAG-04's actual purpose (Phase 11 renders real device types) while still reporting REST 200s.

## Common Pitfalls

### Pitfall 1: `update_host_attributes` may be a full replace, not a merge — unverified
**What goes wrong:** If PUT `.../objects/host_config/{name}` with `{"attributes": {"tag_device_type": "X", "alias": "Y"}}` replaces the host's entire attribute set rather than merging, every other attribute (`ipaddress`, `tag_agent`, `tag_snmp_ds`, `snmp_community`, `tag_criticality`) silently reverts to Checkmk's defaults — exactly the "overwrites the host's existing monitoring method" failure TAG-04 exists to prevent.
**Why it happens:** The only existing call site for this method (`wizard.py:1092`) always sends the complete attribute set anyway, so this codebase has never exercised the partial-update case.
**How to avoid:** Live-verify with a real GET-before/PUT-two-keys/GET-after cycle against a test host on the real site as the first implementation task (mirroring 10-06's own live-verification discipline). Checkmk's REST API documentation (`docs.checkmk.com`, host_config PUT endpoint) should also be checked via Context7/WebFetch before implementation — this research pass did not access it live and cannot upgrade this claim past MEDIUM confidence. If it is a full replace, the plan must add a GET-full-attributes-then-merge-client-side step before every PUT.
**Warning signs:** After a retag run, previously-working hosts silently lose ping/agent monitoring or show `ipaddress` blank.

### Pitfall 2: Stale ETag on batched writes
**What goes wrong:** Fetching all N hosts' ETags up front, then looping PUTs, risks a 412 if anything else touches a host mid-loop (Checkmk's own cron network-scan runs on `scan_interval: 86400` per `_network_scan_attributes`, `wizard.py:605-628` — unlikely mid-session but not impossible on a long-running bulk retag of many hosts).
**Why it happens:** ETags are optimistic-concurrency tokens scoped to the object's exact current state, not the whole request batch.
**How to avoid:** Fetch each host's ETag immediately before its own PUT, inside the same per-host loop iteration (Pattern 2 above already does this correctly).
**Warning signs:** Sporadic `CheckmkAPIError` with a 412 status on some but not all hosts in a bulk run.

### Pitfall 3: Bulk update of ~20 hosts and REST call volume/rate limiting
**What goes wrong:** 20 hosts each need one GET (ETag fetch) + one PUT = 40 sequential REST calls plus one final `activate_changes`. Checkmk Raw Edition (the pinned image, `checkmk/check-mk-raw:2.4.0-latest`, `deploy/compose.yaml:4`) has no documented hard API rate limit in this codebase's existing research (10-RESEARCH.md does not mention one), but sequential `httpx` calls inside a single `async with CheckmkClient` session (matching every other multi-host loop already in this file, e.g. Phase 5's `_onboard_hosts`) is the established, safe pattern — no need for `asyncio.gather` concurrency, and concurrent PUTs to different hosts are unlikely to collide on ETags but add complexity with no demonstrated benefit at this host count (~20, not thousands).
**How to avoid:** Match the existing sequential-loop pattern already used throughout `wizard.py`'s Phase 5 onboarding; do not introduce new concurrency for this phase.
**Confidence:** MEDIUM — no live volume test exists for 20 sequential attribute PUTs in this codebase; flagged as a live-verification item, not assumed safe purely from reasoning.

### Pitfall 4: OPS-03's "consistent failure posture" conflicts with an explicit prior design decision
**What goes wrong:** `run_forever()` (`scripts/mqtt_poller.py:1052-1128`) currently treats Livestatus column-probe failure at startup as **fatal** (`_logger.error`, return 1, lines 1082-1085) but REST folder-lookup failure as **always-degrade**, even at the very first cycle (`fetch_host_folders` wrapped in `try/except RestError`, warns and reuses `last_folders` — which starts as `{}`, lines 1100-1108). This is not an oversight — `10-CONTEXT.md`'s D-03 and the poller's own inline comment (`scripts/mqtt_poller.py:1096-1099`, "A folder lookup is enrichment, not the poller's core duty (RESEARCH.md Pitfall 3)") explicitly designed REST as enrichment-only, non-fatal by design, because Livestatus is the poller's sole mandatory data source (no Livestatus = no snapshots at all = nothing to publish) while REST only adds the `folder` field. The two dependencies are not actually equivalent in severity, and treating them identically (e.g. making Livestatus non-fatal too) would silently mask cases where the poller can never emit any device data.
**Why it happens:** 10-06-SUMMARY.md's finding 4 was written from an operational incident (a Checkmk container restart raced the poller and killed it — `_logger.error` + `return 1` on the very first transient Livestatus failure, with no retry), not from a design-symmetry argument. The real bug is that Livestatus failure at startup has **zero retry tolerance** for a known-transient condition (container restart race), not that its severity classification is wrong.
**How to avoid:** Don't literally equalize the two postures (that would make a real "Livestatus permanently unreachable" case silently hang forever with no operator signal). Instead, give Livestatus's startup probe a **bounded retry with backoff** before treating it as fatal — mirroring the exact precedent this codebase already uses for a different known-transient-timing case: `_DISCOVERY_RETRY_DELAYS_SECONDS = (10, 20, 30)` in Phase 6 (`wizard.py:1590`, for a freshly-registered agent's first data push). This closes the observed container-restart-race bug while preserving the deliberate mandatory-vs-enrichment distinction between the two dependencies. The planner should treat this as the resolution, and should explicitly note in the plan that full postural symmetry was considered and rejected, citing this reasoning — not silently pick one without addressing the tension OPS-03's wording implies.
**Warning signs:** `podman logs mqtt-poller` shows `Cannot start: ...` and exit within the compose `restart: unless-stopped` window during any Checkmk container restart, even a routine one.
