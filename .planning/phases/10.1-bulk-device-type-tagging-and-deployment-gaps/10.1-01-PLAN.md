<objective>
Close the single highest-risk unknown in this phase before any retag code is written: does `CheckmkClient.update_host_attributes()`'s PUT body (`{"attributes": {...}}`, `src/checkmk_wizard/api.py:214-223`) **merge** the given keys into the host's existing attribute set, or **replace** that set wholesale?

Purpose: 10.1-RESEARCH.md Assumption A1 / Open Question 1. The only existing call site of this method (`_create_or_update_host`'s fallback branch, `src/checkmk_wizard/wizard.py:1085-1092`) always sends the *complete* attribute set it would have passed to `create_host()`, so this codebase has never exercised a true partial update. If the semantics are "replace", a bulk retag that sends only `tag_device_type` + `alias` would silently strip `ipaddress`, `tag_agent`, `tag_snmp_ds` and `snmp_community` from every retagged host — the exact "overwrites the host's existing monitoring method" failure TAG-04 exists to prevent (10-06-SUMMARY.md finding 1). This repo's own rule is that Checkmk's live server behaviour, not its docs, is the source of truth (`src/checkmk_wizard/api.py:200-206`), and Phase 10 established the pattern of settling such questions with a stdlib-only probe plus a blocking live checkpoint.

Output: `scripts/probe_host_attribute_merge.py` with a dated live-verified findings block recording the verdict (MERGE or REPLACE) and, either way, whether the replace-safe full-attribute echo PUT is accepted and which keys had to be stripped from it. Plan 10.1-03 reads that block instead of guessing.
