<objective>
Move the poller to MQTT v5 with a deterministic `event_id` user property on every discrete message (D-10, D-11), read and validate `SITE_SEN` (D-12 poller side), and publish each cycle's history rows as chunked QoS 1 MQTT messages for the cloud ClickHouse writer (D-02, D-03).

Purpose: the archive deduplicates on (sen, site, subtopic, event_id); the cloud writer deduplicates history chunks on the same id. Live pass-through of the property was proven in plan 17-01 (A1).
Output: updated scripts/mqtt_poller.py and tests. Status throttling is NOT in this plan (plan 17-04, same file, next wave).

Flagged assumptions for user review:
- FA-6 (RESEARCH Open Question 2, history volume): history is published every poll cycle, uncompressed, chunked at 500 rows, exactly the rows build_history_rows already produces. No gzip, no 1-minute aggregation, no publish-interval knob. RESEARCH estimates about 2.2 GB/day over 4G for a fleet of the walkthrough's size; reducing it (interval knob, aggregation, gzip) is a follow-up decision for the user.
- FA-7: history publishing is switched on by a non-empty SITE_SEN (the value only matters for the cloud feed). With no bridge configured the messages have no subscriber and the broker discards them.
- FA-8 (RESEARCH Open Question 3): the retained `lan/events/recent` array keeps its current shape; its event_id is a content hash of the whole array. A per-event message is not added in this phase.
- FA-9: the browser publishes admin/cmd and needs/triage/cmd over MQTT 3.1.1, so those command messages carry no event_id property (the archive contract makes it optional; each command payload already has its own `id`). The poller's admin ack carries event_id `<command id>-ack`.
- FA-10 (RESEARCH Pitfall 8): device status stays QoS 0; the bridge forwards it at QoS 0, so a state change can be lost on the WAN until the next heartbeat. Not changed in this phase.
- The JSON payload of the history chunk also carries `event_id` (an envelope this phase defines); no existing topic's payload shape changes.
</objective>

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-17-11 | Tampering | SITE_SEN env | mitigate | `_SEN_RE.fullmatch` at startup, exit 2 on mismatch, so a malformed SEN never shapes anything downstream |

| T-17-15 | Denial of service | oversized messages dropped by broker | mitigate | HISTORY_CHUNK_ROWS 500 keeps each chunk far below message_size_limit 2 MB |
