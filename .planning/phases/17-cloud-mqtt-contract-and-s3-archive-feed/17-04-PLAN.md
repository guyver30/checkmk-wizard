<objective>
Throttle the shared `lan/devices/{id}/status` topic in the poller (D-07): publish on discrete change, on a gauge crossing a warn/crit band, or on a configurable heartbeat (D-08, default 300 s), and carry the consequences of D-09 into the payload so the dashboard does not mark quiet hosts STALE.

Purpose: per-cycle status is the dominant small-message cost on the 4G link; the bridge forwards whatever the local broker receives, so the throttle must happen in the poller.
Output: pure decision functions, wiring in run_cycle, tests.

Staleness design (resolves RESEARCH Open Question 5, read against dashboard-react/src/lib/staleness.ts):
- isDeviceStale prefers the payload's Checkmk `staleness` and only falls back to `timestamp` age when staleness is null. A throttled retained payload freezes `staleness`, so the poller treats "staleness >= 3" (the dashboard's STALENESS_FACTOR) as part of the discrete signature: a host becoming stale (or recovering) republishes at once.
- For hosts with null staleness, the payload carries `heartbeat_s`; plan 17-05 widens the timestamp-age fallback to STALENESS_FACTOR x max(poll interval, heartbeat_s).
- A dead poller is already caught by PollerOfflineBanner through `lan/poller/status` (isPollerStale), which keeps publishing every cycle.
- FA-11 (flagged): with the default heartbeat, on-prem gauges refresh every 5 minutes (D-09 accepted consequence) and the analytics container's in-memory status view refreshes at the same rate except on band crossings.
</objective>
