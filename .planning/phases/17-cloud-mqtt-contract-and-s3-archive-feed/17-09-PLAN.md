<objective>
Finish D-10 for the second client the decision names (analytics/service.py:209): move the on-prem analytics MQTT client to v5 and give every discrete analytics publish (`lan/needs/{id}/status`, `lan/forecasts/{host}`, `lan/incidents/{id}/narration`, and the tombstones of all three) a deterministic event_id user property (D-11), using the same format as the poller (plan 17-03).

Purpose: these topics live under sites/<site_id>/ and therefore cross the bridge (plan 17-02, `topic #`) into the archive; the archive deduplicates on (sen, site, subtopic, event_id) and never synthesizes an id. Without this plan the analytics outputs would be the only discrete messages archived without one.
Output: updated analytics/publish.py, analytics/service.py and their tests.

Runs after plan 17-06 (both edit analytics/service.py) and plan 17-03 (the poller's content_event_id is the format reference for the parity test).

Flagged assumption for user review:
- FA-17: analytics tombstones use `<key>-cleared-<epoch>` / `<incident_id>-narration-closed-<epoch>`, where epoch is the `now` of the evaluation cycle or inbound-message handling that decided the clear, computed once and reused for every tombstone of that cycle. This is the same rule as the poller's `<incident_id>-closed-<cycle_epoch>` (plan 17-03): identity plus the deciding cycle, not the publish instant. Need and forecast publishes are refreshed on every slow cycle with a new `generated_at`, so their content hash, and therefore their event_id, changes per slow cycle; unchanged fast-tick republishes are already suppressed by the existing `_need_changed` check.
</objective>
