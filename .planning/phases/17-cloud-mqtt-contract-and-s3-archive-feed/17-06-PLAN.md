<objective>
Build the cloud side of D-02: a `cloud-ingest` mode of the existing analytics container that subscribes to one site's history chunks on the cloud broker, deduplicates them by event_id (D-03), validates them, and inserts them into ClickHouse. The poller keeps no cloud ClickHouse credentials.

Per D-01 the archive and this writer are side-consumers of the broker; dashboard and on-prem analytics keep reading retained state from the broker unchanged. Moving the on-prem analytics client (analytics/service.py::build_client) to MQTT v5 and adding event_id to its publishes (D-10, D-11) is plan 17-09, which runs after this plan because both edit analytics/service.py.

Purpose: the cloud ClickHouse gets the same history rows the on-prem ClickHouse gets, without a new service and without double-counting redeliveries.
Output: config fields, an allow-listed history insert, `analytics/ingest.py`, the main() dispatch, tests. Deploying the cloud container is out of scope (CONTEXT domain); plan 17-08 documents how to run it.

Flagged assumptions for user review:
- FA-13: cloud-ingest is history only. Events, incidents, triage audit and needs/forecasts stay with the on-prem analytics container (whose outputs already reach the archive through the bridge); running the full service in the cloud would publish duplicate needs onto topics the on-prem container owns.
- FA-14 (RESEARCH Open Question 4): one cloud-ingest instance per (SEN, site), each with its own CLICKHOUSE_URL/database; the history tables gain no site or SEN column in this phase. A shared multi-site cloud ClickHouse is a schema decision for the cloud deployment.
- FA-15 (RESEARCH A7 unverified): dedupe is in-process only, a bounded set of the last 4096 (topic, event_id) pairs. ClickHouse insert-deduplication tokens are not used. A restart forgets the set; with manual acks a chunk is acknowledged only after its insert attempt, so the realistic duplicate window is a redelivery that straddles a restart.
- FA-16: an insert failure is logged and the chunk is still acknowledged (same "gap reads as no data" posture as the poller's D-47); the S3 archive remains the replay source.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| cloud broker -> cloud-ingest | Untrusted MQTT payloads from any site that can publish under app/<SEN>/ |
| cloud-ingest -> ClickHouse | SQL INSERT over HTTP with a writer credential |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-17-22 | Tampering / Injection | table name in INSERT SQL | mitigate | Table derived from a fixed topic-segment map and checked against HISTORY_INGEST_TABLES before any request; payload "table" must match the topic |
| T-17-23 | Tampering | row contents | mitigate | validate_rows enforces exact column sets, types, ranges, finite numbers and ts format; rows serialized with json.dumps(allow_nan=False) by the existing insert helper |
| T-17-24 | Repudiation / Tampering | replayed or redelivered chunks inflating rollups | mitigate | (topic, event_id) dedupe set; ack only after the insert attempt |
| T-17-25 | Denial of service | oversized or flood payloads | mitigate | 4 MB cap per chunk before json parse; bounded seen set; broker-side message_size_limit |
| T-17-26 | Spoofing | a site publishing into another site's history | transfer | Cloud broker ACL `pattern write app/%u/#` (plan 17-02 example, verified in 17-01 A8) confines each SEN; the ingest instance subscribes only its own app/<SEN>/<site>/history/+ |
| T-17-27 | Elevation of privilege | on-prem analytics writing poller tables | mitigate | insert_rows keeps refusing history.metrics/host_state/service_state; only cloud-ingest uses the second allow-list |
| T-17-28 | Information disclosure | ClickHouse and broker passwords in logs | mitigate | AnalyticsConfig.__repr__ keeps masking secrets; new fields are non-secret |
</threat_model>
