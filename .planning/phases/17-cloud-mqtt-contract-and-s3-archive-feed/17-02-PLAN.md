<objective>
Ship the broker side of the cloud feed: a rendered Mosquitto bridge that remaps `sites/<site_id>/` to `app/<SEN>/<site_id>/` on the way out (D-04, D-05), the local `bridge` login, explicit queue limits for WAN outages, a cloud ACL example, and the compose/env wiring for `SITE_SEN`, cloud broker settings and the metrics heartbeat (D-08, D-12 env side).

Purpose: the poller, ACLs and dashboard keep the local namespace; only the broker knows about SEN and the cloud.
Output: template + renderer + tests, mosquitto.conf/ACL changes, cloud ACL example, compose/init-env/.env.example wiring.

Flagged assumptions for user review (recorded here and in the SUMMARY):
- FA-1 (RESEARCH Open Question 1, status archival): the bridge forwards the whole subtree with `topic #`, so the throttled `lan/devices/+/status` messages (plan 17-04) also reach the archive. D-06 forbids archiving status "as a stream"; after D-07 throttling it is change-only plus a 5-minute heartbeat, not a per-cycle stream. Excluding it would need one bridge topic line per subtree; not done. The same `topic #` line also forwards `lan/poller/status`, which stays per cycle (D-09 liveness signal), so one small poller-status message per poll cycle (every 15 s) crosses the 4G link and lands in the archive as a stream, which D-06 as written excludes. USER DECISION REQUESTED (surfaced again in plan 17-08's checkpoint and docs "Flagged for review" list): accept per-cycle poller status in the archive as the cloud-side liveness signal, or replace `topic #` with explicit per-subtree `topic` lines that omit `lan/poller/status` (and optionally `lan/devices/+/status`). Switching is a template-only change in this plan (the remap prefixes stay the same), so it can be made after review without replanning.
- FA-2: the cloud feed is opt-in by `CLOUD_BROKER_HOST`. With it empty the bridge is not rendered and the stack behaves as before Phase 17. `SITE_SEN` is "required" in the sense that the wizard always asks for it (plan 17-07) and the renderer refuses to start a bridge without a valid one; compose does not hard-fail on an empty SITE_SEN, so upgrading a deployment does not break `compose up`.
- FA-3: queue limits `max_queued_messages 20000` and `max_queued_bytes 104857600` (100 MB, about one hour of unthrottled history at the walkthrough's 380 KB/cycle estimate). Beyond them Mosquitto drops; the loss window is documented in plan 17-08. Memory impact (also relevant to FA-2's opt-in posture): mosquitto.conf(5) makes both limits global per-client settings, not bridge-only, so every client with a queue (a persistent session that is offline, or a slow connected subscriber such as a dashboard browser on a weak link) may also hold up to 20000 messages / 100 MB. Worst-case broker memory is therefore roughly 100 MB times the number of simultaneously backlogged clients; in practice only the bridge backlogs for long (the poller, analytics and browser logins use clean sessions, dropped on disconnect), and the setting applies even when no bridge is rendered. Accepted for the on-prem broker's handful of clients; documented in plan 17-08.
- FA-4: the cloud broker password charset is restricted to `[A-Za-z0-9_.~=+-]` (1-256 chars) so it can pass through sed safely.
- FA-5: the bridge's remote username is the SEN itself, so one static `pattern write app/%u/#` rule covers every SEN; two Checkmk sites sharing a SEN share that login and are told apart by remote_clientid `bridge-<SEN>-<site_id>`.
