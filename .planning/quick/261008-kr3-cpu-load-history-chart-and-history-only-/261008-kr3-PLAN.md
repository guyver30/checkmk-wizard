<objective>
Make the CPU utilization chart history-only (measured line plus Checkmk warn/crit levels, no forecast) and add a CPU load history chart (load1, load5, load15 plus absolute warn/crit levels) opened from the Load gauge in host details. The CPU gauge gets the same entry point to the utilization history view.

Purpose: operator decision. CPU utilization and CPU load swing hour to hour; a straight-line projection, a confidence badge or a "No clear trend" caption is noise for them. The operator wants their history and how close they run to the levels.
Output: a history client extension and pure helpers (with unit tests), a shared zoom hook and toolbar extracted from ForecastChart, a new HistoryChart and MetricHistoryDialog (with component tests), the two gauge entry points, a README paragraph and a dated UI-SPEC amendment.

Design choice (operator item 1, "mode prop vs shared pieces"): a sibling HistoryChart built on pieces extracted from ForecastChart, NOT a mode="history" prop. Reason: in ForecastChart nearly every computed value depends on the fit (the x domain extends to the later crossing, the y domain includes the projection, markers, captions, the aria status word, the Trend legend). A history mode would add a branch to each, and the component would still draw only one series, so the three-line load chart would need a second component anyway. Extracting the zoom interaction (hook + toolbar) and the pure geometry/format helpers lets both charts share them with no copy-paste, keeps the fit logic out of history charts (operator item 2), and leaves ForecastChart's rendering untouched; the unchanged ForecastChart.test.tsx (23 cases including the zoom suite) is the guard for the extraction.

Analytics decision: analytics keeps publishing the util fit (no analytics change). The dashboard ignores it for history-only metrics: the dialog takes only the fit's warn/crit (as a fallback level, see Task 1) and its unit, and the Trends list in host details skips history-only metrics. DEFAULT_TREND_NEED_METRICS in analytics/config.py is ("fs_used_percent", "mem_used_percent"), so no trend need for util exists by default; if an operator adds util via TREND_NEED_METRICS, its "View chart" still lands on the history-only view through the ForecastDialog dispatcher.

Data decision (operator item 4), verified while planning:
- scripts/mqtt_poller.py build_history_batch writes one history.metrics row per perf_data label of every service with columns ts, host, service, metric, value, warn, crit. The CPU load service is GAUGE_CPU_LOAD_SERVICE = "CPU load" with perf-data names "load1", "load5", "load15" (cited there from Checkmk 2.4.0 cmk/plugins/lib/cpu_load.py). CPU utilization is GAUGE_CPU_SERVICE = "CPU utilization", metric "util".
- deploy/clickhouse-config/initdb/02-users.sh grants SELECT ON history.* TO dashboard_reader; deploy/dashboard-nginx.conf location = /ch-api/ is GET-only. The existing HISTORY_SQL (one host/service/metric per call, typed {h:String}/{s:String}/{m:String}/{d:UInt32} bindings) already fits load series. Therefore: one call per series, no new SQL, no poller/analytics/ClickHouse/nginx change.
- Levels: the device status payload already carries cpu_warn/cpu_crit and cpu_load_warn/cpu_load_crit (quick 261008-d0w; load levels are absolute, per-core level x CPU count). analytics/config.py notes the catalog showed util with NULL warn/crit and supplies FALLBACK_LEVELS util (85, 95), which is what the util fit's warn/crit carry today.
</objective>
