<objective>
Let the operator specify a non-default REST/GUI port for the Checkmk site by typing `host:port` at the Phase 1 host prompt, and thread that port through **only** the HTTP call sites that talk to Checkmk's site webserver.

Purpose: the official `checkmk/check-mk-raw` image serves the site on port **5000** internally (`deploy/compose.yaml`: `ports: "8080:5000"`, and the `worker` service's own `CMK_REST_API=http://checkmk:5000/dmc/check_mk/api/1.0`). Today `CheckmkConnection.base_url` and the three GUI-session-login helpers hardcode a port-80 netloc, so a real container-mode run against the documented stack fails with `GET/POST http://checkmk/dmc/check_mk/login.py -> 0: All connection attempts failed`.

Output: `host:port` accepted at the prompt, port plumbed into REST/GUI URLs, Livestatus and agent-registration paths untouched, container-mode default becomes `checkmk:5000`, tests and docs updated.

**Crux of the design — do not blur these two categories:**

| Category | Call sites | Gets the new port? |
|---|---|---|
| Speaks HTTP to the site webserver | `CheckmkConnection` (wizard.py ~507), `bootstrap_automation_user`, `bootstrap_agent_registration_secret`, `change_cmkadmin_password` | **Yes** |
| Speaks a different protocol on a different port | `_probe_livestatus_tcp(checkmk_host)` (6557), `_resolve_agent_registration_server(...)` / `livestatus.query_host_states(connection.host, ...)` (agent-receiver 8000 / Livestatus 6557) | **No — bare host, unchanged** |

`CheckmkConnection.host` therefore stays a **bare** hostname/IP, and `port` is a separate new field. Both existing `connection.host` consumers (`wizard.py:1338` `_resolve_agent_registration_server`, `wizard.py:1757` `livestatus.query_host_states`) then stay correct with zero edits — that is the reason for this shape, not an accident.
</objective>
